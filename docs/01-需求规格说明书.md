## 2. 引言

### 2.1 目的

本文档定义 SynaRoute 桌面软件的功能需求与非功能需求，作为设计、开发、测试与验收的统一依据。目标读者包括产品经理、架构师、前后端开发、测试工程师以及项目干系人。

本文档中"必须/应/可"遵循如下约定：
- 必须（P0）：MVP 交付必备，缺失即视为不可发布。
- 应（P1）：重要能力，尽量在首版交付，可有降级方案。
- 可（P2）：增强能力，允许延后至后续迭代。

### 2.2 产品范围

SynaRoute 是一款 **Windows / macOS / Linux 桌面软件**，本质是“API Key 路由代理 + 配置管理界面”。它面向使用 Claude CLI、Claude 桌面端、Codex 桌面端等 AI 编码/对话工具的用户，解决以下核心问题：

1. **多厂商 Key 的统一管理与无感切换**：在一个工具下配置多个厂商 API Key，主 Key 失败/超时时自动故障转移，用户无需手动改配置。
2. **多模型协作提升准确性（大脑聚合）**：多个模型并行解答，聚合后交由最终决策者产出更优答案。
3. **配置的可视化管理**：卡片式 Provider 列表、系统托盘快速切换、深浅主题等，对齐 cc-switch 使用体验。

范围内：
- 三类目标工具（Claude CLI、Claude 桌面端、Codex 桌面端）的 Key/模型/参数/映射配置管理。
- 本地路由代理端点的生成与生命周期管理。
- Key 无感切换（故障转移）、独立健康探测与模型/配额/余额等路由保护。
- 大脑聚合（显式桌面或 MCP 入口，普通代理请求不自动聚合）。
- 应用内加密文件方式的 Key 存储。
- 系统托盘、深浅主题、卡片式管理界面等基础功能。
- 按分类、Key、模型统计用量，并按公开价格及用户倍率估算费用。

范围外：
- 移动端客户端。
- 云端账户体系、多设备配置同步。
- 代替上游账单的结算或扣款保证；估算金额不等同于服务商实际收费。

## 3. 整体描述

### 3.1 产品愿景

让开发者"一次配置，稳定可用"：把分散在多个厂商的 API Key 收敛到一个桌面应用中统一管理，通过本地路由代理实现主备无感切换与多模型协作，在不改变现有工具使用习惯的前提下，显著提升 AI 编码/对话链路的可用性与答案质量。

### 3.2 用户画像

| 画像 | 描述 | 核心诉求 |
|---|---|---|
| 重度 AI 编码用户 | 长期使用 Claude CLI / Codex，手上有多个厂商 Key | 主 Key 挂了不中断工作，自动切备用 Key |
| 多厂商羊毛用户 | 同时持有官方与多个第三方兼容厂商 Key | 统一管理、模型名映射、按需启用/停用 |
| 质量敏感用户 | 对答案准确性要求高，愿意多花 token | 大脑聚合，多模型协作出更优答案 |
| 轻度用户 | 只有一个 Key | 直连即可，配置越简单越好 |

### 3.3 运行环境

| 项目 | 约束 |
|---|---|
| 操作系统 | Windows 10 / 11（64 位）、macOS、Linux；各平台安装包与客户端兼容性单独验收 |
| 运行形态 | 桌面 GUI 应用 + 常驻后台的本地路由代理服务 |
| 网络 | 需可访问各上游厂商 API；代理默认仅监听本机回环地址，局域网访问须显式开启并使用接入令牌 |
| 依赖工具 | Claude CLI、Claude 桌面端、Codex 桌面端（由用户自行安装） |

### 3.4 设计约束（基线决策，不可更改）

| 编号 | 约束 |
|---|---|
| CON-1 | 技术栈固定为 Tauri 2（Rust 后端 + React/TypeScript 前端），UI 使用 TailwindCSS + shadcn/ui |
| CON-2 | 目标工具为 Claude CLI、Claude 桌面端、Codex 桌面端，三个全做 |
| CON-3 | 路由采用故障转移而非轮询负载均衡；先按模型服务能力、余额和预算状态排序，再按用户优先级尝试，运行态保护可跳过候选 |
| CON-4 | 大脑聚合提供两种聚合方式可配：A 压缩汇总后交决策者；B 全量上下文交决策者 |
| CON-5 | Key 存储采用应用内加密文件（不使用明文配置、不强制依赖云端） |
| CON-6 | MVP 范围对齐 cc-switch 全功能（卡片式列表、托盘快切、深浅主题等） |
| CON-7 | UI 风格对齐 cc-switch 与 echobird |

### 3.5 假设与依赖

| 编号 | 假设/依赖 |
|---|---|
| ASM-1 | 上游厂商提供 `/models` 类接口用于拉取可用模型列表；若个别厂商不提供，需支持手动录入（见 FR-004） |
| ASM-2 | 三端分别使用各自接入机制：CLI 环境配置、桌面端 gateway 配置档、Codex provider 与模型目录；客户端升级后的兼容性仍需验收 |

## 4. 功能需求

> 编号规则：FR-xxx。每条含：描述、输入、处理、输出、优先级、验收标准。
> 功能分组：
> - 4.1 配置管理（分类/厂商/Key/模型/参数/映射）
> - 4.2 Key 无感切换（功能1）
> - 4.3 大脑聚合（功能2）
> - 4.4 路由代理服务生命周期
> - 4.5 系统托盘与主题（cc-switch 类基础功能）

### 4.1 配置管理

#### FR-001 三分类配置管理
- 描述：系统必须提供三个固定分类——Claude CLI、Claude 桌面端、Codex 桌面端。每个分类下可管理多个厂商 Key。
- 输入：用户选择分类；新增/编辑/删除厂商 Key 的操作。
- 处理：按分类隔离存储各自的 Key 列表与代理配置；分类间配置互不影响。
- 输出：卡片式 Provider 列表，展示每个 Key 的名称、启用状态、健康状态、映射模型摘要。
- 优先级：P0
- 验收标准：
  1. 三个分类均可见且可切换。
  2. 在任一分类下新增的 Key 只出现在该分类，不串到其他分类。
  3. 列表以卡片形式呈现，风格对齐 cc-switch。

#### FR-002 厂商 Key 增删改查
- 描述：用户必须能在某分类下新增、编辑、删除、复制一条厂商 Key 配置。
- 输入：Key 名称（备注）、厂商标识、base_url、API 密钥、可选的自定义请求头。
- 处理：校验必填项与 base_url 合法性；密钥写入加密存储（见 FR-018）；保存后刷新列表。
- 输出：新增/更新后的 Key 卡片；操作成功/失败提示。
- 优先级：P0
- 验收标准：
  1. 新增 Key 后在列表可见，密钥不以明文写入磁盘。
  2. 编辑保存后再次打开显示为最新值。
  3. 删除需二次确认，删除后不可在列表看到。

#### FR-003 Key 启用/停用开关
- 描述：每个 Key 的“是否启用”决定它是否进入普通代理候选池；停用 Key 可另行勾选“允许大脑聚合使用”。
- 输入：用户在 Key 卡片上切换启用或允许聚合开关。
- 处理：按各自开关保存；普通代理只选 `enabled`，聚合按 `enabled || allowInAggregate` 判定资格，仍受聚合本身的配置与前置检查约束。
- 输出：Key 卡片状态与分类启用数量更新；切换单个位不覆盖其他运行态字段。
- 优先级：P0
- 验收标准：
  1. 停用 Key 不参与普通代理；未允许聚合时也不参与聚合。
  2. 停用且允许聚合时，成员、汇总者或决策者可按配置使用它，但普通代理池不改变。
  3. 编辑保存后开关状态不丢失，代理模式随启用数量变化，无需另开“无感切换”开关。

#### FR-004 模型列表拉取（/models）
- 描述：每个 Key 应支持从厂商 `/models` 接口拉取可用模型列表；对不提供该接口的厂商，应支持手动录入模型名。
- 输入：Key 的 base_url + 密钥；用户点击"拉取模型"或手动添加模型名。
- 处理：调用厂商 `/models`；成功则填充模型下拉列表并缓存；失败给出明确错误（鉴权失败/网络失败/接口不存在）并允许手动录入。
- 输出：该 Key 下的可用模型列表；拉取时间戳。
- 优先级：P0
- 验收标准：
  1. 拉取成功后模型列表可用于映射与选择。
  2. 拉取失败时不阻塞流程，可手动录入模型名。
  3. 显示上次拉取时间，可重新拉取。

#### FR-005 参数设置
- 描述：每个 Key 支持 base_url、temperature、top_p、超时时间和自定义 header；模型能力中的“最大单次输出”与请求输出上限分开管理。
- 输入：用户填写参数或模型能力值。
- 处理：编辑器校验取值并保存；留空表示不配置。**各参数的作用范围不同**（见下）。
- 输出：参数保存结果；非法值即时校验提示。
- 优先级：P0
- 作用范围（**2026-08-14 / 08-15 两次定调，改动前先读这一段**）：
  - `temperature` / `top_p`：客户端未显式提供时才补 Key 配置；上游为 Responses 或请求中存在非 null `thinking` 时不补。留空不注入，客户端已有值不由这条补参逻辑覆盖。
  - `timeout_ms`：转发单次尝试的预算，包含并发排队；流式建流后另有静默超时保护，不按该预算截断正在生成的回答。
  - 旧 Key 配置的 `max_tokens`：已从当前参数结构移除，旧文件中的该未知键被忽略；客户端请求自带的输出上限仍按下面规则处理。

- **三类 token 预算必须分清**（历来最容易混的一处）：

  | 用途 | 谁决定 | 说明 |
  |---|---|---|
  | 客户端代理转发的输出上限 | **优先跟随客户端** | 显式值跨协议只改字段名，不按 Key 二次钳制；省略时不加任意固定值，但跨协议转到 Anthropic 必须补上协议要求的 `max_tokens`，按模型能力与输入预算计算 |
  | 大脑聚合的输出预算 | **按协议与模型能力自动算** | OpenAI Chat / Responses：**不发**上限字段；Anthropic：API 必填，按「该模型 `contextWindow` − 本轮输入估算 − 安全余量」现算，工具循环**每轮重算** |
  | 大脑聚合的检索输入预算 | `brain.maxContextTokens` | 限制打包进 prompt 的**文件内容**大小，与输出长度无关 |

- 为什么代理转发不注入（2026-08-14）：本代理相对 cc-switch 的增量只有路由与自动故障转移，
  替客户端决定输出长度不在其内 —— 而 KeyEditor 新建 Key 默认带 8192，一旦注入就等于给几乎
  所有请求悄悄加了上限，用户看到长回答被截断只会去查上游中转商，永远查不到是代理加的。
- 为什么大脑聚合也不设固定上限（2026-08-15）：原实现一律用
  `key.params.max_tokens.unwrap_or(4096)`，参与者/汇总者/决策者的长回答会在 4096 token 处
  被切掉，症状是「模型答一半」而无处归因。决策者 prompt 里嵌着全部成员答案，正是最需要
  按实际输入算的场合。
- **Anthropic 的协议约束（不可绕过）**：Anthropic Messages 的 `max_tokens` 是**必填**字段，
  省略直接 HTTP 400。故 Anthropic 侧不可能既「请求合法」又「请求里没有上限」，只能取
  「能力范围内尽可能大」，取值为：

  ```text
  min(contextWindow − 本轮输入估算 − 1024 余量, 该模型最大单次输出)
  ```

  **两个钳制都不能省**：只按窗口算会在 200k 窗口 / 64k 最大输出的 Claude 4.5 上发出近 200k
  的 `max_tokens` → 官方与严格中转直接 400（**上下文窗口 ≠ 最大输出**，这是审计实测出的
  provider-break）；只按最大输出算则会在长输入时让「输入 + 输出」超窗口。
- **模型能力取值**：使用 `upstream/budget.rs::resolve_max_output`，依次取用户填写的正数能力值、内置模型表、同档位 Claude 世代兜底、全局兜底。不得从上下文窗口直接推导最大单次输出。
- **数据缺失时的分级处理**：
  - 缺 `contextWindow` 时不拒绝，输出只受可取得的最大输出能力约束；这不构成对未知上游窗口的保证。
  - 最大输出无法识别时沿用代码中的 `FALLBACK_MAX_OUTPUT`（当前 8192），可在模型列表里填写能力值覆盖；早期“未知模型直接拒绝”的规则已经撤销。
  - 已知窗口且输入与安全余量耗尽窗口时，报可行动错误并不发上游请求。
- ⚠️ 「不发上限」不等于数学意义上的无限：仍受模型自身上下文窗口、服务商默认值与服务端策略约束。

- 验收标准：
  1. 非法参数值被拦截并提示。
  2. 客户端未给 temperature / top_p 且满足补参条件时才携带 Key 的对应值；Responses 上游及已有 thinking 的请求不补。
  3. 客户端未给输出上限时，不从 Key 的旧 `max_tokens` 注入固定值；跨协议转 Anthropic 的必填字段按第 10 条处理。
  4. 客户端**给了**输出上限时原值保留：同协议原名直通，跨协议按上游协议改名，且不额外冒出同义字段。
  5. 同一请求故障转移到任何候选 Key，输出上限都不随 Key 的 `max_tokens` 变化。
  6. 大脑聚合打 OpenAI 上游时，**每一轮**请求体都不含三个上限字段中的任何一个
     （`openai_aggregation_requests_carry_no_output_cap` 钉住）。
  7. 大脑聚合打 Anthropic 上游时，请求体带 `max_tokens`，其值 **≤ 该模型最大输出**、
     **不等于 4096**，且工具循环历史增长后**不得变大**
     （`anthropic_aggregation_uses_dynamic_cap_not_the_old_default` 钉住）。
  8. Anthropic Key 缺 `contextWindow` 但模型名可辨识时，仍按该模型最大输出正常参与聚合
     （`anthropic_member_without_context_window_uses_known_model_cap` 钉住）。
  9. 已知窗口被输入占满时拒绝调用；未知模型采用能力兜底且可由用户填写值覆盖
     （`anthropic_unknown_model_falls_back_instead_of_failing`、`user_supplied_max_output_overrides_builtin_table`）。
  10. **跨协议**（OpenAI 客户端 → Anthropic Key）客户端省略上限时，转换层不得凭空造 4096；
      由代理按同一套能力计算补齐（`cross_protocol_anthropic_budget_uses_model_cap_not_4096`、
      `o2a_omitted_cap_stays_omitted_for_key_aware_proxy_to_fill` 钉住）。
      客户端显式给的值优先，不被能力计算覆盖（`cross_protocol_anthropic_budget_preserves_client_cap`）。
  11. Key 上残留的旧 `max_tokens` 值对以上任何请求体都无影响。
  12. 图片 base64 是传输编码，**不得**按文本 token 计入输入估算
      （`image_base64_is_replaced_by_bounded_vision_estimate` 钉住）；
      CJK 按每字符 ≥1 token 取上界，不得低估
      （`token_estimate_handles_cjk_without_underestimating` 钉住）。

#### FR-006 模型映射
- 描述：每个 Key 必须支持"模型映射"——把厂商真实模型名映射为工具期望的模型名。例如 `GLM5.1 → opus-4-7`、`GLM5.2 → opus-4-8`。
- 输入：厂商真实模型名（来自 FR-004）+ 工具期望模型名。
- 处理：维护对外名到真实模型名的映射，普通转发时按当前 Key 解析后发往上游；聚合成员以配置中的 `KeyId::真实模型名` 固定调用。菜单显示名不改变实际路由名。
- 输出：映射表；映射生效后的转发日志。
- 优先级：P0
- 验收标准：
  1. 下游工具请求 `opus-4-7`，命中 GLM 厂商时实际发往厂商的是 `GLM5.1`。
  2. 一个期望模型名可在不同 Key 下映射到不同真实模型名。

#### FR-006a 模型映射兜底提示
- 描述：多 Key 分类中，对只有一条启用 Key 声明支持的模型提示单点风险，允许用户在其他 Key 上补映射。
- 输入：启用 Key 的模型、映射与档位声明。
- 处理：对外清单取并集；只有一个明确服务者的模型进入提示，不要求所有 Key 都覆盖所有模型，也不因缺少冗余拦截保存。
- 输出：单点模型及其唯一服务者清单。
- 优先级：P0
- 验收标准：
  1. 某模型只有一个服务者时给出提示，增加第二个明确服务者后该项消失。
  2. 普通转发优先选择能服务请求模型的 Key；未授权的点名模型替换不能静默发生。`allowNamedModelFallback` 是逐 Key 的显式兜底授权，替换仍须留痕。

### 4.2 Key 无感切换（功能1）

#### FR-007 路由模式自动判定（单 Key 直连 vs 多 Key 无感切换）
- 描述：接入始终通过本机代理；“单 Key 直连”指代理透明转发唯一上游，不是让客户端持有真实密钥绕过代理。
- 输入：分类下启用的 Key 集合。
- 处理：单 Key 使用单一上游；多 Key 按模型能力、运行态保护与优先级进行故障转移。无需另行开启切换功能，Key 数变化不更换接入机制。
- 输出：模式标识与稳定的本机端点。
- 优先级：P0
- 验收标准：
  1. 单 Key 请求经本机代理到该上游，客户端配置不含真实 Key。
  2. 增加备用 Key 后，同一入口具备故障转移能力；删回单 Key 后仍沿用该入口。

#### FR-008 本地路由代理生成与工具接入配置
- 描述：系统在本机为每个分类生成代理端点，并按目标工具的正式接入机制生成或写入配置。
- 输入：分类、启用 Key 集合、目标工具类型。
- 处理：优先复用分类的粘滞端口；启动监听后写客户端配置，写入失败撤销本次启动。CLI 写环境配置，桌面端写 gateway 档，Codex 写 provider、模型目录及必要的凭据占位。
- 输出：代理端点地址、目标工具接入配置文本、写入结果。
- 优先级：P0
- 验收标准：
  1. 目标工具按生成的配置连接后，请求经由本地代理转发到上游。
  2. 端口冲突时能自动改用可用端口并更新配置。

#### FR-009 故障转移路由（主备切换）
- 描述：在模型服务能力及运行态保护相同的候选中按用户优先级转发，失败后在剩余预算内尝试下一条；不是轮询负载均衡。
- 输入：客户端请求、启用 Key、优先级、模型解析及熔断/配额/余额/预算状态。
- 处理：候选先按模型服务能力、余额耗尽与超预算状态、用户优先级排序；熔断、模型锁和配额窗口参与过滤，全池被运行态挡住时允许兜底尝试。请求一旦建流，不在中途重新切 Key。
- 输出：响应及诊断头，或含原因的错误；故障转移与显式模型替换留痕。
- 优先级：P0
- 验收标准：
  1. 首候选在建流/成功响应前失败，仍有合格备用且预算允许时，无需用户干预即可继续尝试。
  2. 流内失败不能记为健康成功；Responses 的 `response.failed`、Anthropic error 与兼容流顶层 error 均须识别。
  3. 不可服务的已宣告模型返回 503；明确硬错误与暂时全失败分流，不把所有错误都包装为 529，也不悄悄换成未授权的模型。

#### FR-010 Key 优先级排序
- 描述：用户应能设定同一分类下启用 Key 的优先级顺序（决定谁是主、谁是备）。
- 输入：用户拖拽/上下移动 Key 顺序。
- 处理：持久化配置顺序；候选模型服务能力及其他运行态排序相同时按此顺序尝试，主 Key 徽标只表达用户配置顺序。
- 输出：更新后的顺序；即时生效。
- 优先级：P1
- 验收标准：调整顺序后，主 Key 变为排在最前的启用 Key。

#### FR-011 切换前健康检查
- 描述：保留原编号与标题；现行策略是独立健康探测与真实流量熔断分离，不在每次故障转移前强制发探测请求。
- 输入：Key 的地址、密钥、探测设置及手动/后台触发。
- 处理：探测只更新可达性、耗时与检查时间，不增加真实流量失败计数、不直接剔除候选。主口令锁定时跳过探测；后台仅处理启用 Key。
- 输出：可达性徽标与失败原因；“探测不可达”不能写成“此 Key 已停用”。
- 优先级：P0
- 验收标准：
  1. 探测失败不改变 `fail_count` 或熔断窗口，真实请求仍可尝试该 Key。
  2. 探测遵守独立超时上限，单条不可达不拖住全部 Key；锁定态不把 Key 批量标坏。

#### FR-012 熔断与恢复
- 描述：真实流量的失败按 Key 级或模型级归属记账，达到阈值后暂时限制候选；不能把后台探测失败或所有 HTTP 错误一律计作 Key 故障。
- 输入：实际请求结果、状态码、真实模型名、失败计数与冷却窗口。
- 处理：复用 `proxy::failure_scope` 分流；流内错误在流末记失败而不是被先前的 200 抹掉。一次真实成功衰减失败计数并解除相应保护；窗口到期可重新尝试。
- 输出：熔断状态、剩余时间与可见事件。
- 优先级：P1
- 验收标准：正常候选存在时跳过受限候选；全池受限时允许明确记录的兜底尝试。401、模型端点 404、429/5xx 和流内 error 的记账分别符合既有分层规则，不互相替代。

### 4.3 大脑聚合（功能2）

#### FR-013 大脑聚合开关与开启条件
- 描述：用户按分类开启或关闭桌面会诊与 MCP `synaroute_ai` 能力；该开关与普通代理转发独立。
- 输入：分类级开关及聚合配置。
- 处理：显式聚合入口检查开关；关闭时拒绝聚合调用与文件写入，不把普通请求自动改成聚合，也不把被拒的 MCP 调用暗中改走普通路由。
- 输出：聚合状态或可行动的未启用错误。
- 优先级：P1
- 验收标准：关闭后各聚合入口均被拒；普通代理照常工作。开启后只有显式桌面或 MCP 调用触发聚合。

#### FR-014 聚合成员配置
- 描述：配置固定的 Key＋真实模型成员、最终决策者及可选汇总者；普通路由的主 Key 不决定聚合的调用对象。
- 输入：成员集合、决策者引用、可选汇总者引用及并发/预算设置。
- 处理：保存时校验引用形态、重复成员和范围；不要求未完成的配置立即可运行。运行时必须有可用的决策者引用，汇总者未填则复用决策者。
- 输出：已保存的配置或明确校验错误。
- 优先级：P1
- 验收标准：
  1. 不同 Key 上的同名模型可同时配置，同 Key 同模型重复成员被拒。
  2. 未配决策者可以保留草稿，但执行时明确报错；不悄悄改用普通路由主 Key。

#### FR-015 不可用模型跳过
- 描述：聚合执行前/中，若某成员配置的模型不可用，则本次思考跳过该成员，避免长时间无返回。
- 输入：成员模型的健康/可用性状态。
- 处理：停用且未允许聚合的成员被跳过；成员熔断、配额窗口或确定耗尽时按前置检查跳过并记录。无成功成员时由配置的决策者独答并标明降级；决策者失败且已有成员意见时保留这些意见，不伪称完成综合。
- 输出：本次实际参与成员清单 + 跳过清单。
- 优先级：P1
- 验收标准：不可用成员不拖慢整体；被跳过项在日志/结果元信息中可见。

#### FR-016 并行解答 + 聚合 + 最终决策
- 描述：聚合请求流程必须为：多个成员模型并行解答 → 收集结果 → 按所选聚合方式处理 → 交最终决策者产出最终答案。
- 输入：下游工具的原始请求；成员集合；聚合方式（A/B）；决策者。
- 处理：
  1. 并行向各可用成员发起请求（含各自的映射与参数）。
  2. 汇集结果，按超时上限收敛（见 NFR-001）。
  3. 聚合：方式 A 先压缩汇总各结果（减少上下文与 token）后交决策者；方式 B 将全量结果交决策者。
  4. 决策者综合产出最终答案，作为响应返回下游工具。
- 输出：最终答案；可选的过程元信息（参与成员、聚合方式、耗时）。
- 优先级：P1
- 验收标准：
  1. 可观测到多个成员被并行调用（非串行）。
  2. 方式 A 调用汇总模型压缩意见，失败可回退全量上下文；方式 B 直接拼接成功成员意见。实际压缩长度与内容质量须验收，不能由模式名称保证。
  3. 正常完成时返回决策者答案；发生降级时明确说明原因并保留可用意见。
  4. 桌面端写文件必须先生成预览，再经用户确认执行；写入不重新调用模型，路径及备份防线在实际落盘时仍须生效。

#### FR-017 聚合方式可配（压缩汇总 / 全量上下文）
- 描述：系统必须提供两种聚合方式供用户选择：A 压缩汇总后交决策者；B 全量上下文交决策者。
- 输入：用户选择的聚合方式。
- 处理：方式 A 需对成员结果做汇总/裁剪以降低 token；方式 B 保留完整结果。
- 输出：所选方式；对应的决策者输入。
- 优先级：P1
- 验收标准：切换方式后，决策者输入构造相应变化，且可在日志中区分。

### 4.4 路由代理服务生命周期

#### FR-018 Key 加密存储
- 描述：所有密钥必须以应用内加密文件形式存储，不得明文落盘。
- 输入：待保存的密钥与敏感配置。
- 处理：Windows 默认用 DPAPI，macOS 默认用系统钥匙串持有随机密钥；二者可选主口令，Linux 必须设置主口令。主口令通过 Argon2id 派生并用 AES-GCM 加密；保存或删除失败不得改变当前生效的凭据。
- 输出：加密存储文件；应用内解密后使用，界面默认掩码显示。
- 优先级：P0
- 验收标准：
  1. 配置文件中不含明文密钥。
  2. 界面默认掩码，用户主动“显示”时才临时揭示；锁定态不把不可读误报为没有密钥。
  3. 模式以密钥库自身为准；写盘失败仍可读取旧凭据，重启后不出现未经确认的凭据切换。

#### FR-019 代理服务启动/停止/状态
- 描述：系统必须管理本地代理服务的生命周期：随需启动、可手动停止、显示运行状态与监听端口。
- 输入：用户操作或分类路由模式变化（FR-007）。
- 处理：启动时监听并写入客户端接入配置；停止时还原接入配置并停止监听。窗口关闭隐藏到托盘，真正退出时停止服务、按 FR-029 保存运行状态。监听状态不等于客户端已经发送过请求。
- 输出：服务状态（运行中/已停止/端口/错误）。
- 优先级：P0
- 验收标准：
  1. 界面显示当前代理运行状态与端口。
  2. 停止后目标工具请求不再被转发；重启后恢复。

#### FR-020 请求日志与可观测性
- 描述：系统应记录路由/聚合的关键事件：使用了哪个 Key、是否发生切换、健康检查结果、聚合参与成员与耗时、错误原因。
- 输入：请求处理过程中的事件。
- 处理：结构化记录，支持在界面查看最近事件；敏感信息（密钥）脱敏。
- 输出：可查看的事件/日志视图。
- 优先级：P1
- 验收标准：
  1. 发生一次故障转移后，日志能定位是从哪个 Key 切到哪个 Key 及原因。
  2. 日志不含明文密钥。
  3. 建流日志只说明拿到了响应头；后续流内失败追加错误事件，不能用建流的 200 证明回答成功完成。

#### FR-021 配置导入/导出
- 描述：导出配置供备份或迁移，可选是否包含密钥；包含密钥时用用户提供的导出口令重新加密，不照搬绑机器的密文。
- 输入：导出/导入文件、可选口令及 Merge/Replace 模式。
- 处理：先校验格式和完整性再解析业务配置；新导出为 v2 稳定摘要，v1 按原始字段顺序兼容校验。Merge 同 id 覆盖、新 id 新增；Replace 清理被替代项并备份。端口、日志目录、代理运行记忆等本机状态不随文件迁移。
- 优先级：P2
- 验收标准：
  1. 未篡改的历史 v1 及当前 v2 文件均可导入；新增默认字段不应让旧备份误报损坏，真实载荷篡改仍被拒。
  2. 含密钥文件需要正确口令，锁定或口令错误在修改配置前拒绝；部分密钥写入失败须明确报告，不声称全部迁移成功。
  3. Replace 删除旧密钥前备份库；配置与密钥的备份路径均须回显。v2 导出供支持 v2 的版本导入，旧应用拒绝新格式是兼容边界。

### 4.5 系统托盘与主题（cc-switch 类基础功能）

#### FR-022 系统托盘常驻与快速切换
- 描述：系统必须提供系统托盘常驻，支持从托盘菜单快速切换当前 Key/Provider、开关代理、显示/隐藏主窗口、退出。
- 输入：托盘菜单点击。
- 处理：托盘与主窗口共用启停、Key 排序入口；代理起=接入、停=还原。Codex 模型切换写默认值，按新会话生效，不承诺改动已经在运行的会话。
- 输出：托盘菜单与状态图标。
- 优先级：P0
- 验收标准：
  1. 关闭主窗口应用仍驻留托盘。
  2. 从托盘可完成主 Key/Provider 快切与代理开关。

#### FR-023 深浅主题切换
- 描述：系统必须支持深色/浅色主题，且可跟随系统。
- 输入：用户选择主题或系统主题变化。
- 处理：切换主题并持久化偏好。
- 优先级：P0
- 验收标准：切换后 UI 立即变化，重启后保持。

#### FR-024 卡片式 Provider 管理界面
- 描述：Provider/Key 列表必须以卡片式呈现，风格对齐 cc-switch 与 echobird，展示名称、启用状态、健康状态、映射模型摘要等，并提供快捷操作。
- 输入：配置数据。
- 处理：渲染卡片列表，支持编辑/启用/删除/排序入口。
- 优先级：P0
- 验收标准：界面观感与交互对齐 cc-switch 卡片式列表。

#### FR-025 开机自启动（可选）
- 描述：系统应支持配置开机自启动并最小化到托盘。
- 输入：用户开关。
- 处理：写入/移除系统自启动项。
- 优先级：P2
- 验收标准：开启后重启系统应用自动驻留托盘。

#### FR-026 聚合参与者按需检索（只读工具调用）
- 描述：大脑聚合的参与者应可在回答过程中主动调用一组**只读**工具按需取上下文，而不是仅依赖
  FR-016 之前一次性注入的前置检索结果（前置检索靠 prompt 关键词猜哪些文件相关，猜错即白填
  token、猜漏则模型盲答）。
- 输入：分类级开关 `toolsEnabled`（默认**关**）、轮数上限 `maxToolRounds`（默认 6，运行时夹在 2~12）。
- 处理：
  1. 工具集固定四个：`read_file`（可带行区间）、`grep`（正则，ripgrep 不可用时降级为字面量匹配
     并在结果里明示）、`list_dir`、`codegraph_query`（未安装或项目未建索引时**不声明**该工具）。
  2. 每轮把模型请求的工具调用在本地执行，结果按各协议形状回填（Anthropic `tool_result` 打包进
     一条 user 消息；OpenAI 每条一个 `role:"tool"` 消息），进入下一轮。
  3. 到轮数上限或探索预算（整轮成员预算的 70%）用尽时，追加一条「不要再调用工具、直接出结论」
     的指示再发一轮；该轮仍须声明 tools（Anthropic 规定历史中出现 tool_use/tool_result 时必须带 tools）。
  4. 单次工具结果默认最多 8000 字符，可在配置中调整，运行时限制在 1000～40000 字符；截断后仍保留不可信数据围栏。
- 安全约束（**恒定生效、无开关**）：
  - 成员工具只读，不提供写文件与执行命令。MCP 返回方案供客户端处理；桌面端另有预览后确认写入入口，不属于成员工具权限。
  - 路径三道防线：① 拒 `..`/绝对路径/盘符/UNC；② canonicalize 后必须仍在工作目录内（堵符号链接
    与 junction 逃逸）；③ 凭据类文件（`.env`/密钥/证书/密码库）一律拒读，且按「模型给的名字」与
    「解析链接后的真实落点」各判一次。
  - `grep` 命中结果逐条过敏感文件过滤后才回给模型（ripgrep 搜所有文件，`.env` 命中会直接出现在
    stdout 里；工具结果会进上游请求体，等于外发）。
- 优先级：P2
- 验收标准：
  1. 开关关闭时行为与开启前完全一致（单轮、请求体不含 tools 字段）。
  2. 开启后提出「需要读多个文件才能回答」的问题，运行日志出现 `read_file`/`grep` 调用记录，
     且答案引用了具体文件内容。
  3. 让模型去读 `.env` → 被拒且日志留痕；模型据拒绝原因改读其他文件、成员不失败。
  4. 模型持续要求调用工具时，在轮数上限处停止并给出结论，不无限循环。

#### FR-027 聚合图片输入（多模态）
- 描述：客户端调用 `synaroute_ai` 时应可附带图片，使「这个报错截图是什么问题」这类任务可用。
- 输入：MCP 工具参数 `images`（字符串数组，**相对 `cwd` 的路径**）。桌面端 UI 不提供上传入口。
- 处理：按扩展名判定 `media_type`，base64 编码后按各协议形状拼进 user content
  （Anthropic `{type:"image",source:{type:"base64",…}}`；OpenAI `{type:"image_url", url:"data:…"}`），
  图片块置于文本块之前。
- 约束与失败口径：
  - 最多 4 张、单张 ≤ 5MB、仅 `png/jpg/jpeg/gif/webp`（两家协议的交集）；路径同样过 FR-026 的三道防线。
  - 任何一项不满足即**整次调用报错**并说明原因，**不静默丢弃**——静默丢会让用户拿到一个看起来
    正常、实则没看图的答案。
  - 传了 `images` 但未提供工作目录时报错要求同时传 `cwd`。
  - 成员模型不支持图片时上游回 4xx，失败原因里显式附「该模型可能不支持图片输入」的提示
    （判据：本次带了图 且 错误含 `HTTP 4xx`）。
- 优先级：P2
- 验收标准：传一张截图提问，答案应描述图片内容；传 6MB 图应报「超过单张 5MB 上限」；
  传 5 张应报张数超限；传 `.bmp` 应报格式不支持。

#### FR-028 用量统计 / 健康告警 / 请求路径可视化
- 描述：显示代理使用的线路、捕获到的 token 用量、估算费用和真实流量健康告警。
- 输入：上游回报的 usage、实际 Key/模型、公开价格与用户倍率，以及路由/健康事件。
- 处理：
  - 用量独立于事件环累计，普通代理按“分类 × Key × 真实模型”记账；模型未知的历史或聚合行仍使用代表模型估价并标为近似，不伪造模型身份。
  - 收到一笔 usage 时按本机日期归桶；查询与延后落盘不改变该日期。流式通常在流末捕获用量，不按请求起始时间归桶，也不凭空拆分跨午夜生成的 token。
  - `usage.json` 保持 v4；每 60 秒有变更才保存，退出补落。提交成功只消费该次快照，期间新记录保留；失败按原日期重试。历史 UTC 桶无逐笔时刻，不重切。
  - 日视图包含尚未落盘的增量；本周按周一、本月按 1 号起算。90 天前日桶折入累计，不使累计值下降。
  - 没有收到 usage 的新 Key 显示“尚无用量”，不是已发生但免费的 `$0`；缺少价格时说明未计价原因，部分未计价不冒充总额。
  - 删除 Key 经确认后清理其用量；离开配置但未走删除动作的历史行按现有墓碑规则显示并可清理。落盘失败不得把删除当成已持久化。
  - 路由事件记录实际 Key/模型与尝试；建流和最终流内失败分开记录。真实熔断与恢复发通知，免打扰等系统设置可能影响通知呈现。
- 输出：累计及日/周/月用量、逐模型费用明细、估价来源与错误/健康事件。
- 约束：金额是公开单价乘用户倍率的估算，不保证等于中转账单；上游未回报的用量不补猜。崩溃可能丢失最后未刷盘的增量，未来格式或读取失败时保护原文件、不以空账本覆盖。
- 优先级：P1
- 验收标准：
  1. 请求数超过事件环容量仍累计，重启保留已落盘总量；同 Key 不同模型分别估价。
  2. 午夜、周/月/年边界及连续落盘失败后的重试，已接收用量保留原入账日期；查看、重复 flush、并发提交不丢失或重复计数。
  3. 删除后重启不复活；落盘失败的删除须在后续可写时重试。Key 真正熔断时事件可见，不能以一次建流成功掩盖流末失败。

#### FR-029 代理启用状态的记忆与自动恢复
- 描述：上次退出前处于启用状态的代理分类，下次启动应用（含开机自启动）应自动恢复启用，
  用户不必每次手点「启动」。绝大多数人的用法是「一直开着」，每次手点是纯粹的重复劳动。
  MCP 早已具备同等能力（`mcp_enabled` + 启动时的门），本条把代理补齐到同一水平。
- 输入：无用户输入。状态由系统自行记录。
- 处理：
  - **记录**：周期性（60s，搭用量落盘那条后台线程）+ **退出时**各采样一次
    「当前哪些分类的代理在跑」，写入 `settings.proxyRunningCategories`。
    采样的是 `ProxyManager` 的**真实运行态**，不是用户点击意图 —— 启停的意图点有四处以上
    （命令 / 接入 / 托盘 / 首启向导 / 改端口），逐点埋标记漏一处就是静默失效。
  - **恢复**：启动时逐个走与界面按钮、托盘**完全相同**的入口
    （`service::apply_tool_config` = 监听端口 + 写客户端工具配置）。
    绝不能只 `proxy.start()`：那样客户端读到的仍是官方端点，会出现
    「界面显示已启动、客户端根本没走代理」。
- 约束与失败口径：
  - 幂等落盘：与上次快照相同（顺序无关）则**一个字节都不写**。空闲的应用零磁盘写入
    —— 否则等于「开着不用也每分钟重写一次含全部 Key 的 config.json」。
  - 逐个独立：一个分类恢复失败（端口被占、配置文件被占用）**不得阻断**其余分类。
  - 失败必须可见：记 error 事件 + 发系统通知。此处静默失效最坏 ——
    用户以为在跑、实际没跑，客户端报错却找不到原因。
  - 全新安装无任何记忆，不得凭空自启动代理。
  - **已知窗口**：崩溃且距上次状态变更 < 60s 时，这次变更会丢。代理是可重建的运行态
    （再点一次即可），故接受；不像用量是纯累加历史值。
- 不做：不提供「是否恢复上次状态」开关 —— 用户要的就是别每次手点，加开关等于把要解决的
  问题又还给用户。想下次不自启，退出前点一次「停止」即可（语义自解释）。
- 优先级：P1
- 验收标准：启动某分类代理 → 退出应用 → 重新打开，该分类应自动在跑，且客户端配置里的
  端口与实际监听端口一致；退出前先「停止」再退出，则下次不应自启动；
  全新安装首次启动不应有任何代理自动启动；恢复失败时应有系统通知与日志，界面不得显示为已启动。

## 5. 非功能需求

> 编号规则：NFR-xxx。注：以下数值为建议目标值，标注 [待确认] 者需产品与用户对齐（见第 7 节）。

### 5.1 性能

#### NFR-001 聚合响应时间收敛
- 需求：大脑聚合设整轮预算，默认 60 秒，保存范围 10 秒～30 分钟；阶段共享剩余预算并给决策者留时间。成员超时按失败收敛，保留已到意见；预算存在不等于所有真实上游下都已验收响应时限。
- 优先级：P0
- 验收：模拟某成员超时，整体仍在上限内返回最终答案。

#### NFR-002 健康检查耗时
- 需求：单次元数据探测使用 Key 超时且封顶 8 秒；后台有界并发，不把每次业务故障转移与一次同步探测绑定。
- 优先级：P0
- 验收：不可达端点在超时内结束，其他探测仍能进行；探测失败不改变业务熔断计数或直接剔除该 Key。

#### NFR-003 故障转移切换延迟
- 需求：主 Key 判定失败到切至下一个 Key 的额外开销应尽量低（建议除上游本身耗时外新增 < 200ms 决策开销）；对下游工具应表现为一次正常（稍慢）请求。
- 优先级：P0
- 验收：日志显示切换决策开销在目标范围内。

#### NFR-004 代理转发开销
- 需求：单 Key/普通转发场景下，代理引入的额外延迟应尽量小（建议 < 50ms，不含上游耗时）。
- 优先级：P1

#### NFR-005 资源占用
- 需求：常驻托盘 + 代理的空闲内存与 CPU 占用应保持在桌面软件合理范围（建议空闲内存 [待确认] ，空闲 CPU 近 0）。
- 优先级：P1

### 5.2 安全

#### NFR-006 密钥加密与脱敏
- 需求：密钥必须加密存储（FR-018），界面默认掩码，日志脱敏，剪贴板复制敏感信息应有提示。
- 优先级：P0
- 验收：密钥库不存明文，普通日志与诊断不泄露 API Key；界面默认掩码，只有用户主动显示或复制时才揭示，主口令锁定时拒绝读取。

#### NFR-007 本地监听最小暴露
- 需求：路由代理默认仅监听本机回环地址（127.0.0.1），不对外网暴露；如需局域网访问必须显式开启并告警。
- 优先级：P0
- 验收：默认端口仅本机可访问。

#### NFR-008 传输安全
- 需求：与上游厂商通信必须使用 HTTPS/TLS，校验证书。
- 优先级：P0

### 5.3 可靠性

#### NFR-009 故障转移正确性
- 需求：建流/响应前失败时，在剩余预算内尝试可服务且符合用户授权的候选；无合格候选、预算不足或全失败时说明原因。已经开始输出的流不承诺中途无缝换 Key。
- 优先级：P0

#### NFR-010 熔断保护
- 需求：连续失败的 Key 应被熔断，避免反复重试拖慢整体（FR-012）。
- 优先级：P1

#### NFR-011 崩溃恢复与配置一致性
- 需求：应用异常退出后重启，配置不丢失、不损坏；写配置应具备原子性/备份，防止半写损坏。
- 优先级：P0

### 5.4 可用性

#### NFR-012 上手成本
- 需求：新用户应能在 [待确认，建议 5 分钟] 内完成"新增一个 Key 并让目标工具连通"。
- 优先级：P1

#### NFR-013 错误可读性
- 需求：所有失败（鉴权失败、网络、超时、模型不存在、端口冲突等）必须给出可读的中文错误与建议动作。
- 优先级：P0

### 5.5 兼容性

#### NFR-014 操作系统
- 需求：支持 Windows 10 / 11（64 位）、macOS 和 Linux；安装、密钥保护及目标客户端兼容性按平台分别验收，不能用一个平台的单测结果代替其他平台。
- 优先级：P0

#### NFR-015 目标工具接入兼容
- 需求：使用三端各自支持的接入方式，生成配置、备份和还原；桌面端使用 gateway 部署配置，不写无效的 base_url 字段。配置完好与真实客户端连通分开验证。
- 优先级：P0

#### NFR-016 上游协议兼容
- 需求：支持 Anthropic Messages、OpenAI Chat Completions 和 Responses 的请求、响应、SSE 与工具调用适配。支持范围以转换器和协议回归为准；私有扩展及客户端升级需单独验证，不能承诺任意字段无损转换。
- 优先级：P1

## 6. 关键用例

> 编号规则：UC-xxx。用步骤流程描述。

### UC-001 单 Key 直连
- 参与者：用户、目标工具、SynaRoute。
- 前置：某分类下仅 1 个 Key 启用。
- 主流程：
  1. 用户新增并启用一条 Key，点击启动接入。
  2. 代理监听本机端口，写入该工具的接入配置。
  3. 客户端请求到达代理，再转发唯一上游；模式显示为单 Key 直连。
- 后置：真实密钥只由代理持有，不因候选只有一条而写进客户端配置。

### UC-002 多 Key 无感切换（含模型映射，示例场景）
- 参与者：用户、Claude CLI、SynaRoute、厂商1/2/3。
- 前置：Claude CLI 分类下配置三家厂商：
  - 厂商1：opus-4-6 / opus-4-7 / opus-4-8
  - 厂商2：opus-4-6 / opus-4-7 / opus-4-8 / fable-5
  - 厂商3：GLM5.1（映射 opus-4-7）/ GLM5.2（映射 opus-4-8）
- 主流程：
  1. 用户为三家厂商各配置 Key，拉取模型（FR-004），为厂商3配置模型映射 GLM5.1→opus-4-7、GLM5.2→opus-4-8（FR-006）。
  2. 用户最终选定要使用的期望模型：opus-4-7、opus-4-8。
  3. 系统对只有一个明确服务者的模型提示单点风险（FR-006a）；补映射可增加冗余，不要求每条 Key 都支持全部模型。
  4. 用户启用多个 Key，系统判定为多 Key 无感切换（FR-007），生成本地路由代理端点并给出 Claude CLI 接入配置（FR-008），用户一键写入/复制到 Claude CLI。
  5. 设置 Key 优先级：厂商1为主（FR-010）。
  6. Claude CLI 发起对 opus-4-7 的请求，经代理：
     - 主 Key（厂商1）：直接以 opus-4-7 请求。
     - 若厂商1在建流前失败/超时，在预算允许时继续尝试合格候选。模型能力及其他运行态相同时按厂商2、厂商3顺序；厂商3映射为 GLM5.1。候选过滤使用真实流量保护，不另发同步探测。
  7. 首个成功候选返回响应；建流后的流内失败不重放到其他 Key，追加错误事件并记失败。
- 异常流程：
  - 全部 Key 不可用：返回明确错误（NFR-009）。
  - 某 Key 不能按请求模型服务：按模型保护规则跳过或报错；只有该 Key 明确允许点名模型兜底时才可替换，并记录替换。缺少映射本身不等于不可服务，同名模型或透传也可能有效。
- 后置：日志记录使用的 Key、切换过程与原因（FR-020）。

### UC-003 切换前健康检查
- 本用例保留原编号；现行行为为探测与路由保护分离。
- 主流程：
  1. 手动或后台触发某 Key 的健康探测。
  2. 探测在独立超时内结束，更新可达性、检查时间与耗时。
  3. 即使探测失败，后续普通请求仍按模型能力和真实流量保护选择候选。
  4. 真正的业务失败按 FR-012 记账，探测失败不冒充业务失败。
- 后置：界面显示准确的探测状态，原有失败计数与熔断窗口不被本次探测改写。

### UC-004 大脑聚合（多模型协作）
- 参与者：用户、目标工具、SynaRoute、成员模型若干、决策者。
- 前置：开启本分类大脑聚合，配置成员、最终决策者与聚合方式；不依赖普通路由主 Key。
- 主流程：
  1. 用户在桌面端发起会诊，或客户端显式调用 MCP `synaroute_ai`；普通对话转发不自动触发。
  2. SynaRoute 按配置和前置检查确定本轮参与者，跳过项给出原因。
  3. 固定 Key＋模型的成员调用有界并发，并在阶段预算内收敛。
  4. 方式 A 调用指定汇总者（未指定时复用决策者），方式 B 拼接成功成员意见。
  5. 决策者综合意见，返回答案及可用的过程信息。
- 异常流程：
  - 无成功成员：决策者独答并明确说明，不冒充多模型共识。
  - 压缩失败：保留成员意见，降级为全量上下文。
  - 决策者失败且已有意见：返回这些意见和失败说明；没有可用产物时明确报错。
- 后置：记录参与、跳过、降级与已捕获用量；桌面文件修改仍须另经预览与确认。

### UC-005 系统托盘快速切换
- 主流程：
  1. 用户关闭主窗口，应用驻留托盘（FR-022）。
  2. 用户右键托盘菜单，切换当前主 Key/Provider 或开关代理。
  3. 配置顺序与代理状态按操作结果更新；Codex 默认模型切换在新会话生效，不改变已运行会话的模型。

### UC-006 首次配置目标工具连通
- 主流程：
  1. 用户新增 Key（FR-002），拉取模型（FR-004），设置参数（FR-005）。
  2. 启用 Key 后点击“启动”，系统监听本机端口并写入该工具的接入配置（FR-008）。
  3. 按接入结果提示启动或重启客户端，使其读取配置。
  4. 目标工具发起请求验证连通；界面显示代理状态与最近事件（FR-019、FR-020）。
- 后置：目标工具通过 SynaRoute 正常工作（NFR-012 建议 5 分钟内完成）。

## 7. 原始问题与现行决策（Open Questions 对账）

> 保留原 OQ 编号用于追溯；下表不把已经实现的决策继续列成“待确认”。实现存在与真实客户端验收是不同状态，后者统一见 docs/14 §21.2。

| 编号 | 原始问题 | 现行决策与边界 |
|---|---|---|
| OQ-1 | Claude 桌面端如何接入？ | 使用 gateway 部署配置档；模型 ID 合规检查与显示名分别处理，不采用早期无效的 base_url 写法。 |
| OQ-2 | 协议转换做到什么范围？ | 三协议请求/响应、六方向 SSE 与工具调用已有实现；私有字段及客户端版本差异仍需实际验证，不承诺完全无损。 |
| OQ-3 | 压缩汇总由谁执行？ | 调用配置的汇总模型，未配置则复用决策者，产生额外用量；失败保留成员意见并回退全量拼接。 |
| OQ-4 | 聚合成员与并发上限？ | 保存最多 16 位成员，默认并发 3，运行时并发夹到 1～32；同分类同容量的并发闸在各聚合入口间共享。 |
| OQ-5 | 健康探测频率与路由关系？ | 默认 60 秒后台探测，可关闭或手动触发；探测只观测可达性，不直接改变真实流量熔断，业务转发不强制先探测。 |
| OQ-6 | 是否做用量及金额？ | 已有独立账本、逐模型估价与周期统计；公开价格乘倍率是估算，不替代上游结算账单。见 FR-028。 |
| OQ-7 | 加密密钥由谁持有？ | Windows DPAPI、macOS 系统钥匙串、可选主口令；Linux 强制主口令。跨机器迁移使用口令加密导出，见 FR-018/021。 |
| OQ-8 | 聚合失败如何降级？ | 无成功成员时决策者独答；压缩失败回退全量；决策者失败保留已有意见。没有可用产物时报错，不暗中走普通路由。 |
| OQ-9 | 哪些失败触发保护？ | 按 `proxy::failure_scope` 区分 Key/模型/暂时错误；流末另判 SSE error，不能把响应头 200 当成最终成功。见 FR-009/012。 |
| OQ-10 | 聚合按什么条件开启？ | 分类级开关＋显式桌面/MCP 调用，不拦截普通代理请求做聚合。 |
| OQ-11 | 是否维护对外模型字典？ | 分类清单来自启用 Key 的模型、映射与档位并集；单点提示不要求全池交集。 |
| OQ-12 | 单 Key 是否仍走代理？ | 始终走代理，客户端端点稳定、真实密钥不写入客户端配置。 |
| OQ-13 | 聚合多模态及工具调用？ | MCP 支持受限图片输入，成员可选只读检索工具；桌面写文件单独预览确认。见 FR-026/027。 |
| OQ-14 | 请求级路由覆盖？ | 按请求模型的服务能力与显式映射/档位选择候选；未增加独立“每请求指定厂商”规则引擎，不将其记成已实现功能。 |

## 8. 验收标准汇总

> 下表是核心行为的验收摘要，不是完成状态。原生客户端、跨平台、安装包及发布检查的实际结果统一记在 docs/14 §21.2；不能只凭本表或测试总数认定可发布。

| 验收项 | 关联需求 | 通过标准 |
|---|---|---|
| A1 三分类配置隔离 | FR-001 | 三分类可见可切，配置互不串扰 |
| A2 Key 增删改查 + 加密 | FR-002、FR-018、NFR-006 | 增删改查可用，密钥库加密、日志脱敏、界面默认掩码；显式揭示与锁定行为符合 FR-018 |
| A3 启用开关联动路由模式 | FR-003、FR-007 | 单 Key 与多 Key 均走本机代理；停用与允许聚合分别生效，改变数量不切换接入机制 |
| A4 模型拉取与手动录入 | FR-004 | 拉取成功可用；失败可手动录入不阻塞 |
| A5 参数生效 | FR-005 | 仅在条件允许时补采样参数，Responses 与 thinking 请求不补；显式输出上限保留，跨协议 Anthropic 必填值按能力计算 |
| A6 模型映射生效 + 兜底 | FR-006、FR-006a | 映射与显示名分离，单点提示符合真实声明；未经授权不静默替换点名模型 |
| A7 代理生成与工具接入 | FR-008、FR-019、NFR-015 | 启动监听并写配置、停止还原；真实客户端请求到达代理，不能仅以配置匹配代替连通验证 |
| A8 故障转移正确性 | FR-009、NFR-009 | 建流前在预算内尝试合格候选，全失败明确报错；流内失败不记健康成功、不跨 Key 重放已开始的输出 |
| A9 切换前健康检查 | FR-011、NFR-002 | 独立探测有超时，探测状态与真实流量熔断分离，不把探测失败当作候选剔除依据 |
| A10 本地最小暴露 + TLS | NFR-007、NFR-008 | 默认仅本机可访问，局域网需显式开启与令牌；公网传输满足 TLS 要求，不能以客户端支持 HTTPS 代替端点实际使用 TLS |
| A11 托盘常驻与快切 | FR-022 | 关窗驻留托盘，启停与主窗口同语义；Codex 默认模型切换明确为新会话生效 |
| A12 深浅主题 | FR-023 | 主题切换即时生效并持久化 |
| A13 卡片式界面风格 | FR-024 | 卡片信息与操作可用，遵循既有设计及可访问性要求 |
| A14 崩溃恢复与配置一致性 | NFR-011 | 成功与失败回执符合磁盘状态，写前备份可恢复；断电、原地写回退及平台差异须原生验收 |
| A15 错误可读性 | NFR-013 | 各类失败给出可读中文错误与建议，不把未知原因写成确定结论 |
| A16 大脑聚合基础流程 | FR-013–FR-017、NFR-001 | 显式聚合入口执行并发分析与综合，降级如实呈现；普通代理不受聚合开关影响，文件写入须预览后确认 |
| A17 用量与估价一致性 | FR-028 | 入账日期固定，跨日写盘和失败重试不迁移消费；多模型估价、空用量与缺价区分，提交/删除/重启不重复计数 |

> 这些是验收要求，不是“已全部通过”的声明。功能回归、平台实测、安装包检查和正式发布分别记录，历史编号不重新分配。
