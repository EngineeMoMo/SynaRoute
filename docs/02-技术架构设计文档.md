## 2. 架构目标与设计原则

### 2.1 架构目标

1. **稳定路由**：本地代理对下游工具透明，主备 Key 故障转移在毫秒级决策开销内完成（NFR-003）。
2. **协议兼容**：屏蔽上游厂商协议差异（Anthropic Messages / OpenAI Chat Completions），支持故障转移与聚合场景下的跨协议适配（NFR-016）。
3. **安全存储**：密钥全链路加密，磁盘/界面/日志无明文（NFR-006）。
4. **接入无侵入**：通过改写目标工具配置文件的方式接入，不做系统级网络劫持（对齐 cc-switch 做法）。
5. **可观测**：路由/切换/聚合全过程结构化记录，界面可查（FR-020）。

### 2.2 设计原则

| 原则 | 说明 |
|---|---|
| 前后端职责分离 | 前端（React）只做配置管理与状态展示；后端（Rust）承载代理、路由、加密、协议转换等全部核心逻辑 |
| 代理与 UI 解耦 | 本地代理是独立的常驻服务模块，UI 关闭/退出到托盘时代理仍可运行 |
| 配置驱动 | 路由行为、聚合行为完全由持久化配置决定，改配置即改行为，无需重启代理 |
| 协议内部归一 | 上游协议差异在"上游适配层"消化，路由引擎只处理统一的内部请求模型 |
| 失败快速收敛 | 健康检查、聚合、故障转移均有明确超时上限，绝不无限等待 |

### 3.2 进程与线程模型

- **单进程**：Tauri 应用主进程内，Rust 侧用 Tokio 异步运行时承载代理服务与所有后台任务（健康检查定时器、熔断恢复、日志落盘）。
- **代理生命周期独立于窗口**：主窗口关闭 → 隐藏到托盘，代理服务与 Tokio 运行时不退出；仅"退出"菜单才真正终止进程并优雅关闭监听。
- **前后端通信**：前端通过 Tauri `invoke` 调用 Rust 命令（配置增删改、启停代理、拉取模型、健康检查等）；Rust 通过 Tauri `emit` 事件向前端推送实时状态（代理状态、健康变化、日志流）。

## 4. 下游工具接入机制（对齐 cc-switch）

> 这是整个项目落地的技术基石。核心结论：**通过改写目标工具的配置文件，把其 API 端点指向 SynaRoute 本地代理**，不做系统级网络劫持。这与 cc-switch 的做法一致。

### 4.1 cc-switch 的接入范式（调研结论）

cc-switch 的核心不是"劫持网络"，而是"**在切换时把选中 provider 的配置写入目标工具的实时配置文件**"，并对支持的工具做免重启热切换（其文档明确 Claude Code 支持 provider 数据的热切换）。数据本身存于其 SQLite 库，切换动作即"原子写入目标工具配置 + 通知/触发生效"。

SynaRoute 沿用同一范式，但把"切换到某个固定 provider"升级为"把端点指向本地代理，由代理动态路由"，从而实现无感切换与聚合。

### 4.2 三类工具的接入方式

| 目标工具 | 接入方式 | 关键配置项 | 生效方式 |
|---|---|---|---|
| **Claude CLI** | 写入其配置/环境变量，令 `ANTHROPIC_BASE_URL` 指向本地代理，`ANTHROPIC_API_KEY` 用占位或代理令牌 | `ANTHROPIC_BASE_URL`、`ANTHROPIC_API_KEY`（或对应 settings 文件字段） | Claude Code 支持热切换，无需重启；CLI 会话下次请求即走代理 |
| **Claude 桌面端** | 改写其配置文件中的端点字段（cc-switch 已实现该工具接入，说明存在可写的端点配置） | 端点字段（以实测为准，见 4.3 验证项） | 可能需重启桌面端进程；提供"一键写入 + 重启提示" |
| **Codex 桌面端** | 改写其 config（OpenAI 兼容），令 base_url 指向本地代理对应端点 | base_url / api_base、api_key | 视工具而定，可能需重启；提供重启提示 |

### 4.3 落地前必须做的实测验证项（开发阶段第一件事）

| 编号 | 验证项 | 目的 | 若失败的降级方案 |
|---|---|---|---|
| V-1 | Claude CLI 的 `ANTHROPIC_BASE_URL` 写入位置与热切换行为 | 确认无需重启即可改端点 | 提示用户重启 CLI 会话 |
| V-2 | Claude 桌面端配置文件路径与可写端点字段（参照 cc-switch 对该工具的实现） | 确认端点可改写 | 若无可写端点：该分类降级为"仅配置管理，路由需手动/或引导用户用 CLI" |
| V-3 | Codex 桌面端 config 文件路径与 base_url 字段 | 确认端点可改写 | 提示重启；或提供手动配置指引 |
| V-4 | 各工具改写后是否需重启、是否有缓存 | 决定"生效提示"文案与自动化程度 | 统一给出重启引导 |

> 说明：cc-switch 支持包括 Claude 桌面端在内的 7 个工具接入，是"端点/配置可改写"的强证据。但各工具版本可能变动配置格式，故 V-1~V-4 列为开发阶段最先执行的技术验证，验证脚本与结论回填到本文档。

### 4.4 接入配置的写入安全

- 写入目标工具配置前**自动备份原文件**（`*.synaroute.bak`），支持一键还原。
- 采用**原子写**（写临时文件 → fsync → 重命名替换），避免半写损坏目标工具配置。
- 记录 SynaRoute 对每个工具做过哪些改动，卸载/停用时可回滚。

## 5. 本地代理与协议转换

### 5.1 端点编排

- 代理默认仅监听 `127.0.0.1`（NFR-007），端口自动分配、冲突自动改用可用端口并回写工具配置（FR-008）。
- **按分类区分路由**：三个分类各自对应一套 Key 集合与路由规则。区分方式二选一（开发阶段定，默认方案 A）：
  - **方案 A（推荐）**：三分类各监听独立端口，端点稳定、隔离清晰。
  - 方案 B：单端口 + 路径前缀（`/claude-cli/...` `/claude-desktop/...` `/codex/...`）。
- 单 Key 场景也经代理（透明转发），使工具侧端点稳定，Key 增减无需改工具配置（对应 OQ-12 推荐结论）。

### 5.2 内部统一请求模型（UReq / URes）

代理内部定义与厂商无关的统一模型，路由引擎只处理它：

```
UReq {
  category,            // 分类
  requested_model,     // 下游请求的"期望模型名"
  messages[],          // 归一化消息（role/content 块）
  params { temperature, max_tokens, top_p, ... },
  stream: bool,
  tools[]?,            // 工具调用（tool use）— MVP 见下方范围
  raw_protocol,        // 下游用的协议（anthropic / openai）
}
URes { content_blocks[], usage, finish_reason, ... }
```

### 5.3 协议转换矩阵

| 下游协议 | 上游协议 | 是否需转换 | MVP 支持范围 |
|---|---|---|---|
| Anthropic | Anthropic | 否（直通，仅改模型名/端点） | ✅ 完整（含流式 SSE、tool_use） |
| OpenAI | OpenAI | 否（直通） | ✅ 完整 |
| Anthropic | OpenAI | 是（Messages ↔ Chat Completions） | ✅ 文本 + 流式；tool_use 转换尽力支持 |
| OpenAI | Anthropic | 是（反向） | ✅ 文本 + 流式；tool_use 转换尽力支持 |

**转换要点**：
- 消息结构：Anthropic 的 `system` 独立字段 ↔ OpenAI 的 system message；content 块 ↔ 文本/多部分。
- 流式：两边都是 SSE，但事件结构不同（Anthropic `message_start/content_block_delta/...` ↔ OpenAI `chat.completion.chunk`），需做增量事件的双向翻译并保持背压。
- **多模态与工具调用**：MVP 聚合场景仅保证纯文本合并（对应 OQ-13）；直通路由场景下工具调用透传。跨协议的 tool_use 转换标注为"尽力支持"，复杂用例延后。

### 5.4 模型映射生效点

模型映射在**上游适配层**生效：路由选中某 Key 后，将 `requested_model`（期望名）经该 Key 的映射表翻译为该厂商真实模型名，再组装上游请求。映射缺口在配置阶段已被兜底拦截（FR-006a）。

## 6. 路由引擎设计

### 6.1 模式判定（FR-007）

```
读取当前分类启用 Key 集合 →
  启用数 == 0：返回配置错误（无可用 Key）
  启用数 == 1 且未开启聚合：单 Key 透明转发
  启用数 >= 2 且未开启聚合：故障转移模式
  聚合开关开启（且成员/决策者合法）：大脑聚合模式
```

### 6.2 故障转移调度（FR-009 / FR-010 / FR-012）

```
候选列表 = 启用Key 按优先级排序，过滤掉[熔断中]和[健康=不可用]
for key in 候选列表:
    if 需要实时探测 且 key健康未知: 健康检查(超时 NFR-002)
    尝试请求(key, 应用映射+参数)
    if 成功: 记录事件, 返回响应   ← 对下游透明
    else:
        判定失败类型(见 6.4)
        累计失败计数 → 达阈值则熔断(FR-012)
        continue 下一个
全部失败 → 返回聚合错误信息(NFR-009, 含各 Key 失败原因)
```

- **决策开销目标**：除上游本身耗时外，切换决策新增 < 200ms（NFR-003）。
- **流式已开始后失败的处理**：若上游在已向下游输出部分 SSE 后中断，MVP 默认**不重放到其他 Key**（避免重复内容），向下游透传错误结束；"首字节前失败"才触发无缝切换（对应 OQ-9，作为默认策略，评审确认）。

### 6.3 健康检查（FR-011 / NFR-002）

- **混合策略**（对应 OQ-5 推荐结论）：后台定时探测（默认间隔 30–60s，可配）+ 缓存健康状态 + 切换前用缓存判定；缓存过期或状态未知时才实时探测。
- **探测方式**：优先轻量 `/models` 或最小 chat 探测；单次超时上限 3–5s（NFR-002），超时即判不可用并跳过。
- 健康状态变化通过 Tauri 事件实时推送前端，卡片徽标即时更新。

### 6.4 失败判定表（FR-009，对应 OQ-9）

| 情况 | 判定 | 默认处理 |
|---|---|---|
| 网络错误 / 连接超时 / DNS 失败 | 失败 | 立即切换下一个 Key |
| 5xx | 失败 | 立即切换 |
| 401 / 403（鉴权失败） | 失败 | 立即切换 + 标记该 Key 不健康 |
| 404（模型/端点不存在） | 失败 | 立即切换 + 提示可能缺映射 |
| 429（限流） | 失败 | 默认**立即切换**（不原地等待），并对该 Key 施加短冷却；"是否原地退避重试"作为可配项（默认关，评审确认） |
| 请求超时（无响应超过阈值） | 失败 | 切换 |
| 2xx | 成功 | 返回 |

> 该表为 MVP 默认策略，作为评审确认项之一。

## 7. 大脑聚合架构（FR-013 ~ FR-017）

### 7.1 编排流程

```
聚合请求进入 →
  1. 成员可用性预检（跳过不可用成员 FR-015；可用成员=0 → 回退普通路由 OQ-8）
  2. fan-out：对每个可用成员并行发起解答（各自映射+参数），并发上限默认 3–5（OQ-4）
  3. 收敛：等待全部返回或触及总超时（默认 60s，NFR-001）；超时未返回者按跳过处理，用已到结果继续
  4. 汇总（按聚合方式）：
       方式A 压缩汇总：调用【专门的汇总模型】把各成员答案压缩成结构化摘要（降低交给决策者的 token）
       方式B 全量上下文：将各成员完整答案拼装
  5. 决策：把汇总/全量结果交【最终决策者模型】，产出最终答案
  6. 返回下游 + 记录过程元信息（参与/跳过成员、方式、耗时）
```

### 7.2 关键决策落地（已确认）

- **聚合方式 A 的压缩汇总由"专门的汇总模型"执行**（用户已确认，见 [open-questions-resolved]）。因此聚合链路的模型调用为：`N 个成员 + 1 次汇总（方式A） + 1 次决策 = N+2 次`（方式 B 为 N+1 次）。
  - 汇总模型来源：默认可复用决策者所在 Key/模型，或允许单独指定一个低成本模型（配置项，默认复用决策者模型；评审确认）。
- **总超时优先**：任何成员卡住都不拖垮整体，到点即用已有结果继续（NFR-001）。
- **回退策略**：可用成员为 0 或决策者不可用 → 默认回退到普通故障转移路由（OQ-8），保证有返回。

### 7.3 成本与提示

- 聚合会放大 token 消耗（N+1/N+2 次调用）。UI 在开启聚合时明确提示成本放大，并展示每次聚合的调用次数与 token 估算（原始计量数据记录，报表延后，对应 OQ-6）。
- 并发上限可配，防止上游限流与成本失控。

## 8. 数据模型与加密存储

### 8.1 存储选型

对齐 cc-switch 使用 **SQLite**（本地单文件、原子写、抗损坏），承载配置与元数据；**敏感字段（API 密钥）单独加密**后再入库或存于加密文件。

```
数据目录（Windows）：%APPDATA%\SynaRoute\
├── synaroute.db           // SQLite：分类/Key元数据/映射/路由与聚合配置/日志
├── secrets.enc            // 加密的密钥材料（AES-256-GCM）
└── backups/               // 目标工具配置备份 + 自身配置备份
```

### 8.2 核心表结构（逻辑模型）

```
category            (id, type[claude-cli|claude-desktop|codex], routing_mode, ...)
provider_key        (id, category_id, name, vendor, base_url, protocol[anthropic|openai],
                     enabled, priority, secret_ref, headers_json, created_at, ...)
key_params          (key_id, temperature, max_tokens, top_p, timeout_ms, ...)
model               (id, key_id, real_name, source[fetched|manual], fetched_at)
model_mapping       (id, key_id, expected_name, real_name)   // 期望名→真实名
health_state        (key_id, status[up|down|unknown], last_checked, latency_ms, fail_count, breaker_until)
brain_config        (category_id, enabled, aggregate_mode[A|B], concurrency_limit,
                     total_timeout_ms, summarizer_ref, decider_ref)
brain_member        (id, category_id, key_id, model_name)
event_log           (id, ts, category_id, type[route|failover|health|aggregate|error],
                     key_id?, detail_json)   // 敏感信息脱敏
proxy_state         (category_id, port, status, updated_at)
```

> `secret_ref` 指向加密存储中的条目，DB 内不含明文密钥（NFR-006）。

### 8.3 加密方案（FR-018 / NFR-006，OQ-7 已确认：应用内加密文件）

- **算法**：AES-256-GCM（认证加密，防篡改）。
- **主密钥来源（默认）**：Windows DPAPI 保护（`CryptProtectData`）——把随机生成的数据加密密钥（DEK）用 DPAPI 加密后落盘，绑定当前用户账户，**免用户每次输入口令**（体验优先）。
- **可选增强**：用户可开启"主口令"，用 PBKDF2/Argon2 从口令派生密钥再包裹 DEK（安全优先，启动时输入口令）。默认关闭。
- **全链路脱敏**：界面默认掩码 + 临时"显示"；日志/事件对密钥、token 脱敏；剪贴板复制敏感信息给提示。

### 8.4 一致性与恢复（NFR-011）

- 所有配置写入走 SQLite 事务；密钥文件写入用原子替换 + 校验（GCM tag 校验完整性）。
- 启动时校验数据文件完整性，损坏则从最近 `backups/` 恢复并告警。

## 9. 模块划分（Rust 后端）

| 模块（crate/mod） | 职责 |
|---|---|
| `app`（Tauri 入口） | 窗口/托盘/生命周期、注册 IPC 命令与事件 |
| `proxy` | axum HTTP 服务：监听、接入层、下游协议识别、SSE 处理 |
| `router` | 模式判定、故障转移调度、聚合编排 |
| `upstream` | 上游适配：协议转换、模型映射、流式转换、上游 HTTP 客户端（reqwest + TLS） |
| `health` | 健康检查定时器、探测、熔断器状态机 |
| `secret` | AES-GCM 加解密、DPAPI/口令主密钥管理 |
| `store` | SQLite 访问（sqlx/rusqlite）、配置 CRUD、备份/恢复 |
| `tools` | 目标工具接入：配置文件路径解析、原子写入、备份/回滚（Claude CLI/桌面端/Codex） |
| `log` | 结构化事件日志、脱敏、供 UI 查询与实时推送 |
| `ipc` | 前后端命令与事件的类型定义（与前端 TS 类型对齐） |

### 9.1 关键技术选型

| 领域 | 选型 | 理由 |
|---|---|---|
| 桌面框架 | Tauri 2 | 基线约束 CON-1，包体小、Rust 后端安全 |
| HTTP 服务 | axum + tokio | 成熟异步、SSE 友好 |
| HTTP 客户端 | reqwest（rustls TLS） | 稳定、支持流式 |
| 存储 | SQLite（rusqlite 或 sqlx） | 对齐 cc-switch、原子可靠 |
| 加密 | `aes-gcm` + Windows DPAPI（`windows` crate） | 认证加密 + 免口令保护 |
| 前端 | React + TS + Tailwind + shadcn/ui | 基线约束 CON-1、对齐 cc-switch |
| 状态管理 | Zustand 或 React Query | 轻量、贴合 IPC 数据流 |

## 13. 待架构评审确认项（默认策略汇总）

1. **端点编排方案 A（三分类独立端口）** 作为默认（§5.1）。
