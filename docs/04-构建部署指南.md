## 2. ⚠️ 头号坑点：生产 exe 必须用 `tauri build`，禁止裸 `cargo build`

### 2.1 现象

部署后启动 `synaroute.exe`，界面打不开，WebView2 报：

```
嗯… 无法访问此页面
localhost 拒绝连接。
ERR_CONNECTION_REFUSED
```

### 2.2 根因

Tauri 应用的前端有两种加载方式，由构建方式决定：

| 构建命令 | 前端来源 | 结果 |
|---|---|---|
| `cargo build --release`（❌ 错误） | 运行时连 `devUrl`（`http://localhost:1420`） | 前端**没有嵌入**二进制；生产环境没有 dev server，连接被拒 → `ERR_CONNECTION_REFUSED` |
| `tauri build`（✅ 正确） | 编译期把 `frontendDist`（`../dist`）**嵌入**二进制 | 前端随 exe 分发，离线可用 |

关键：**裸 `cargo build` 不会执行前端构建、不会嵌入 `dist`、不会关闭 devUrl 回退**。它只编 Rust 部分，产出的 exe 是"半成品"，只能在 `npm run dev` 已启动的开发机上跑。

配置见 [`src-tauri/tauri.conf.json`](../src-tauri/tauri.conf.json)：

```jsonc
"build": {
  "frontendDist": "../dist",              // tauri build 时嵌入这里
  "devUrl": "http://localhost:1420",      // 仅 dev 用；裸 cargo build 会错误地回退到这里
  "beforeBuildCommand": "npm run build"   // tauri build 会先跑它重建前端；cargo build 不会
}
```

### 2.3 正确构建命令

```bash
# 在项目根目录（E:\workCode\ccCode\SynaRoute）执行

# 出正式安装包（NSIS）——交付用
npm run tauri build

# 只出 exe、不打安装包（日常快速验证用，更快）
npm run tauri build -- --no-bundle
```

产物路径：`src-tauri/target/release/synaroute.exe`

> 注意：`beforeBuildCommand` 已配为 `npm run build`，所以 `tauri build` 会**自动重建前端**。
> 不需要（也不应该）先手动 `npm run build` 再单独 `cargo build`——那正是踩坑的路径。

### 2.4 部署前必做的可证伪验证

**编完不要直接推。** 用以下命令确认前端确实嵌入了二进制，再部署：

```bash
# 1. 取当前前端 chunk 名
ls dist/assets/

# 2. 验证 exe 里含该 chunk 名（嵌入成功应 > 0；裸 cargo build 产物为 0）
grep -c "index-XXXXXXXX.js" src-tauri/target/release/synaroute.exe   # 用上一步实际文件名

# 3. 体积旁证：tauri build 产物比裸 cargo build 产物大约 10 万字节（前端资源的重量）
```

判据：**exe 内含前端 chunk 名 = 嵌入成功**。这是决定性证据。
（不要用 "exe 里是否含 `localhost:1420`" 判断——该串在正常 build 的配置数据段里也存在，无鉴别力。）

## 3. 部署流程（改配置/二进制前必备份，见 dev 硬规则）

```bash
# 1. 备份当前线上 exe（带日期与用途后缀，可回滚）
cp -f "F:/SynaRoute/synaroute.exe" "F:/SynaRoute/synaroute.exe.bak-<用途>-$(date +%Y%m%d-%H%M)"

# 2. 部署新 exe
cp -f "src-tauri/target/release/synaroute.exe" "F:/SynaRoute/synaroute.exe"

# 3. 部署后再校验一次前端 chunk 命中
grep -c "index-XXXXXXXX.js" "F:/SynaRoute/synaroute.exe"   # 应 = 1
```

> 部署目标 `F:\SynaRoute\synaroute.exe` 是本机当前运行位置，属环境相关信息，非硬编码进代码——代码内路径一律动态解析（dev 硬规则 2）。

## 5. 在线更新（Tauri updater）发布流程

在线更新走 Tauri updater 插件 + GitHub Releases（见 delivery-and-updates 决策）。客户端启动时拉取 endpoint 的 `latest.json`，比对版本号，用内置公钥验签后下载并安装新安装包。**验签是硬性的：签名对不上，客户端会拒绝更新。**

### 5.1 签名密钥（关键：私钥丢了就无法再发更新）

| 文件 | 位置 | 用途 |
|---|---|---|
| 私钥 | `~/.tauri/synaroute.key` | `tauri build` 时对产物签名。**绝密，绝不上传仓库，务必单独备份** |
| 公钥 | `~/.tauri/synaroute.key.pub` | 已 base64 编入 `tauri.conf.json` 的 `plugins.updater.pubkey`，随客户端分发 |

- 配置里的 `pubkey` 与本地 `synaroute.key.pub` **已核对一致、配对可用**（公钥指纹 `1F6689C022960775`）。
- **私钥一旦丢失**：无法为新版本签出能被老客户端验证的签名 → 只能重新 `tauri signer generate` 生成新密钥对、替换 `pubkey` 重新发一版，但**已装的旧客户端将无法自动更新到新链**（因为它们内置的是旧公钥），需用户手动重装。所以 **`synaroute.key` 必须离线安全备份**。
- 若确需重新生成：
  ```bash
  npm run tauri signer generate -- -w ~/.tauri/synaroute.key
  # 然后把新的 .pub 内容 base64 后替换 tauri.conf.json 的 pubkey（改前备份配置）
  ```

### 5.2 发布一个新版本的完整步骤

1. **改版本号**（三处保持一致）：`package.json` 的 `version`、`src-tauri/tauri.conf.json` 的 `version`、`src-tauri/Cargo.toml` 的 `version`。updater 靠这个号判断"有没有新版"。

2. **带签名构建**（私钥通过环境变量传入，`tauri build` 自动签名）：
   ```bash
   # 私钥密码：生成密钥时设了口令就填，没设留空
   export TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/synaroute.key)"
   export TAURI_SIGNING_PRIVATE_KEY_PASSWORD=""     # 若设了口令则填入
   npm run tauri build
   ```
   产物在 `src-tauri/target/release/bundle/nsis/`：
   - `SynaRoute_<版本>_x64-setup.exe` —— 安装包
   - `SynaRoute_<版本>_x64-setup.exe.sig` —— 该安装包的签名（updater 验签用）
   - `latest.json` —— 更新清单（含版本、下载地址、签名）

   > 若 NSIS 打包在本机报 `os error 17`（跨设备 rename），按 dev-progress 记录的手工预置 `%LOCALAPPDATA%\tauri\NSIS` 步骤处理。

3. **核对 `latest.json`**：里面的 `url` 必须指向第 4 步 Release 里安装包的实际下载地址，`signature` 为 `.sig` 内容，`version` 与第 1 步一致。

4. **发到 GitHub Releases**（endpoint 指向 `releases/latest/download/latest.json`，所以必须发成 **latest** release）：
   - 在 https://github.com/EngineeMoMo/SynaRoute 新建 Release，tag 用 `v<版本>`（如 `v0.2.0`）。
   - 上传 assets：`SynaRoute_<版本>_x64-setup.exe` **和** `latest.json`（两个都要传；`.sig` 的内容已进 `latest.json`，可不单独传）。
   - 确认该 Release 标记为 Latest（不要勾 pre-release，否则 `releases/latest/` 拿不到）。

5. **验证**：`curl -sL https://github.com/EngineeMoMo/SynaRoute/releases/latest/download/latest.json` 能拿到清单，`version` 是新版号；老客户端启动应能检测到更新。

### 5.3 endpoint 现状

当前 endpoint（见 `tauri.conf.json`）：
```
https://github.com/EngineeMoMo/SynaRoute/releases/latest/download/latest.json
```
仓库 owner 变更时，此处要同步改（改前备份配置）。历史上已因换 owner 改过两次，务必与实际仓库地址一致，否则客户端拉不到更新清单。

## 7. 快速自查清单

**日常构建/部署：**
- [ ] 用的是 `npm run tauri build`（不是 `cargo build`）
- [ ] `dist/assets/` 里的 chunk 名能在产物 exe 里 grep 到（> 0）
- [ ] 产物体积正常（约 1.9 MB 量级，明显大于裸 cargo build 产物）
- [ ] 部署前已备份线上 exe
- [ ] 部署后再次 grep 校验前端 chunk 命中

**发布在线更新：**
- [ ] 三处 version 已同步递增（package.json / tauri.conf.json / Cargo.toml）
- [ ] 构建前已 `export TAURI_SIGNING_PRIVATE_KEY`（否则产物无签名，updater 验签失败）
- [ ] `latest.json` 与安装包都上传到了 GitHub Release，且该 Release 是 Latest
- [ ] endpoint 的 owner/仓库名与实际一致
- [ ] 私钥 `~/.tauri/synaroute.key` 已离线安全备份
