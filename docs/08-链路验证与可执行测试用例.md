## 第一部分：链路验证结论（代码走读）

走读范围：`proxy.rs` / `upstream.rs` / `aggregate.rs` / `mcp.rs` / `tools.rs` / `store.rs` / `health.rs`。

### 1. 路由转移链路（下游请求 → 上游响应）

```
客户端请求
  → handle_request（proxy.rs:109）
      · 收集透传头（剔除鉴权/hop-by-hop/accept-encoding，is_stripped_header:641）
      · 读 body → 解析 model / stream / 下游协议（/messages=Anthropic）
      · candidates = enabled_keys_sorted(按 priority 升序) ∩ is_candidate(未熔断且非 Down)
  → 无候选 → 503「无可用 Key」
  → 逐个候选尝试：
      A. 流式且同协议 → try_stream_to_key（proxy.rs:389）
           · 2xx：SSE 边收边发，content-type 沿用上游，return（不再切换）
           · 非 2xx：缓冲错误体，切下一个
           · 连接失败：切下一个
      B. 其余 → forward_to_key（proxy.rs:515）
           · 模型映射（expected_name → real_name，命中才换，否则原样）
           · 跨协议转换（请求 + 响应双向；非 2xx 不翻译）
           · 2xx：return json_resp；非 2xx：记 failover，切下一个；连接失败：切下一个
  → 全部失败 → 502「全部 Key 不可用: {last_err}」
```

**结论：链路闭环，无死路。** 每个分支要么 return，要么 continue 到下一候选，末尾统一兜底 502。验证到的正确点：

- ✅ 优先级排序：`enabled_keys_sorted` 按 `priority` 升序，小号优先。
- ✅ 故障转移触发条件覆盖两类：上游非 2xx（有响应）+ 连接层失败（无响应），都记 failover 并续试。
- ✅ 流式首字节前可安全切换；首字节发出后不再切换（标准行为，符合文档）。
- ✅ 跨协议请求 + 响应双向翻译，非 2xx 错误体原样透传（便于看上游真实错误）。
- ✅ 鉴权头永远用 Key 自己的（覆盖下游带来的），下游鉴权头被剔除。

**已修复：**

- ✅ **健康探测语义**：原 `health_probe` 用 `/v1/models` 返 2xx 判活，只有 chat 端点的上游（/models 返 404/405）会被误判 `Down` 踢出路由。已改为**可达即健康**：拿到任意 HTTP 响应即视为 up，仅连接层失败（超时/连不上/DNS）或鉴权失败（401/403）判 down。借鉴 cc-switch `speedtest.rs` 的可达性判定思路。测试 R-11 验证。

**注意点（非缺陷，测试时留意）：**

- ⚠️ `wants_stream` 仅从 body 顶层 `stream` 布尔取值；下游不传则按非流式走缓冲路径。

### 2. 大脑聚合链路

```
run_plan / run_mcp（aggregate.rs）
  → resolve_work_dir（auto_follow ? 最近活跃项目 : 手填 work_dir）
  → retrieval_enabled ? retrieve(work_dir, prompt, brain.max_context_tokens) : 空
       ↑ 注意这是**检索输入**预算（打包多少文件正文），与输出长度无关
  → build_member_prompt（只读审阅者角色 + 文件上下文）
  → gather_members（并行，Semaphore 限流 concurrency_limit，总 timeout total_timeout_ms）
       · 每成员：get_key → is_candidate → 取密钥 → output_budget → text_completion/工具循环
       · output_budget：OpenAI 不发上限；Anthropic 取 min(窗口剩余, 模型最大输出)（每轮重算）；
         模型最大输出无法辨识 / 输入已占满窗口 → 报可行动错误且不发请求；
         仅缺 contextWindow 但模型名可辨识 → 按模型最大输出照常参与
       · 空答案/失败 → None（静默跳过，可选成员容错）
  → answers 为空 → 降级：决策者独答（不算失败）
  → 聚合：Full=全拼接 / Compressed=summarizer 压缩
  → 决策者 call_ref（keyId::model 解析）出计划/建议
  → run_plan: 返回 Plan；run_apply: 解析 ```file:path``` 块写盘；run_mcp: 只返建议不写盘
```

**结论：链路闭环，降级路径完备。** 验证到的正确点：

- ✅ `call_ref` 严格解析 `keyId::model`（split_once "::"），格式错误 fail-loud。
- ✅ 决策者是必需组件：`decider_ref` 缺失直接报错；成员可选，失败静默跳过。
- ✅ MCP 通道绝不写文件（run_mcp 无 parse_and_apply），只返 Markdown 建议。
- ✅ 并发受 `concurrency_limit`（`.max(1)` 防 0）与 `total_timeout_ms` 双重约束。
- ✅ 大 prompt 用 `Arc<str>` 共享，避免 N 个成员各持大副本。

**已修复：**

- ✅ **成员超时保留已完成结果**：原 `timeout(total, join_all(tasks))` 会因单个慢成员丢弃整轮结果。已改为**每个成员各自套 `timeout(total_timeout_ms, ...)`**：慢成员到点各自作废，`join_all` 总能在时限内返回，已答完的成员结果保留进聚合；只有全部成员超时/失败才降级为决策者独答。`total_timeout_ms` 语义变为「单成员上限」。测试 B-6 验证。

### 3. CLI 接入链路（codex / claude）

两条独立通道，别混淆：

| 通道 | 机制 | 写入文件 | 客户端看到的 |
|------|------|----------|--------------|
| **代理路由**（tools.rs apply） | 改客户端的 base_url 环境变量指向本地代理 | claude-cli: `~/.claude/settings.json`；codex: `~/.codex/config.toml` | 正常 chat，背后被 SynaRoute 转发/转移 |

- ✅ 两者写前都 `*.synaroute.bak` 备份 + 原子写。
- ⚠️ Claude 桌面端只写 `baseUrl` 字段（键名随版本可能变），可能需重启，属已知不确定项。

## 第二部分：可执行测试用例

> **环境变量约定**（按你的实际端口替换）：
> ```bash
> # 分类代理端口：启动代理后在分类页顶部查看，或用下面的探测命令
> export PROXY=http://127.0.0.1:<代理端口>
> export MCP=http://127.0.0.1:9527/mcp   # MCP 端口，默认 9527，被占用会自动上移
> ```
> Windows 上用 Git Bash / WSL 执行 curl；PowerShell 用户把 `curl` 换成 `curl.exe`。

### A 组：路由转移（代理通道）

前置：某分类（如 claude-cli）配 ≥2 个 Key，priority 分别为 0、1；启动代理。

#### R-1 代理存活探测
```bash
curl -s -o /dev/null -w "%{http_code}\n" $PROXY/v1/messages -X POST \
  -H "content-type: application/json" -d '{}'
```
**判据**：返回任意 HTTP 码（非 connection refused）即代理在监听。空 body 通常返回 400/502，正常。

#### R-2 单 Key 正常转发（Anthropic 非流式）
```bash
curl -s $PROXY/v1/messages -X POST -H "content-type: application/json" -d '{
  "model": "claude-sonnet-4",
  "max_tokens": 64,
  "messages": [{"role":"user","content":"只回复两个字：收到"}]
}'
```
**判据**：返回 Anthropic 格式响应，`content[0].text` 含模型回复。分类页事件日志出现一条 `route · 成功返回`。

#### R-3 OpenAI 协议非流式
```bash
curl -s $PROXY/v1/chat/completions -X POST -H "content-type: application/json" -d '{
  "model": "gpt-4o-mini",
  "max_tokens": 64,
  "messages": [{"role":"user","content":"只回复两个字：收到"}]
}'
```
**判据**：返回 OpenAI 格式，`choices[0].message.content` 有内容。

#### R-4 优先级顺序
把 priority=0 的 Key 配为**有效**，priority=1 配为无效密钥。发 R-2 请求。
**判据**：日志显示直接命中 priority=0 的 Key，不尝试 priority=1（第一个就成功不会往下走）。

#### R-5 故障转移（首个非 2xx）★核心
把 priority=0 的 Key 密钥改成错的（会返回 401），priority=1 配有效密钥。发 R-2 请求。
**判据**：
- 最终返回 2xx 成功响应（来自 priority=1）。
- 日志依次出现：priority=0 的 `failover · 失败（HTTP 401...）尝试下一个` → priority=1 的 `route · 成功返回`。

#### R-6 连接层失败转移
把 priority=0 的 Key 的 base_url 改成不可达地址（如 `https://127.0.0.1:1`），priority=1 有效。发请求。
**判据**：日志出现 `failover · 失败（连接 ... 失败）` → 切到 priority=1 成功。

#### R-7 全部失败
所有 Key 都用错误密钥。发请求。
**判据**：返回 502，body 为 `{"error":{"message":"全部 Key 不可用：HTTP 401: ...","source":"synaroute"}}`。日志每个 Key 都有 failover 记录，含上游真实错误体片段。

#### R-8 模型映射
给某 Key 配映射 `expected_name=claude-sonnet-4` → `real_name=<该Key真实模型>`。发 R-2（model 用 `claude-sonnet-4`）。
**判据**：开启"调用模型日志"后，日志的 trace 显示 `requested_model=claude-sonnet-4`、`real_model=<真实模型>`，发往上游的 request_body 里 model 已被替换。

#### R-9 跨协议：Anthropic 客户端 → OpenAI Key
分类下只留一个 **OpenAI 协议** Key（关流式）。发 R-2（走 /v1/messages，非流式）。
**判据**：客户端收到的是 **Anthropic 格式**响应（有 `content[].text`、`stop_reason`、`usage.input_tokens`），能正常解析——说明请求转 OpenAI、响应又翻译回了 Anthropic。

#### R-10 跨协议：OpenAI 客户端 → Anthropic Key
分类下只留一个 **Anthropic 协议** Key。发 R-3（走 /v1/chat/completions）。
**判据**：收到 **OpenAI 格式**响应（`choices[0].message.content`、`finish_reason`、`usage.total_tokens`）。

#### R-11 健康探测：可达即健康（不因 /models 404 误判）★已修复
配一个**只有 chat 端点、/models 返 404/405** 的上游 Key（如 DeepSeek 类），密钥有效。等一轮健康检查。
```bash
# 先确认该 Key 的 /models 确实非 2xx（复现旧误判的前提）
curl -s -o /dev/null -w "  /models http=%{http_code}\n" <该Key的base_url>/v1/models \
  -H "authorization: Bearer <该Key密钥>"
```
**判据**：分类页该 Key 显示 `up`（可达即健康），并正常参与路由——不再因 /models 返回 404/405 被误判 `down` 踢出。反向验证:把密钥改成错的(触发 401/403) → 显示 `down`(鉴权失败判不可用,符合预期)。
> 实现：`health_probe` 改为「拿到任意 HTTP 响应即可达」，仅连接层失败（超时/连不上）或鉴权失败（401/403）判 down。借鉴 cc-switch `speedtest.rs` 的可达性判定思路（其 `proxy/health.rs` 为占位、真实逻辑在 speedtest）。

#### R-12 同协议流式透传
```bash
curl -N $PROXY/v1/messages -X POST -H "content-type: application/json" -d '{
  "model": "claude-sonnet-4",
  "max_tokens": 256,
  "stream": true,
  "messages": [{"role":"user","content":"数到10，每个数字一行"}]
}'
```
**判据**：`-N` 下能看到内容**逐块**打印（不是等整段才出）；响应头 content-type 为 `text/event-stream`。

### B 组：大脑聚合

前置：某分类大脑聚合已启用，配 ≥2 个成员 + 1 个决策者，各成员 Key 有效。

#### B-1 桌面端聚合出计划（Plan）
桌面端大脑页填 prompt「审查 xxx 模块」→ 运行。
**判据**：返回决策者综合的**修改计划文本**（不含完整代码）；参与者并行跑（观察日志各成员调用）。

#### B-2 执行计划（Apply，会写盘）
B-1 后点确认执行。
**判据**：按计划把 ```file:path``` 块写入 work_dir 对应文件；返回 `AppliedChange` 列表标记每个文件 success/error。**此步会真实改文件，在测试目录做。**

#### B-3 成员失败容错
把一个成员的 Key 密钥改错（另一个成员 + 决策者有效）。运行聚合。
**判据**：失败成员静默跳过，聚合照常用剩余成员完成，不整体报错。

#### B-4 决策者失败 fail-loud
把决策者 Key 改成无效。运行聚合。
**判据**：整体报错（决策者是必需组件），错误信息明确指向决策者/密钥。

#### B-5 无成员降级
临时移除所有成员，只留决策者。运行聚合。
**判据**：不报错，由决策者独立回答（member_labels 为空，返回内容仍有）。

#### B-6 成员超时边界（保留已完成成员）★已修复
把 `total_timeout_ms` 调小（如 3000），配一个必然慢的成员（指向会 hang 的端点）+ 一个快成员。运行。
**判据**：慢成员到点被单独作废，**快成员的答案照常进入聚合**，决策者基于已完成成员出计划——不再"一个超时全丢、降级为决策者独答"。只有当**全部**成员都超时/失败时才降级独答（等同 B-5）。
> 实现：`gather_members` 现按单个成员套 `timeout(total_timeout_ms, ...)`，`join_all` 总能在时限内返回；`total_timeout_ms` 语义为「单成员上限」。

## 附：一键冒烟脚本（代理 + MCP 快速自检）

保存为 `smoke.sh`，改好端口后 `bash smoke.sh`：

```bash
#!/usr/bin/env bash
set -u
PROXY="${PROXY:-http://127.0.0.1:0}"      # 改成真实代理端口
MCP="${MCP:-http://127.0.0.1:9527/mcp}"

echo "== R-1 代理存活 =="
curl -s -o /dev/null -w "  proxy http=%{http_code}\n" $PROXY/v1/messages -X POST \
  -H "content-type: application/json" -d '{}' || echo "  proxy 未监听"

echo "== C-1 MCP initialize =="
curl -s $MCP -X POST -H "content-type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' | head -c 300; echo

echo "== C-2 MCP tools/list =="
curl -s $MCP -X POST -H "content-type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}' | head -c 300; echo

echo "== C-6 缺 prompt 应报工具错误 =="
curl -s $MCP -X POST -H "content-type: application/json" \
  -d '{"jsonrpc":"2.0","id":6,"method":"tools/call","params":{"name":"synaroute_ai","arguments":{}}}' | head -c 300; echo
```

**判据**：四段都返回内容、无 connection refused，initialize 返回 protocolVersion，缺 prompt 返回 isError=true。
