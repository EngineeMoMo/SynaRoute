### 第二轮审查（2026-08-01）修出的问题

按严重度：

1. **P0 · 切主题会把刚关掉的开机自启动重新装回系统**（`store.ts` `setTheme`/`setLang`）。
   `store.settings` 只在挂载时写一次，设置页此后改的字段只进它自己的局部 state，而
   `setTheme` 提交的是 `{...get().settings, theme}` —— 挂载那一刻的旧快照。后端
   `save_settings` 对 `mcp_*`/`active_*`/`proxy_ports`/`master_password_enabled` 有「保留后端值」
   防线，但 `auto_start`/`log_dir`/`request_log_enabled`/`lan_exposure`/`health_*` 没有。
   路径：关自启动（注册项已删、页面显示关）→ 同页点「深色」→ 提交旧快照 `autoStart: true`
   → **重新注册自启动项**，而页面仍显示「关」。
   修法：新增 `persistOneSetting` —— 先 `getSettings()` 拉磁盘权威值再合并。
   **已故障注入验证**：旧写法确实会把 `autoStart` 翻回 true。
2. **P1 · 路径遏制有两条绕过**（`aggregate.rs`）。原守卫 `parent.exists() && !is_within_work_root(..)`
   在父目录不存在时被短路，紧接着就是 `create_dir_all` + `fs::write`：① `vendor/` 是链接目录时
   `vendor/sub/x.txt` 的父目录不存在 → 沿链接把目录建到工作目录外（Windows junction 普通权限可建，
   pnpm 就在用）；② 目标文件自身是符号链接时 `fs::write` 跟随链接覆盖其目标。
   改成 `check_no_link_escape`：向上找最近**已存在**的祖先再校验 + `symlink_metadata` 判目标是否为链接。
   +4 测试，已故障注入（退回旧守卫，3 条相关测试立刻变红）。
3. **P2 · `Retry-After` 取最大值拖垮整池**（`proxy.rs`）。候选 A 撞按天配额回 3600（夹到 300）、
   候选 B 只是瞬时抖动 → 取最大值让整个分类停摆 300s，而 1s 后 B 就能服务。改取**最小值**
   （各候选中最早可再试的时刻）。注意 `all_failed_gate_remaining` 里那处 `.max()` 是**对的**、
   不能一起改：它比较的是同一个结论的两个下限（短路窗口剩余 vs 上游要求），都是「不早于」。
4. **P2 · 硬错误被包装成「过载请重试」**（`proxy.rs`）。密钥填错回 401 → 全候选失败 → 529
   `overloaded_error` + `Retry-After`，客户端当上游过载持续退避重试，界面显示「过载」而根因是
   配置错误；短路窗口一到期又放行一个请求再撞 401。现按最后失败状态码分流：401/403/404 等
   4xx 与协议不匹配的 501 **原样回传、不带 Retry-After、不武装短路窗口**；408/409/429/5xx/
   连接层失败才走 529（这三个 4xx 划进临时性，与 Anthropic SDK 重试判据一致）。
5. **P3 · `supports1m` 借用非路由落点的窗口数据**（`model.rs` + `tools.rs`）。两个漏洞叠加：
   逐 Key `find_map`（主 Key 查不到就用备用 Key 的）+ 兜底解析路径也返回窗口。可能写出
   `supports1m: true` 而请求实际落在 200k 上 → 桌面端给出必然被截断的选项。改成只认**主 Key**
   + 只认命中路径（Mapping/Tier/Native）。
6. **P3 · 锁定态在大脑聚合里被报成「未配置密钥」**（`aggregate.rs`）。`.ok().flatten()` 把
   「未解锁」的 `Err` 吞成 `None`。`secret.rs` 的 `get` 专门返回 `Err` 就是为了让这条可行动信息
   传出去；决策者路径用 `?` 本来就是对的，两条口径不一致。已改为保留 `Err` 文案。
7. **前端一致性 5 条**：导入后没刷新全局 settings（导入的主题不生效、且会被下次切主题顶回）、
   启用主口令弹窗字面显示 `{count}`、busy 期间遮罩/X 仍可关弹窗（导出跳过条数与迁移失败原因
   随组件卸载静默丢失）、口令校验提示是不可达死码（只塞进 disabled、界面一个字不说原因）、
   i18n 三条 en 缺失 + 20 条死键。i18n 现为 **zh 418 / en 418，双向零缺失、占位符零不一致**。

**审查者指出的一处推理错误（已确认）**：锁定态选 503 的理由原写「529 会引起客户端无意义的
自动重试」，但 Anthropic SDK 的重试判据是 `408/409/429 或 >= 500` —— 503 一样会被自动重试，
该前提不成立。保留 503（语义上「服务暂时不可用」比「上游过载」贴切；真要阻止自动重试只能用
4xx，而那会让人以为是请求本身有问题），但把理由改正了。

## 二、P0：~~必须先修~~ ✅ 已修 —— 重复接入会冲掉「接入前备份」

> **2026-07-31 换机后已修。** 修法：`.bak` **首写即锁**（`backup_path_for(path)` 已存在时不再覆盖）
> + `restore_one` 还原成功后**删除 `.bak`**，让下一轮接入重新抓一份新鲜的接入前快照。
> 护栏 `tools::tests::repeated_apply_with_changed_content_keeps_original_backup`
> 已用故障注入**双向验证**：把「首写即锁」还原成无条件覆盖 → 变红（.bak 被写成 v1）；
> 把「还原后删 .bak」去掉 → 也变红。以下保留原始分析，供理解根因与判据方法。

**这是数据丢失级缺陷，触发条件很日常。**

### 定位

`src-tauri/src/tools.rs` 的 `backup_and_write_bytes`（约 1047 行）：

```rust
if path.exists() {
    if let Ok(current) = std::fs::read(path) {
        if current == data { return Ok(()); }   // ← 只有「逐字节相同」才短路
    }
}
if path.exists() {
    std::fs::copy(path, backup_path_for(path))?;  // ← 否则无条件覆盖 .bak
}
```

### 复现

| 步骤 | `.bak` 内容 |
|---|---|
| 首次接入 | 用户原始配置 ✅ |
| 改代理端口后再接入（内容变了 → 守卫不命中） | **已接入态 v1** ❌ |
| 点「还原」 | 拿回「已接入 v1」，**用户原始配置永久丢失** |

触发条件（任一即可，都很日常）：改代理端口、可服务模型列表变化、
MCP 注册时 exe 路径变化（升级换目录必然发生）。

### 影响面

- **CLI 与 Codex 会真的还原错** —— 它们的 `restore` 走 `restore_one(&path)`，直接从 `.bak` 读。
- 桌面端只是留误导性残留 —— 它的 `restore_desktop_at` 不读 `.bak`，
  走 `write_desktop_meta_clear_preferring` + `read_desktop_prev_applied_id`。

### 现存测试为何没抓到

`tools.rs` 的 `repeated_apply_does_not_clobber_backup`（约 2347 行）**只覆盖「内容相同」那一种**，
所以它一直是绿的。改端口/改模型/换 exe 路径这三条真实路径都绕过了它。

### 实证

本机 `%LOCALAPPDATA%\Claude-3p\configLibrary\_meta.json.synaroute.bak` 里存的是
`{"appliedId":"…000053796e61","entries":[{"id":"…000053796e61","name":"SynaRoute"}]}`
—— **已接入态**，不是接入前的 cc-switch 态。

### 实际修法（已落地）

1. `.bak` **首写即锁**：`backup_and_write_bytes` 里备份前先判 `backup.exists()`，已存在就不再拷。
2. `restore_one` 还原成功后**删掉 `.bak`**（删除失败只告警，不把已成功的还原报成失败），
   让下次接入重新抓一份新鲜的接入前快照。
   （副作用：连点两次还原，第二次返回「无备份，无需还原」—— 这是准确的，可接受。）

### 验证判据（可证伪，已执行）

`tools::tests::repeated_apply_with_changed_content_keeps_original_backup` 覆盖：

```
写入用户原始内容 → 接入 v1（.bak = 原始）
→ 接入 v2 / v3（内容各不相同）→ 断言 .bak 仍是原始，而不是 v1
→ restore → 断言拿回原始内容
→ 断言 .bak 已被删除
→ 用户改动 → 再接入 → 断言新 .bak 记录的是「本轮接入前」的内容
```

故障注入实测（两处分别注入、分别复现红）：
- 把守卫改回无条件 `copy` → `left: SYNAROUTE_V1_PORT_8787 / right: OFFICIAL_CONFIG`（红）
- 去掉「还原后删 .bak」→ 「还原成功后应删除 .bak」（红）

## 三、~~测试基线不稳定~~ ✅ 已修：短路窗口在测试间串台

> **2026-07-31 换机后已修。** 两处一起改：
> 1. 短路窗口的键从「分类名」改为「**代理实例命名空间 + 分类名**」（`ProxyManager::gate_key`）——
>    生产环境全程只有一个 `ProxyManager`，语义完全不变；测试里每个用例各建一个实例，天然互不干扰。
> 2. `ProxyManager::start()` / `stop()` 里各清一次窗口，顺带修掉一个真实产品缺陷（下详）。
>
> 现在 `cargo test --lib` = **283 passed / 0 failed**，连跑 5 次全绿；`--test-threads=1` 全量也全绿。
> 以下保留原始分析，因为它同时是「进程级共享状态如何污染测试」的取证范式。

原先 `cargo test --lib` 会**偶发**红一条，同一份干净代码（`06aa63a`，工作区 clean）连跑三次实测：

```
run 1 → 276 passed; 1 failed
run 2 → 276 passed; 1 failed
run 3 → 277 passed; 0 failed
```

红的固定是 `proxy::tests::proxy_fails_over_bad_to_good`：

```
assertion `left == right` failed: 应故障转移到好 Key 返回 200
  left: 502
 right: 200
```

**这不是故障转移的 bug，是测试污染。**

### 根因

`6928f4c` 加的「全部 Key 失败」短路窗口用的是**进程级共享状态**，而测试默认多线程并发跑：

| 位置 | 内容 |
|---|---|
| `all_failed_gate()` | `OnceLock<Mutex<HashMap<String, …>>>`，**整进程一份**，早先按分类名字符串做 key |
| 全部候选失败处 | `arm_all_failed_gate(...)` 给该分类武装 5s（`ALL_FAILED_SHORT_CIRCUIT_MS`） |
| 每个请求入口 | 先查窗口，命中就**直接返回失败，压根不打上游** |

冲突的两条测试**都用 `CategoryType::ClaudeCli`**，而 gate 只认分类名、不认是哪个 `Store` / 哪个 `ProxyManager` / 哪个临时目录：

1. `proxy_all_fail_returns_*` 故意让两个候选全失败 → 给 `ClaudeCli` 武装 5s 窗口
2. `proxy_fails_over_bad_to_good` 也用 `ClaudeCli`，若在这 5s 内发请求 → 撞上短路 → 直接失败
3. 谁先跑、隔多久跑由线程调度决定 → 时红时绿

`all_failed_gate_arms_blocks_then_clears_on_success` 注释里写了「用独立分类避免与其它并发测试共享 gate 状态」——**这个隔离意识只落到了那一条单元测试上，两条 e2e 测试没做**。

### 取证（三种时序三种结果，与假设完全吻合）

```bash
cd src-tauri
# 修复前必挂：强制让 all_fail 先跑完立刻跑 failover
cargo test --lib -- --test-threads=1 proxy_all_fail_returns proxy_fails_over_bad_to_good
# 全过：只跑 proxy 模块，时序不同
cargo test --lib proxy::
# 全过：单独跑，没人给它武装窗口
cargo test --lib proxy_fails_over_bad_to_good
```

### 实际修法（已落地，同时修掉一个真实产品缺陷）

**为什么没采用「只在 `start()` 里清一次」这个更小的改法**：那只能覆盖「先武装、后 start」的时序。
两条 e2e 用例各自 `start()` 后才发请求，谁的窗口在谁的请求之前落下仍由调度决定——治不彻底。
故改成从键上隔离，`start()`/`stop()` 的清理只作为产品行为保留。

1. **按代理实例隔离**：`ProxyManager` 持有一个自增的 `gate_ns`，窗口键为 `{gate_ns}:{分类名}`
   （`ProxyManager::gate_key`），并把它随 `handle_request` 一路传下去。生产环境全程只有一个
   `ProxyManager`（`lib.rs:905`），语义与原先「按分类」完全一致。
2. **启停即清**：`start()` 在插入 `running` 前、`stop()` 在移除后各清一次窗口。这修掉的是产品缺陷——
   窗口原本只有「一次成功转发」或「自然到期 5s」两条解除路径，而「停止代理 → 换/修好 Key →
   重新启动」这个**用户已介入的明确信号**被忽略，导致刚点启动后最长 5s 内的请求仍被挡成失败，
   用户视角是「刚点了启动却说全部 Key 不可用」。

新增护栏：
- `gate_is_isolated_per_proxy_manager_instance`：两个 `ProxyManager` 的同一分类必须是不同的键，
  一个武装不影响另一个。
- `start_clears_leftover_short_circuit_gate`：`start()` 与 `stop()` 都必须清掉残留窗口。

### 验证判据（可证伪，已执行）

故障注入分两轮，确认两处修复**各自**都能被抓到：
1. 同时禁用 `start`/`stop` 的清理并把 `gate_key` 退化成不带命名空间 →
   `--test-threads=1` 那条命令复现 `left: 529 / right: 200`（红）。
2. 恢复命名空间、仍禁用清理 → 那条命令**转绿**（证明隔离本身就足以解决测试串台），
   而 `start_clears_leftover_short_circuit_gate` 变红（证明清理这条产品行为独立被覆盖）。

全部恢复后：`cargo test --lib` 连跑 5 次均 **283 passed / 0 failed**；`--test-threads=1` 全量也全绿。

无上游 `Retry-After` 时的兜底退避 = 短路窗口秒数（5s），且**最少 1s**——`Retry-After: 0` 等于不退避，

#### ✅ 主口令增强模式（FR-018 可选增强）

原状态：开关 `disabled` + 「开发中」，`master_password_enabled` 字段后端零使用点。

**核心设计：模式的事实来源是密钥库文件本身**（`secrets.enc` 里有无 `master` 头部），
`settings.master_password_enabled` 只是 UI 镜像，启动时**以库为准**对账修配置。
反过来（以配置为准改库）会改掉用户真实的加密状态。

| 模式 | 密钥来源 | 换机可用 | 需输口令 |
|---|---|---|---|
| DPAPI（默认） | `CryptProtectData`，绑当前 Windows 账户 | ❌ | 否 |
| 主口令 | Argon2id 派生（64MiB/t=3/p=1） | ✅ | 每次启动一次 |

`crypto.rs` 为此加了**第二组 API**（与 `seal`/`open` 并存，别混用）：
`derive_vault_key` + `seal_with_key`/`open_with_key`。理由是性能——
密钥库每条密钥各一个盒子，而代理转发每次取密钥都要解一次；
若每条都跑 KDF，一次多 Key 故障转移就是几百毫秒纯 CPU。故解锁时派生一次 `VaultKey`
常驻内存，各条只做 AES-GCM（微秒级）。每条独立 nonce（同密钥复用 nonce 泄露明文异或）。

还加了**校验串**（`make_verifier`/`check_verifier`，固定明文的密文存在库头部）。
这是必需的：若靠「试解某条密钥」判断口令，密钥库为空时无从判断，
会把错口令当成解锁成功 → 随后新存的密钥用错密钥加密、旧密钥永久解不开。

`secret.rs` 的三个迁移操作（`enable`/`disable`/`change_master_password`）都遵守三条硬要求，
任一不满足即密钥永久丢失：

1. **先整库解密成功再写盘**。边解边写时中途某条失败会留下「一半口令密文、一半 DPAPI 密文」，
   而 `is_master_mode()` 已为真 → 剩下那半永远读不出来。
2. **落盘前备份原库**（`.enc.master-{on,off,change}-<时间戳>`）。这是唯一一次整份重写全部密文。
3. **落盘失败回滚内存**（含 `vault_key`），保持「内存态不领先磁盘」。

另有几处刻意的判断，都有测试：

- **锁定态 `get` 返回 `Err` 而不是 `Ok(None)`**。这是最容易写错、后果最隐蔽的一处：
  `Ok(None)` 会让转发、`has_secret` 对账、导出都当成「这个 Key 没配密钥」去提示用户重录。
- **锁定态 `set` 拒绝写入**，绝不回退成 DPAPI 加密（否则库里两种密文并存而用户以为全由口令保护）。
- **降级态（本次启动读盘失败）禁止切换模式**——那时 `entries` 是空的，迁移等于把密钥全丢掉还声称已加密。
- **关闭/改口令都要求输入当前口令**，即使已解锁（防止有人趁已解锁的机器直接撤掉保护）。
- **`save_settings` 不让前端覆盖镜像字段**。用户切个主题就会带上旧快照，
  若能写成 `true`，下次启动便按「已启用」引导解锁而库里没有 `master` 头部 —— 自造死局。
- **锁定态跳过 `has_secret` 对账**，否则会把全部标记刷成 false 写盘。
- **锁定态跳过健康探测**（`check_one` 与 `check_category` 各一道，因为前端「手动检测」直接走前者），
  否则 UI 一片红而真实原因只是没解锁。

UI：设置页开关改为触发对话框（启用/关闭都要整库迁移，必须收口令），
`MasterPasswordDialog` 四合一（enable/disable/unlock/change），启用时显式警告
「口令无法找回，忘记等于永久失去全部密钥」；已启用时旁边有「立即锁定」与「修改主口令」；
锁定时 CategoryPage 顶部有 **danger 级常驻条**（比 cc-switch 接管那条更靠前——它让**全部**转发失败）。

测试：`secret.rs` 13 个（迁移往返 + 重开解锁、锁定态读写、错口令不锁回已解锁态、
空库靠校验串判口令、备份、降级拒绝、重复启用拒绝、两个密文 map 都清）、
`crypto.rs` 8 个长驻密钥用例、`store.rs` 3 个（镜像不被前端覆盖双向、专用写入幂等、锁定态跳过对账）、
`health.rs` 1 个（锁定态不改健康态）。**其中 4 个做过故障注入验证确实能变红**
（锁定态退化成 `Ok(None)`、迁移残留 DPAPI 密文、关闭时只在锁着才验口令、
镜像允许前端覆盖、对账不跳过锁定态）。

### ✅ 原「未系统覆盖」清单已全部查完（2026-07-31）

五个区域逐一过完，**未发现缺陷级问题**；顺手补了 2 处加固 + 10 个测试。结论备查：

| 区域 | 结论 |
|---|---|
| `aggregate.rs` 超时预算 / 成员降级 / 决策者兜底 | 干净。三阶段共享墙钟 deadline，`decider_floor_ms`（35%、≥90s、被 45% 夹住）保证决策者不被饿死；各阶段 5s 最小下限防 0ms。降级链完整：成员全败→决策者独答（带上已检索文件，不浪费检索开销）；压缩失败→全量拼接；决策者失败→返回已聚合成员意见并标注原因。信号量排队时间**刻意不计入**成员超时（否则并发数<成员数时后排成员在队列里就被判超时）。单请求 HTTP 超时给预算 +5s 余量，让外层 `tokio::timeout` 先到点报干净错误。空响应（200 但 content 空）显式转错误，不当有效答案流转。`mcp_client_timeout_ms` = 各分类 total 最大值 +30s，保证服务端先返回 |
| `retrieval.rs` / `codegraph.rs` | 干净。敏感文件排除分两级、恒定无开关，Tier B 只对配置类扩展名按名字子串判定（不误伤 `TokenService.java` / `secret.rs`）。`pack_symbols` 有个易写错却写对的细节：预算装不下第一个符号时**截断后装入**而非 `break`——返回空会让上层降级到文件级检索、反而按 8000 字符/文件发送，更贵。codegraph 全部 `Command::args` 数组传参，无 shell 拼接；失败判据是「能否解析成 T」而非退出码（codegraph 恒返回 0） |
| `health_probe_real` | 干净。探测与熔断彻底分离：探测只写 `status`/`latency`，`is_candidate` 只看熔断窗口，故探测端点 401 / 探测模型名不匹配都不会把真实流量本可成功的 Key 踢出路由。探测超时封顶 30s（`fast_timeout`）不跟随用户为慢厂商设的长超时，否则串行探测循环会被一个挂掉的慢 Key 拖住几分钟 |
| 前端与磁盘状态一致性 | **比原先担心的更好**。前端 Badge 用的是 `ToolConfigPreview.mcpRegistered`，由 `is_mcp_registered()` **每次实读磁盘**（CLI/桌面端读 `mcpServers.synaroute`，Codex 解析 `config.toml`）；settings 里的 `mcp_registered_categories` 只用于「端口漂移后批量重写」这一后端内部用途，不参与 UI 展示 → 不存在展示漂移 |
| `lib.rs` IPC 命令面密钥外泄 | 40 个命令逐个过完。`reveal_secret` 是唯一返回明文的，设计如此。`RequestTrace` 不含鉴权头；`fetch_models_draft` 接受前端传 secret，但那是用户正在编辑器里填的值、本就在前端内存里，不构成新外泄面；事件日志 / `get_settings` / `get_tool_config_preview`（走 `redact_config_secrets`）均不泄密 |
| 测试隔离性（剩余三处进程级状态） | 已核对，**可划掉**。`default_log_dir()` 的 `OnceLock` 缓存的是一个路径；`LOG_LOCK` 与 `atomic_write` 的 `WRITE_LOCK` 是纯互斥锁。三者都不携带「会改变后续请求判定的业务状态」，与 `all_failed_gate`（按字符串键存业务状态）性质不同，不具备串台条件 |

**本轮顺手做的 2 处加固**（不是发现的 bug，是「会写磁盘 + 有安全判定 + 零覆盖」这个组合本身的风险）：

1. **`parse_and_apply` 加第二道路径防线**（`aggregate.rs`）。原有的组件检查看的是 LLM 给的
   **字符串**（拒 `..`/绝对路径/盘符/UNC），但符号链接是文件系统层面的事：work_dir 下若存在
   指向外部的链接目录（`link/` → `C:\Windows`），`link/x.dll` 不含 `..`、非绝对路径，
   组件检查完全放行，实际却写到了工作目录之外。新增 `is_within_work_root`：落盘前把父目录
   `canonicalize` 后确认仍在 work_dir 下，**fail-closed**（canonicalize 失败即判不安全，
   宁可拒写让用户重试）。只在父目录已存在时校验——待创建的新子目录无链接可循。

### Claude Code CLI（`claude.exe`，本轮版本 v2.1.219）

位置：`%LOCALAPPDATA%\Claude-3p\claude-code\<版本>\claude.exe`（约 265MB，内含打包后的 JS）

分块搜字节串定位，再 dump 上下文：

```bash
node -e '
const fs=require("fs");const f="claude.exe";
const fd=fs.openSync(f,"r"),size=fs.statSync(f).size;
const n=Buffer.from("CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY");
const CH=1<<24;let pos=0,prev=Buffer.alloc(0);
while(pos<size){const len=Math.min(CH,size-pos);const b=Buffer.alloc(len);
 fs.readSync(fd,b,0,len,pos);const hay=Buffer.concat([prev,b]);let i=0;
 while((i=hay.indexOf(n,i))!==-1){console.log(pos-prev.length+i);i++;}
 prev=b.slice(Math.max(0,len-n.length));pos+=len;}'
```

已确认的关键事实（写代码时的判据）：

- `kn()`（getAPIProvider）只有在 `wy()`（即 `Ot.gatewayAuth` 已设）时才返回 `"gateway"`；
  `gatewayAuth` 仅由 `CLAUDE_CODE_USE_GATEWAY` + `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`
  或企业 `enterpriseGateway` 设置。**SynaRoute 不写 USE_GATEWAY，故 CLI 走的是 `firstParty` 分支。**
- 因此模型发现走的是 `BIc()`/`GIc()`/`uGr()`（源码内叫 gatewayDiscovery），条件为：
  `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` 为真 **且** `kn()==="firstParty"`
  **且** 非官方 anthropic base url **且** `ANTHROPIC_BASE_URL` 已设。
  它 `GET {base}/v1/models?limit=1000`，**超时仅 3000ms**、`redirect:"error"`，
  校验 schema 是 `{id: string, display_name?: string}`（`.optional()` 不接受 `null`），
  并按 `/^(claude|anthropic)/i` 过滤 `id` —— 这就是 `to_gateway_model_id` 要包
  `claude-synaroute-` 前缀的原因。
- bool 型环境变量的真值判据 `Yt()`：`["1","true","yes","on"]`。
- **claude.exe 内嵌了一份官方 gateway 协议规范全文**（本轮在 offset ≈ 258929000 附近）。
  错误信封形状、status→`error.type` 对应表、`/v1/models` 返 404 即干净回退、
  `/managed/settings` 的 404 与 `200 {}` 语义不同、`/v1/{metrics,logs,traces}` 返 404

## 九、桌面端模型名判据（2026-07-31 反查修正，**推翻了此前的错误结论**）

### 此前错在哪

旧记忆/文档写的是「模型名校验**只是面板黄字**，只要 `inferenceModels` 非空就能用」。
**这是错的**，实际是硬过滤。按错的结论办事的后果：桌面端分类里配 `glm-4.6` 之类对外名，
保存与接入都不报错，用户重启桌面端后模型选择器**空的**，开会话抛 `ModelsNotDiscoveredError`
——症状与「卡在登录页」同级难排查，而根因埋在几天前存 Key 那一刻。

### 判据原文（app.asar v1.24012.9，offset ≈ 6842900）

```js
const Dc=["sonnet","opus","haiku","fable","mythos"];
const nhe=new RegExp(`^(${Dc.join("|")})(-[\d.]+)?$`);   // 裸档位名，可带 -数字/点
const Snt=["claude",...Dc,"anthropic"];                   // 须含其一
const Ent=/ark-code|astron|command-r|deepseek|doubao|gemini|gemma|glm|gpt|grok|hermes|hy3|kimi|lfm|\bling\b|llama|longcat|mimo|minimax|mistral|mixtral|moonshot|nemotron|openai|phi-|qianfan|qwen|tc-code|\bunic\b|yi-|stepfun|step-3|seed-|bytedance|hunyuan|granite|amazon\.nova|nova-|devstral|ministral|ernie|codex|arcee|trinity|abab|phi\d|\bk2\.|\bm2\.|jamba|arctic|solar|mercury|zamba|kat-coder|\bds-|dpsk/;
function sD(e){const t=e.toLowerCase();return Ent.test(t)?!1:nhe.test(t)||Snt.some(n=>t.includes(n))}
```

**厂商名黑名单（`Ent`）优先于关键词（`Snt`）。**

### 硬过滤链路（offset ≈ 7964450）

```
resolvedModels() → W0n(provider,{adminList,discovered})
  末行: return e ? i.filter(o => aD(e, o.id).ok) : i     ← 直接删掉不合规条目
       （aD("gateway", id) → aKt(id) → sD(id)）
→ resolveDefaultSessionModel() 见空 → {ok:false, reason:"models_not_discovered"}
→ 开会话抛 ModelsNotDiscoveredError
```

`validateSessionModel` 的 allowed 成员判断（`min(t,n)`）也是拿**过滤后**的列表比对，同样救不回来。
所以「`inferenceModels` 非空但全不合规」与「`inferenceModels` 为空」后果**完全等价**。
面板旁那句 `Doesn't look like an Anthropic model: {reason}` 只是 warn 谓词，不是全部影响。

### 最容易踩的一条：`claude-synaroute-` 前缀对桌面端无效

| 名字 | Claude Code CLI | 桌面端 |
|---|---|---|
| `glm-4.6` | ✗（不以 claude/anthropic 开头） | ✗（命中 `glm`） |
| `claude-synaroute-glm-4.6` | ✓ **靠前缀救回** | ✗ **仍命中 `glm`，前缀无用** |
| `claude-opus-4-8` | ✓ | ✓ |
| `opus`（裸档位名） | ✗（会被包前缀） | ✓ |

两端是两套规则：CLI 只判前缀、无黑名单（`is_cli_discoverable_model_id`）；桌面端要求含关键词
**且**不含厂商名（`is_desktop_acceptable_model_id`）。**别拿一个顶另一个。**

### SynaRoute 的实现与取舍

1. `model.rs::is_desktop_acceptable_model_id` —— 1:1 复刻 `sD()`，**不引 `regex` 依赖**
   （手写词边界 `\b` 与 `phi\d`；黑名单其余项是普通子串）。
2. `lib.rs::upsert_key` → `reject_desktop_key_with_unusable_model_names` ——
   桌面端 Key 的**对外名**（`serviceable_models()`，即真正写进 `inferenceModels` 的那份）
   有任一不合规就**拒绝落盘**，错误消息含被拒名字 + 后果 + 可照做的修法。
   **无条件校验**（用户拍板「该严，避免不可用」）：即使这次只改了优先级，历史遗留的不合规 Key
   也必须先修好。代价是老数据调优先级/开关会被拦一次，但报错已给出修法；
   放行的代价是不可用状态一直留在库里、到接入那刻才炸。
   真实上游名不受限——配映射 `claude-opus-4-8` → `glm-4.6` 即可。
3. `tools.rs::desktop_model_names_warning` —— 接入侧**兜底强警告，不阻断**（对齐 cc-switch，
   保留「先接入、再回头调映射」的用法）。全不合规时措辞升级为「写进去了但用不了」。
   注意：不合规名必须**原样写进档里**，不能过滤——过滤会让 `effective` 变空、撞上
   「空列表 → 报错」分支，把「照写」变成阻断。
4. `lib.rs::apply_tool_config` —— 另记一条 `error` 事件进运行日志（接入弹窗一关就没了，
   而这问题往下排查很久，需要留痕）。用 `error` 而非新增 `warn` kind：前端 `LogsPage`
   的分组映射是穷举的，且这条本质是「配置不可用」。

## 十、FR-025 开机自启动：从「静默失效的开关」到真接线

### 原来错在哪（这是个比「功能没做」更坑的状态）

`AppSettings.auto_start` 字段存在、设置页开关能点、值也确实落进 `config.json` ——
但后端**从无任何代码去注册系统自启动项**（`lib.rs` / `store.rs` 里搜不到该字段的消费点）。
用户打开开关看起来生效了，重启后什么也不会发生，而设置页下次打开仍显示「已开启」。
「看起来能用但什么都不做」比明确标注「开发中」（主口令、导入导出那两处的做法）危险得多。

### 修法

接官方 `tauri-plugin-autostart`（Windows 走注册表 `Run` 键，跨平台差异由插件适配），
没有自己撸注册表——项目虽是 Windows-only，但注册表边界情况（组策略锁定、
MSIX 沙箱、路径带空格）插件已经处理过，自己写等于重造且更易漏。

三个接线点：

1. **`save_settings` 命令里同步系统状态**（`sync_autostart`）。顺序是**先动系统、成功后才落盘**
   —— 反过来会留下「配置说开、系统实际没开」的不一致，而用户下次看到的是开着的、无从察觉
   （与 `save_secret` 先写密钥再置 `has_secret` 同一道理）。失败**上抛**而非只记日志：
   注册可能因权限/组策略失败，静默吞掉又回到「以为开成了」。
2. **启动时状态对账**（`setup` 内）。`config.json` 与系统实际注册项可能背离——用户手动改过
   注册表、用清理工具删过启动项、或**从旧版本升级**（旧版只存字段、从不注册，所以老用户
   开关是开着的但系统里没有项）。以配置为准把系统拉回一致，让开关「所见即所得」。
   对账失败只告警不阻断启动（功能降级，应用照常可用）。
3. **随系统启动时最小化到托盘**（需求原文要求）。判据是启动参数含 `--autostart`
   （`AUTOSTART_FLAG`，注册自启动项时带上），**不是**「`auto_start` 配置为真」——
   后者在用户手动双击时同样成立，那时把窗口藏起来会让人以为程序没启动、反复双击。

### 前端顺带修的一处

`SettingsPage` 的 `update()` 原先乐观更新 UI + 失败弹 toast，但**不回滚开关状态**。
对「后端要动系统」的设置（自启动是第一个这类设置）这就是致命的：系统侧失败了，
UI 却仍显示已开启。已改为失败时 `setSettings(prev)` 回滚。

### 验证边界（诚实说明）

- 单测覆盖的是**参数判据**（`launched_by_autostart`）：精确相等而非 `contains`，
  故 `--autostart=1` / `autostart` / `--mcp-stdio` 都不误命中。已用故障注入
  （把判定改成 `contains("autostart")`）验证该测试确实会变红。
- **注册表写入本身没有自动化测试**，也无法有：`autolaunch()` 需要真实 `AppHandle`，
  且会往当前用户的 `HKCU\...\Run` 里真写。这部分只能真机验证（见下）。
- 开发模式（`tauri dev`）下注册的是 `target/debug` 的 exe 路径。**别在开发模式下测这个开关**
  —— 会往注册表塞一个指向 debug 产物的启动项，卸载后残留。要测就用安装后的正式产物。

### 真机验证步骤（加进第八节清单）

1. 装正式包 → 打开设置页 → 开「开机自启动」
2. `reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v SynaRoute`
   应能查到，值为安装后的 exe 路径 + `--autostart`
3. 重启系统 → 应用应自动起来且**窗口不弹出**、只在托盘
4. 关掉开关 → 再查注册表，该项应消失

### 12.5 本轮的两条教训（都是我自己犯的，写下来防复发）

**教训一：`grep -c` 返回 0 会中断 `&&` 链，让「没有」看起来像「没查」。**
我一串 `&&` 拼的核对命令在第一个 0 处静默停住，导致我据此下过一个**错误结论**
（说 `backfill_usage_for_collapsed_event` 在生产路径从未被调用，还围着这个错前提
做了一整轮分析）。实际它早在 `e486706` 就已接进 `proxy.rs`。
核对存在性时用 `|| echo 0` 兜住，或改用循环逐项打印。

**教训二：从并行测试的 CI 日志抓测试名会漏。**
我第一次用 `grep -E '^test .* ok$'` 只捞到 549 个名字，而 run 报告 579 —— 并行输出
同行交错吃掉约 30 行，据此算的差集虚高。改用 `grep -oE 'test [\w:]+ \.\.\. ok'`
抓到 579 个唯一名、与报告数吻合后，差集才可信。
**判据：抓出来的条数必须等于 `test result` 里报的数，不等就说明解析漏了。**

### 13.4 三条教训（两条是关于「验证方法本身」的）

**教训一：我的修复本身也得按同样标准自审一遍。**
第一版 created 标记只看 `path.exists()`，漏了「二次接入」：首次凭空新建后文件已存在，
第二次 `apply`（如改端口）就会把 SynaRoute **自己写的内容**当原始快照拷进 `.bak`，
于是 marker 与 `.bak` 同时存在，而 `restore_one` 先看 `.bak` → 把「删除」误判成
「还原成中间版本」，凭空新建的文件从此永远回不到「不存在」这个真实原状。
判据必须是「两把锁都没上过才可能上锁，且互斥」。
`repeated_apply_after_created_from_nothing_does_not_fabricate_a_backup` 钉住它。

**教训二：故障注入没生效时，测试通过什么都证明不了。**
我用 Python 字符串替换注入，因 CRLF 静默 no-op —— 测试跑的其实是**原始已修复的代码**，
却显示「通过」，我差点据此说「防线已验证」。改用 `sed` 按行号注入，并在跑测试**之前**
用 `grep -c '\[FAULT\]'` 确认注入数为 1。
配套坑：`grep -c 'FAULT'` 会命中 `ANTHROPIC_DEFAULT_*` 等无关串（我一度看到 24 条
以为注入失控），**必须精确匹配 `\[FAULT\]`**。

**教训三：测试失败时要先怀疑实现 —— 但要能分清「断言写错」和「注入点失效」。**
`desktop_restore_is_atomic_on_midway_failure` 原先靠「写非法 JSON 让
`write_deployment_mode` 解析失败」注入故障，而新增的 created 分支**直接删文件、
不再解析 JSON**，注入点失去着力点。这属于**技法过期**，不是断言错 ——
改法是在用例里预建两个 config 走 `.bak` 分支（断言一字未动），另加
`desktop_restore_deletes_configs_it_created` 覆盖新分支。
**「技法过期」绝不能成为放宽断言的借口。**

**教训四：提交说明必须是代码的镜像，不能是「打算做的事」。**
`878752e` 的说明里写了 P3「抽出 `restore_client_config_keeping_mcp`、三条停止路径共用」，
但那次提交对停止路径**一行没改**，全仓也没有那个函数 —— 说明描述的是我脑子里的计划，
不是磁盘上的代码。用户复查「使用官方操作合理性」时正是靠读代码戳穿了它。
**判据：写完提交说明，对每条"已修"用 `git show <sha> -- <file>` 或 `grep` 确认那段代码真在这次 diff 里；
搜不到就删掉那句，别让说明替代码许愿。** 停代理与 MCP 是两条独立的路（用户拍板），
本次才真正落地：`restore_client_config_keeping_mcp` 抽出，界面停止 / 托盘停止 / 切官方三条
共用，`stopping_proxy_restore_does_not_touch_mcp_registration` 钉住「还原不动注册记录」。

### 15.5 悬浮球「压根看不见」：现状与下一步

**另有一条我自己代码里的确定错误（尚未修）**：球的停靠位置是按**展开态尺寸**

1. **临时关掉 `transparent(true)` + 恢复 `shadow(true)` 打一版**。透明 + WebView2 有一类

2. app 运行中按父 PID 数 webview 进程（判据见上），区分「WebView 没起来」

3. 再走 §14.6 的 `diagnose()` 那条（`URL=` 字段分辨「窗口没建起来」vs「前端没加载对」）。

### 15.6 本轮教训（三条，都关于「我的判断/手段本身出错」）

1. **判据清单与实施记录必须对账**。虚拟滚动被当成待办至少两次（本轮又一次，
   动手前才查到 docs/16 §8 写着「刻意不做」）——根因是 §4 的复选框一直空着，与 §8 矛盾。
   已作废那三条并指向 §8。清单不对账，它就会持续生产假待办。
2. **本机 `python` 是 Windows 应用商店的占位存根**：存在、`--version` 无输出、退出码 49，
   用它改文件**静默不生效**。我据此一度断定「并发去重那条测试没测到东西」，
   实为编辑从未落盘。**改文件别走 python 一行流**；故障注入后先 `grep` 确认目标行真变了
   再看测试红绿 —— 否则「测试没红」既可能是测试无效、也可能是注入无效，结论完全相反。
   （上一轮是 `python3 - <<'PY'` 的 stdin 没接上，同一类，这是第二次。）
3. **查「配置值自己变了」之前，先确认没有旧实例在跑**。我一度以为置顶值有别的写入点,
   受控实验（杀净实例 + 置 false + 每 2s 采样 16s）证明干净起点下一直是 false ——
   那次翻转是**残留旧实例把内存里的陈旧值刷回磁盘**，即本仓记过的「内存领先磁盘」。
   <br>另：我先前报过一次「值不会自己翻成 true」，那个结论**是错的**（当时主窗口可见、
   没走到显示路径）。同一现象要在**会触发写入的路径上**复现才算验过。

### 15.7 本轮修掉的一条 P1：批量保存静默关掉悬浮球开关

前端 `prefs.ts` 白名单里从来没有 `floatingWidgetEnabled` /
`floatingWidgetAlwaysOnTop`（`types.ts` 注释也这么写），但 Rust 的 `UserPrefs`
**两个都有**且 `apply_to` 会赋值 → 每次 `saveSettings`（切主题、切语言、改任何设置）
JSON 都缺这两个键 → `serde(default)` 补 false → **把用户开着的悬浮球静默关掉**。

与自启动那条 P0 同类（那条是切主题把**关掉的**自启动装回系统），方向相反。
注意 `floating_widget_enabled` **本来就在这条坏路径上**，本轮加第二个字段只是放大了它。

修法：从 Rust `UserPrefs` 移除这两个字段（结构上让批量保存碰不到）。
回归测试 `batch_save_settings_never_touches_side_effect_toggles` 用**前端真实会发出的
那种 JSON**（只含 `theme`、其余全缺）走完整往返，断言三个带副作用的开关都不被动。
已故障注入验证（把赋值加回去即变红）。

**判据推广**：`UserPrefs` 的字段集必须与 `src/lib/prefs.ts` 的 `pickPrefs` 逐字段对齐。
往 `UserPrefs` 加字段前先问「前端白名单里有吗」——没有就不该加。

### 14.8 重装电脑前**必须先做**的一件事（不可逆）

**`secrets.enc` 由 DPAPI 绑当前 Windows 账户，重装后解不出来** —— 即便同一台机器、
同样的用户名也不行（账户 SID 变了）。直接把文件拷走是**没用的**。

→ **重装前用应用内的「配置导出」，勾选含密钥，设一个口令。**
含密钥导出走 Argon2id + AES-GCM 用**用户口令**重新加密（`crypto.rs`），
正是为跨机器这个场景设计的。**漏了这一步，所有 API Key 永久丢失，无补救路径。**

其余注意：
- 端口 / 日志目录 / MCP 注册态属**本机运行态**，刻意不随导出走，新机器需重配。
- `.codegraph/` 不必搬，新机器重新 `codegraph init -i`。
- 环境重装清单见 [docs/18-重装系统开发环境清单.md](docs/18-重装系统开发环境清单.md)
  （9 项各带可证伪判据；结论之一：**装了 Git 就自带 gpg**，不必单装 GnuPG）。
- PATH 里 `node_global` 必须是**绝对路径**（`F:\nodejs\node_global`）。
  曾因写成裸相对路径导致 `claude` 命令整个消失。
- 本文档里的绝对路径都是**旧机器实测值**，新机器会不同。

### 14.9 三条教训（两条是关于「我的探测手段本身出错」）

**教训一：判断产物里有没有某段代码，不要用 `grep` / `strings` 搜中文串。**
本轮实测：`grep -c` 在 exe 上给出自相矛盾的结果（「失败」= 1 而「成功」= 0），
`strings -a` 更是连 `悬浮窗同步` 都返回 **0** —— 而那个串是**这个二进制自己写进日志的**，
必定存在。两种手段都匹配不到产物里的 UTF-8 中文。
**可靠判据是时间戳对比**：产物 mtime **11:17** 早于提交时间 **11:37** → 必不含该代码。
**推论（更普适）**：拿不准探针可靠不可靠时，先用一个**已知为真**的样本试一次；
连它都探不到，说明是探针坏了，不是结论成立。

**教训二：`tauri-build` 不为图标发 `cargo:rerun-if-changed`。**
换了图标重新构建，产物里还是旧图标，**编译期零提示**。
修法是在 `build.rs` 里对 5 个图标文件显式声明依赖（`icon.ico` / `icon.png` /
`32x32.png` / `128x128.png` / `128x128@2x.png`）—— 这是根因修复，不是清 target 了事。

**教训三：方案文档写的是「打算做的事」，落点要靠实测找。**
docs/16 的 PERF-2 原写「给 `KeyCard` 包 `memo` + `useCallback`」，
实测**无效** —— `k` 这个 prop 来自 IPC，每次轮询都是新对象，默认浅比较恒失效。
真正的落点在**数据层**：新增 `src/lib/reuseUnchanged.ts`，按 id 比对，
内容未变就**复用旧对象**（引用不变，`memo` 才生效），同时检测「内容相同但位置变了」
（排序变更）以免误判。配 10 条测试 + 双向故障注入验证。

> 本轮我自己写的测试出现过 **3 种假绿**，都已修：正则按未压缩 CSS 写（产物是压缩的，永不匹配）、
> `toContain` 子串比对被 `-TYPO` 后缀骗过（`bg-warning/8-TYPO` 也含 `bg-warning/8`）、
> 断言「首次加载数组同引用」（不可能成立）。
> **凡「防静默失效」的测试，必须做故障注入双向验证：去掉防线后测试必须变红，且真的跑过一遍。**

### 17.1 教训：「按窗口算」这个直觉是错的

## 十六、输出 token 上限透明化（2026-08-14 代理侧 / 08-15 大脑聚合侧，用户定调）

> 本节分两轮：16.1~16.3 是**代理转发**侧（08-14），16.4 起是**大脑聚合**侧（08-15）。
> 两轮是同一条原则的延伸：**SynaRoute 不替模型决定回答能有多长。**

### 16.1 结论先行

**代理转发不再从 `KeyParams.max_tokens` 补写 `max_tokens` / `max_output_tokens`。**
客户端（Claude Code / Codex）自己的请求带了输出上限就尊重并按需做协议字段转换；没带就不给，
由客户端 / 上游自己的默认行为决定。故障转移到哪个 Key 都不能改变同一次请求的输出上限。

用户给的边界是：**参考 cc-switch，代理只干代理的活；SynaRoute 比 cc-switch 多的是自动故障转移，
不是替客户端决定输出长度。** 注意这里的「代理只干代理的活」指**请求参数透明性**，
不是拆代理启停与客户端配置接管 —— 曾误读成后者，已被用户明确否定，勿再沿错方向改。

### 16.2 与 2026-08-10 P1 修复的关系（别误判成回归）

§13.1 的 P1「Key 上配的采样参数从不生效」当时把 temperature / top_p / max_tokens 三项
一起接进 `proxy.rs::apply_key_params`。其中：

- temperature / top_p：客户端未给时仍从 Key 补，修复保留；
- max_tokens：**有意撤出代理注入**，只留给 `aggregate.rs` 的大脑聚合请求使用。

> ⚠️ **本小节是 08-14 当时的中间状态，已被 08-15 那轮取代**：那时 `max_tokens` 还留给
> 大脑聚合读；08-15 之后**没有任何请求路径读它**，字段纯为兼容旧配置而保留。
> 现行契约看 §16.4 起与 docs/01 FR-005，不要照这一段去恢复「聚合读 Key 值」的行为。

### 16.3 不变量与判据

- 实现：`proxy.rs::apply_key_params` 只处理 temperature / top_p，函数内刻意没有 max_tokens 分支；
- 回归测试：`key_max_tokens_is_never_injected_by_proxy` 覆盖三个可能字段名；

验收契约的完整矩阵见 docs/01 FR-005。

### 16.4 大脑聚合侧（2026-08-15）：也不设固定上限

用户追问「大脑聚合为什么还有 max_token 限制」，并定调**大脑聚合也不该设上限，
否则拿不到完整回答**。原实现三条路径（成员、汇总者、决策者）一律
`key.params.max_tokens.unwrap_or(4096)` —— 长回答在 4096 token 处被切掉，
而症状（模型答一半）指向的是上游，没人会想到是本地那个默认值。

**新语义**（实现在新模块 `src-tauri/src/upstream/budget.rs`）：

| 上游协议 | 请求体里的输出上限 | 依据 |
|---|---|---|
| OpenAI Chat / Responses | **不发**该字段 | `max_tokens` / `max_completion_tokens` / `max_output_tokens` 都是可选项 |
| Anthropic Messages | 必须发，取 `min(contextWindow − 输入估算 − 1024 余量, 模型最大输出)` | 该字段**协议必填**，省略直接 400 |

### 16.5 ⚠️ 上下文窗口 ≠ 最大输出（审计修出的 P1，别再只按窗口算）

首版实现只算 `contextWindow − 输入`，被全链路审查（§17）判为 **provider-break**：
内置预设给 Claude 4.5 写的是 200k **上下文窗口**，而它的**最大单次输出是 64k**。
短 prompt 时算出近 199k 的 `max_tokens`，官方与严格中转直接 400 —— 请求根本发不出去。

故现在**两个钳制同时生效**，缺一个都是缺陷：

```text
max_tokens = min(窗口剩余, 该模型最大单次输出)
```

模型最大输出表在 `budget.rs::CLAUDE_MAX_OUTPUT_TABLE`，按家族片段 `contains` 匹配
（`claude-*-4-5` = 64k、`claude-3-7` = 64k、`claude-3-5` = 8192、`claude-3` = 4096）。
**用 `contains` 而非全等是刻意的**：第三方中转普遍加前后缀
（`anthropic/claude-sonnet-4-5`、`claude-3-7-sonnet-20250219`），全等会把它们全判成未知、
从而拒掉本项目主场景。表的顺序**从新到旧**，`claude-3-7` 必须排在 `claude-3` 前面。

### 16.6 数据缺失时的三级处理（不一刀切拒绝）

| 情形 | 行为 | 理由 |
|---|---|---|
| 缺 `contextWindow`，但模型名可辨识 | **照常参与**，取该模型最大输出 | 真实 Claude 窗口都 ≥ 200k、输入通常远小于它，这个值实际安全。拒掉会误伤「手填模型名 / 刚拉取列表」这类完全可用的常见配置 |
| 模型最大输出**无法辨识** | 报可行动错误，不发请求 | 填大可能 400、填小就是静默截断，两边都是赌 |
| 输入（含余量）已占满窗口 | 报可行动错误，不发请求 | 首版硬塞最小值让上游报 context overflow —— 既烧额度又把本地已知的原因藏起来 |

### 16.7 判据与不变量

- **输入 token 估算取上界**：ASCII 按 4 字符/token，**非 ASCII 逐字符算 1 token**。
  首版用「一律 chars/2」被审查判为**低估** CJK（注释自己写的是 1~1.5 字符/token，
  除以 2 等于 0.5 token/字符）—— 低估会让 `max_tokens` 偏大而超窗口 400。
  低估的代价（400）比高估（少留一点输出空间）严重得多，故整体偏保守。
- **图片 base64 不按文本计**：那是传输编码，不是模型看到的 token。首版把整条消息
  `to_string()` 后按字符数估，一张允许的 5MB 图片（base64 后约 670 万字符）会被估成
  数百万 token，明明有效的视觉请求被本地判成「没有输出空间」。现走
  `estimate_json_tokens_without_image_transport`：识别 Anthropic 的 `source.data`
  与 OpenAI 的 `data:image/...` URL，每张替换为固定视觉占位。
- Anthropic 预算**每轮重算**（`session.estimated_input_tokens(&tools)`）：工具循环每轮重发
  整份历史，沿用首轮估计会在第 N 轮把 `max_tokens` 算得过大。断言是「后一轮**不大于**前一轮」
  —— 注意不能断言「严格小于」：两轮都被 64k 能力上限钳住时它们相等，那是正确行为。
- **跨协议路径必须走同一套计算**：`convert.rs` 的两个转换器**不再**凭空造 4096
  （`openai_to_anthropic` / `anthropic_to_openai` 都改成「源有才带」），
  Anthropic 必填字段由 `proxy::ensure_anthropic_output_budget` 在**转换之后**补 ——
  只有那里同时握有 `ProviderKey` 和已解析的 `real_model`。转换器里补必然只能瞎填。
  客户端显式给的值**优先**，不被能力计算覆盖。
- `KeyParams.max_tokens` 现在**没有任何请求路径读它**，仅兼容旧配置（字段、批量 IPC、UI 都留着，
  文案已标注不生效）。删字段要做配置迁移，收益不抵风险。
- 故障注入双向验证：把 `unwrap_or(4096)` 加回聚合路径后三条测试同时变红
  （OpenAI 那条的失败信息里能看到混进请求体的 `"max_tokens":4096`），随后已撤销。

### 16.8 本轮未做

- **真机验证**：只用单元测试的请求体断言，没有真实跑一次聚合确认长回答不再截断
  （尤其 Anthropic 侧那个动态值会不会被某些中转商拒绝）。
- **模型最大输出能力仍是代码内置表**，用户无法在 UI 里为第三方模型补这项。
  认不出的模型会被拒 —— 若真机遇到，正解是给 `ModelInfo` 加 `maxOutputTokens` 字段 + UI，
  而**不是**回退某个默认值。
- 可观测性两条 P1 未修（见 §17.3）。
- 未提交、未 bump 版本、未出包。

## 二十、更新签名私钥泄露：定性、补门与处置（2026-08-23 定性 / 08-27 处置完毕）

> **本节已全部闭环**，含 20.5 原先那 4 项待决策。读 20.5 可以一次看到四条结论
> 与各自的判据；其中「不清洗 git 历史」那条的理由是量化的（5 个 fork），
> 不是偏好 —— 想反转它先看那节末尾的反转判据。
> 本节起因是一次产品视角的功能盘点，顺带撞出了这条。

### 20.1 结论先行

2026-08-14 的提交 `29b9257` 把 Tauri 在线更新的**签名私钥连同它的解密口令**一起写进了
`GITHUB_SECRETS_SETUP.md` 的正文，推上**公开**仓库（`EngineeMoMo/SynaRoute`，
实测 23 star / 5 fork），2026-08-23 才发现 —— 在仓库里躺了 9 天。

后果与 CLAUDE.md 自己写下的那段警告逐字吻合：拿到私钥的人能签出「验签通过」的伪造更新，
而客户端二进制里嵌着配对公钥、会把它当正品安装 —— 而这个软件里装着用户全部的 API Key。

**但泄露的不是现役钥。** 这一点极易判错，我第一遍就judged错了，务必看 20.2 那张表。

### 20.2 🔑 三把钥、两次换钥（**这张表是本节最重要的产出**）

`secrets/README.md` 原先只记了**一次**换钥，而实际发生过两次 ——
**漏记的那把恰好就是泄露的那把**，于是排查时第一反应必然是「泄露的是现役钥、必须紧急换钥」，
而那个结论会让你白白再甩掉一批用户。台账已补进 `secrets/README.md`：

| KeyID | 生效区间 | 覆盖的发布版本 | 私钥现在在哪 |
|---|---|---|---|
| `1F6689C022960775` | 初始 ~ 08-14 | ≤ v0.1.19 | `secrets/synaroute.key.gpg`（推断）；GPG 层能被泄露口令打开，里层 rsign 口令未知 |
| `DE14C6EC68286277` | `29b9257`（08-14）~ 08-16 | **仅 v0.1.23** | 🔴 **已连口令一起公开，永久失效** |
| `7A46ECB8087DE26F` | `983c333`（08-16）起 | v0.1.26 ~ 现在 | 只在 `~/.tauri/synaroute.key` 与 GitHub Secrets，**未泄露** |

**v0.1.23 的用户处境最坏**：他们收不到之后的正版更新（0.1.26+ 用新钥签、他们的客户端不认），
却**能**收到任何人用泄露钥签的伪造更新。这批人只能带外通知（README / 官网 / Release 说明）手动重装 ——
**没有**技术办法捞回来：`latest.json` 一个平台只能带一个签名，而老客户端问的是同一个
`releases/latest/download/latest.json`，给它签旧钥会让新版客户端全部拒收，净效果更差。

#### 怎么从密钥字节反查它是哪把（不必破口令）

```bash
npx tauri signer sign -k "<base64 私钥>" -p "<口令>" /tmp/probe.txt
```

拿到 `.sig` 后**base64 解两层**（tauri 把整个 minisign 签名文件又包了一层），
明文里 offset 2..10 就是 KeyID，**字节序是反的**。核对客户端认哪把公钥：

```bash
git show v0.1.23:src-tauri/tauri.conf.json | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>console.log(Buffer.from(JSON.parse(s).plugins.updater.pubkey,'base64').toString().split('\n')[0]))"
```

### 20.3 为什么已有的门没抓到（**本节的通用教训**）

当时 `npm run audit:release` 已经在跑，并且 CLAUDE.md 里明明写着「判据是机械检查，不是
『我记得没加』」。它照样漏了，原因是**判据存在 ≠ 判对了维度**：

1. 它按**文件名**判（`\.key$|\.pem$`）。密钥贴在 `.md` 正文里，文件名毫无异样。
2. **就算改成内容 grep `untrusted comment: rsign …` 也照样抓不到** ——
   `TAURI_SIGNING_PRIVATE_KEY` 的形态是「整份密钥文件再 base64 一层」，
   那句注释在文件里根本不以明文出现，第 15 行看上去只是一串普通 base64。
3. 它只在**发版时**跑。而泄露发生在一次 commit —— 于是密钥躺了 9 天。

还有一条自我作废的设计：`secrets/synaroute.key.gpg` 的立论是「密文可以公开，
因为口令只有我知道」，而那句口令就写在另一个 tracked 的 `.md` 里（实测能解开）。

### 20.4 已补的机械判据（已闭环，含故障注入）

新增策略门 `no-secrets-in-tracked-files`，实现在
[`scripts/lib/secret-scan.mjs`](../scripts/lib/secret-scan.mjs)。三条判据：

1. **私钥材料** —— 明文签名串 + **把长 base64 串解出来再匹配，最多解两层**
   （密钥文件第二行自身又是一层 base64）。这是核心判据，也是上面第 2 点的解药。
2. **签名凭据口令** —— 只认 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 这一小类标签，
   **刻意不泛化成任何 `password`**：本应用自己有主口令功能，泛化必然淹没在假警里，
   而一道会喊狼来了的门等于没有门。带**前向窗口**，因为泄露的实际形态是
   「标签 → 空行 → `**Value**:` → 围栏 → 值」，隔了 4 行。
3. **拿仓库里出现过的口令去试解仓库里的密文** —— 这次就是这么破的。

接线：`check-forbidden.mjs`（**每次 `npm run gates` 与 CI 都跑** —— 门必须在它能拦住的
那个时刻跑，不能只在发版时）+ `audit:release` 第二道 + 单独入口 `npm run check:secrets`。
判据本身的详细说明也进了 CLAUDE.md 的「质量门」一节，那里是策略门的正式清单。

两个设计细节，别改坏：
- 脚本里的签名串是**拼接**而成的，所以扫描器不会命中自己、**不需要任何白名单** ——
  白名单就是下一次泄露的藏身处。
- 测试夹具在临时目录**现造现删**，不入库，同理。

**故障注入 4 条全部验证变红、还原后全绿**：关掉 base64 解码 / `B64_MIN_RUN` 60→8 /
去掉口令前向窗口 / 去掉「围栏外只接受不含冒号的裸值行」那道假警防线。
另做过端到端：往仓库真放一个与当年逐字同形的泄露文件 → `check:secrets` 与 `gates` 都红并
逐条指位置，删掉即回绿。

⚠️ **注入时又踩了同一个坑**：有一条第一次注入**仍绿**。原先写成「run 下限 60 +
前缀下限 200」两个常量，把 200 改成 8 被 60 那道先挡住了 —— 那个 200 既是死数、
又制造了 60~199 长度的**盲区**。已收成单个 `B64_MIN_RUN`。

#### ~~B2~~ ✅ 日志按体积设上限（**已实现，2026-08-27，用户定调「滚动切分」**）

**两级上限，缺一级都不成立**：

| 级 | 常量 | 行为 |
|---|---|---|
| 单文件 | `FILE_MAX_BYTES = 16 MB` | 写满滚到 `2026-08-27.1.jsonl`、`.2.jsonl`… |
| 单日总量 | `DAY_MAX_FILES = 16`（= **256 MB/天**） | 越过配额时删**当天序号最小**的，形成滑窗 |

🔴 **只做滚动切分是无效的** —— 它把一个大文件变成很多个，磁盘占用一分不少。
而只做「写满即停」在排障时最糟：日志恰好在最需要的时刻消失，且用户不会知道。
选「保最近、丢最旧」是因为**开着原始日志的用户正在排障**，他要的是刚刚发生的事。
与 `LOG_RETAIN_DAYS = 30` 相乘得最坏 7.5 GB（连续 30 天跑满原始日志的极端值）。

**第 0 个文件刻意不带序号**（`2026-08-27.jsonl` 而非 `.0.jsonl`）：绝大多数日子只有一个文件，
而用户会直接 `tail` 它、冒烟脚本会遍历它、docs 里到处写着这个名字。序号只在真的滚动时出现。

🔴 **加滚动就必须同时改清理判据，这是一件事而不是两件**：
`cleanup_old_logs_in`（`store.rs:279`）原先是 `strip_suffix(".jsonl")` 再按 `%Y-%m-%d` 解析，
而 `"2026-08-27.1"` 解析**会失败** → **滚动出的分片永远不会被清理**。
那是个典型静默失效：保留期看着在工作，实际只管住每天第一个文件，
而磁盘占用这个方向**永不自愈** —— 正是本功能要解决的问题本身。
判据已收进 `log_rotate::parse_name`（单一事实来源，严格拒 `.0`/前导零/`events.jsonl`/
`2026-99-99.jsonl`，**删错文件比留着旧日志严重得多**）。

**11 条测试，8 条注入全部确认变红**：`parse_name` 退回旧判据 / 去掉体积判据 /
已写字节从 0 起（重启即重置上限）/ 恒用序号 0（重启后从头再滚）/ 配额删最新而非最旧 /
去掉配额 / 配额跨天计数 / **写线程改回裸 `write_all`**。

🔴 **最后那条注入只有源码级判据抓得住** —— 其余 10 条用例都直接构造 `OpenLog`，
把写线程改回裸写它们**照样全绿**，而那就是「体积上限完全不生效」这个缺陷本身。
同 `route_meta` / `lan_guard` 的 peer / `mcp::handle_http` 那三次：
**单元覆盖了组件 ≠ 覆盖了调用它的那条线**，而漏掉接线的表现恰恰是静默的。

**端到端实测**（`#[ignore]`，同 `perf_probe.rs` 的模式，手动跑）：
真写 16 MB → 第 0 个精确停在 16 MB、`.1` 分片生成。
上面那条源码级判据只证明「调用点在」，这条证明「跑起来真的会滚」。

⚠️ **用户可感的变化**：此前最大单日 38 MB 是**一个文件**，今后同样的量会分成 3 个
（16+16+6）。这是预期行为，但「日志目录里文件变多了」会被误当成异常，
故滚动与删除都落 `tracing` 一行（写线程持不到 `Store`，落不了事件 —— 那会成循环引用）。

`store.rs` 因此从 2956 行**降到 2938**，棘轮基线已同步下调（只准往好的方向动）。
