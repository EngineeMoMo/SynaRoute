## 二、P0：必须先修 —— 重复接入会冲掉「接入前备份」

**这是数据丢失级缺陷，触发条件很日常，优先于本文其余所有条目。**

### 定位

`src-tauri/src/tools.rs` 的 `backup_and_write_bytes`（约 1047 行）：

```rust
if path.exists() {
    if let Ok(current) = std::fs::read(path) {
        if current == data { return Ok(()); }   // ← 只有「逐字节相同」才短路
    }
}
if path.exists() {
    std::fs::copy(path, backup_path_for(path))?;  // ← 否则无条件覆盖 .bak
}
```

### 复现

| 步骤 | `.bak` 内容 |
|---|---|
| 首次接入 | 用户原始配置 ✅ |
| 改代理端口后再接入（内容变了 → 守卫不命中） | **已接入态 v1** ❌ |
| 点「还原」 | 拿回「已接入 v1」，**用户原始配置永久丢失** |

触发条件（任一即可，都很日常）：改代理端口、可服务模型列表变化、
MCP 注册时 exe 路径变化（升级换目录必然发生）。

### 影响面

- **CLI 与 Codex 会真的还原错** —— 它们的 `restore` 走 `restore_one(&path)`，直接从 `.bak` 读。
- 桌面端只是留误导性残留 —— 它的 `restore_desktop_at` 不读 `.bak`，
  走 `write_desktop_meta_clear_preferring` + `read_desktop_prev_applied_id`。

### 现存测试为何没抓到

`tools.rs` 的 `repeated_apply_does_not_clobber_backup`（约 2347 行）**只覆盖「内容相同」那一种**，
所以它一直是绿的。改端口/改模型/换 exe 路径这三条真实路径都绕过了它。

### 实证

本机 `%LOCALAPPDATA%\Claude-3p\configLibrary\_meta.json.synaroute.bak` 里存的是
`{"appliedId":"…000053796e61","entries":[{"id":"…000053796e61","name":"SynaRoute"}]}`
—— **已接入态**，不是接入前的 cc-switch 态。

### 建议修法

1. `.bak` **首写即锁**：`backup_path_for(path)` 已存在时不再覆盖。
2. `restore` 成功后**删掉 `.bak`**，让下次接入重新抓一份新鲜的接入前快照。
   （副作用：第二次还原会返回「无备份，无需还原」—— 这是准确的，可接受。）

### 验证判据（必须是可证伪的）

新增测试覆盖「**内容变化**的重复接入」：

```
写入用户原始内容 → 接入 v1（.bak = 原始）
→ 接入 v2（内容不同）→ 断言 .bak 仍是原始，而不是 v1
→ restore → 断言拿回原始内容
→ 断言 .bak 已被删除
```

改完务必先把测试跑成**红**（临时还原旧逻辑），确认它真能抓到，再修成绿。

`config.json`（Key 的名称/base_url/映射等元数据）是普通 JSON，可以搬。

## 六、判据来源与取证方法（可复现，别再靠猜）

本轮所有关于「客户端到底认什么字段」的结论，都来自**反查客户端二进制**，不是文档推测。

### Claude Code CLI（`claude.exe`，本轮版本 v2.1.219）

位置：`%LOCALAPPDATA%\Claude-3p\claude-code\<版本>\claude.exe`（约 265MB，内含打包后的 JS）

分块搜字节串定位，再 dump 上下文：

```bash
node -e '
const fs=require("fs");const f="claude.exe";
const fd=fs.openSync(f,"r"),size=fs.statSync(f).size;
const n=Buffer.from("CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY");
const CH=1<<24;let pos=0,prev=Buffer.alloc(0);
while(pos<size){const len=Math.min(CH,size-pos);const b=Buffer.alloc(len);
 fs.readSync(fd,b,0,len,pos);const hay=Buffer.concat([prev,b]);let i=0;
 while((i=hay.indexOf(n,i))!==-1){console.log(pos-prev.length+i);i++;}
 prev=b.slice(Math.max(0,len-n.length));pos+=len;}'
```

已确认的关键事实（写代码时的判据）：

- `kn()`（getAPIProvider）只有在 `wy()`（即 `Ot.gatewayAuth` 已设）时才返回 `"gateway"`；
  `gatewayAuth` 仅由 `CLAUDE_CODE_USE_GATEWAY` + `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`
  或企业 `enterpriseGateway` 设置。**SynaRoute 不写 USE_GATEWAY，故 CLI 走的是 `firstParty` 分支。**
- 因此模型发现走的是 `BIc()`/`GIc()`/`uGr()`（源码内叫 gatewayDiscovery），条件为：
  `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` 为真 **且** `kn()==="firstParty"`
  **且** 非官方 anthropic base url **且** `ANTHROPIC_BASE_URL` 已设。
  它 `GET {base}/v1/models?limit=1000`，**超时仅 3000ms**、`redirect:"error"`，
  校验 schema 是 `{id: string, display_name?: string}`（`.optional()` 不接受 `null`），
  并按 `/^(claude|anthropic)/i` 过滤 `id` —— 这就是 `to_gateway_model_id` 要包
  `claude-synaroute-` 前缀的原因。
- bool 型环境变量的真值判据 `Yt()`：`["1","true","yes","on"]`。
- **claude.exe 内嵌了一份官方 gateway 协议规范全文**（本轮在 offset ≈ 258929000 附近）。
  错误信封形状、status→`error.type` 对应表、`/v1/models` 返 404 即干净回退、
  `/managed/settings` 的 404 与 `200 {}` 语义不同、`/v1/{metrics,logs,traces}` 返 404
  会让 exporter 每次 flush 记错误、「Don't buffer SSE on the stream:true path」
  —— 全部出自这份文档。**改代理行为前先搜出来读一遍。**
