## 一、总体结论

**架构是合理的，成熟度明显高于同规模的个人项目——但它的成熟度是「补丁式成熟」，不是「结构式成熟」，且已走到当前结构能承载的上限。**

**决策质量很强。** 三个「选错了会长期流血」的岔路口都选对了，且每处旁边都留了「为什么不那么写」的根因注释：

- 非流式协议转换用 Chat Completions 中枢，把 N×M 压成 N+M（`upstream.rs:2309`）
- `mutate_and_persist` 的失败回滚走**磁盘对账**而非内存快照覆盖（`store.rs:404`）
- 密钥保护模式的事实来源定在 `secrets.enc` 的 `master` 头部，而非可被前端旧快照覆盖的 settings 字段（`secret.rs:103`）

这种「记录否决了什么」的注释密度在同类项目里属于前 5%。加上每条安全防线都做过故障注入双向验证的纪律，这是个可以继续在上面加功能的底子。

**短板高度同构：正确的抽象只覆盖了一半，另一半靠「人记得住」在兜。**

| 抽象 | 做对的一半 | 没覆盖的一半 |
|---|---|---|
| 协议转换 | 非流式 N+M 中枢 | 流式是 6 个手写有向方法（1023 行 21 字段单结构体），已能力漂移 |
| 配置落盘 | 10+ 处走 `mutate_and_persist` | **12 处裸 `persist()`**，而文档声称「仅剩 2 处」 |
| settings 防护 | 4 字段 `mem::take` 黑名单 | `auto_start` 落在名单外 → 已发生过 P0 |
| 鉴权头 | `apply_auth` 统一入口 | `anthropic-version` 三处各自补，已分叉 |
| 日志开销 | `downstream_body` 有 `req_log` 守卫 | 另两处无条件 pretty-print |

**20 条问题里有 7 条根因是同一件事。** 这解释了为什么 docs/14 必须写那么长——它在替结构做本该由类型系统做的事。也预示着加第 4 个客户端或第 4 种协议会把这个成本一次性引爆。

**本轮无 P0**：未发现数据丢失、密钥外泄或可稳定复现的功能失效。

## 二、设计得好的地方（勿在重构中弄丢）

1. **非流式协议转换的中枢归一**（`upstream.rs:2309`、`:2364`）。3 协议本需 6 个有向转换，实际用 6 个「单边」函数覆盖，加第 4 协议只需 4 个。`if from == to { return }` 明确规避 Responses→Chat→Responses 往返丢信息。

2. **`mutate_and_persist` 把教训固化进抽象本身**（`store.rs:404-425`）。闭包 Err 与 persist Err 两条路径都走 `rollback_from_disk`，注释写明「不用内存 snapshot 覆盖以免吞并发写者已提交的变更，也不依赖闭包契约」。有专测钉住（`store.rs` 的 `rollback_from_disk_reconciles_to_committed_disk_state`）。

3. **密钥保护模式的事实来源定在被保护的数据旁边**（`secret.rs:103`、`:37-49`）。两模式密文分存 `entries`/`boxes`，「在哪个 map 里」本身即是「这条是哪种密文」的答案，迁移中断也无需靠猜。

4. **三个整库迁移的编排是教科书级的**（`secret.rs:241/315/367`）。取两个 map 的并集逐条解密，`Ok(None)` 显式返 Err 而非跳过（注释点明「继续走下去会在 `mem::take` 时静默丢弃那条密文」）→ 备份 → 写盘 → 失败回滚内存。

5. **KDF 参数随库落盘而非硬编码**（`crypto.rs:101-113`），且刻意拆出「长驻密钥」第二组 API：解锁派生一次、各条只做 AES-GCM。这个性能判断在动手前就做对了。

6. **失败判定表比设计文档更准确**（`proxy.rs:1571`）。把 400/429/5xx 全部排除出熔断、只留 401/403/404/422，并附实测依据（68 条失败近半是空探测与自身转换 bug）。配套 `is_contentless_probe` 在代理侧直接挡回空探测，从源头掐断放大链。

7. **流式切换点选得准**（`proxy.rs:1136-1151`、`:1066`）。先 `send()` 探状态码、非 2xx 才切 Key，2xx 后不再切换（避免向下游吐重复内容）；同协议 `bytes_stream()` 零缓冲透传；刻意不设总超时以免掐断长回答。

8. **两处写放大已被主动挡住**（`store.rs:829-846`、`health.rs:126-138`）。`update_health` 只在 status/fail_count/breaker_until 变化时落盘，配合 `record_live_success` 的 fresh 判据，**稳态高频转发的成功路径完全不触发磁盘写**。这是热路径上最值钱的优化。

9. **`persist` 明确「先序列化、放锁、再阻塞落盘」**（`store.rs:447-460`）。注释交代了 parking_lot 写者优先会饿死后续转发读者的机理。

10. **`.bak` 首写即锁 + 还原后删**（`tools.rs:1284`、`:1351`）。注释记录了为什么「内容相等」守卫不够（改端口/改模型列表/升级换 exe 路径三条日常路径都会绕过它）。

## 三、问题清单

### P1（用户可感知或结构性风险）

#### P1-1 故障转移循环没有整体截止时间

- **证据**：`proxy.rs:611`（循环起）至 `:827`；非流式超时 `:1410`；流式 `:1110-1113` 注释明说不设总超时。候选数 = 该分类启用 Key 总数（`health.rs:172-180` 全部熔断时返回全部 Key）。
- **影响**：6 Key + 上游整体抖动时单请求最坏 **180 秒**才返 529。客户端早已超时重发，代理侧「僵尸链」仍在打上游、烧额度、写日志。`ALL_FAILED_SHORT_CIRCUIT_MS`（`proxy.rs:61`）只挡得住第一条链**走完之后**的重发，挡不住这 180s 内涌入的并发链各自走满全程（gate 要等第一条链走到 `:863` 才武装）。
- **方案**：① 进循环前算 `deadline = Instant::now() + overall_budget`（新增设置项，默认 90s）；② 每轮开头判 `remaining < MIN_SLICE(5s)` 则 break；③ `remaining` 传进 `forward_to_key`，`.timeout(key_timeout.min(remaining))`；④ 流式**只对 `send()` 探头阶段**套 timeout，**不掐已建立的 SSE 流**；⑤ 预算耗尽走与「全部失败」相同的 529 + `arm_gate`；⑥ gate 武装点提前到第一条链开始遍历时。
- **必测**：单 Key 慢于预算时返 529 而非等满 `key_timeout`；`proxy_fails_over_bad_to_good` 必须仍绿；流式已建立后不受预算影响。
- **M / 中风险**（落在最核心的转发循环上）

#### P1-2 12 处配置写入绕过 `mutate_and_persist`

- **证据**：`grep -n "self.persist()" src-tauri/src/store.rs` → `update_health:843`、`set_active_model:1029`、`set_active_effort:1052`、`set_proxy_port:1067`、`add_registered_category:1084`、`remove_registered_category:1099`、`clear_registered_categories:1113`、`set_mcp_port:1128`、`set_mcp_enabled_flag:1142`、`set_master_password_flag:1157`、`upsert_vendor:1184`、`delete_vendor:1200`。（`:414` 那处在 `mutate_and_persist` 内部，是正确的。）
- **影响**：落盘失败即「内存领先磁盘」，该方向**永不自愈**（mtime 自愈只认「磁盘比内存新」）。① `upsert_vendor`/`delete_vendor`：自定义厂商「保存成功」但重启消失；② `set_proxy_port`：粘滞端口丢失 → 重启后端口漂移、客户端里写的旧端口连不上（正是引入粘滞端口本要解决的问题）；③ `add_registered_category`：端口漂移时的批量重写漏掉该分类，客户端 MCP 指向死端口；④ `set_master_password_flag`：启动对账逻辑本身失效。这批字段全是「后端自管、前端无从察觉」的。
- **方案**：改走 `mutate_and_persist`（机械改法：`{ let mut cfg = self.config.write(); ...; } self.persist()` → `self.mutate_and_persist(|cfg| { ...; Ok(()) })`）。优先前 4 个有用户可见后果的。**闭包内不得再取 `self.config` 锁**（parking_lot 非重入会死锁）。每个补一条「落盘失败后内存与磁盘一致」测试（构造手法：把目标路径建成目录，`store.rs` 已有先例）。
- **`update_health` 保留直写**，理由见第六节。
- **M / 低风险**

#### P1-3 转发热路径在 tokio worker 上做同步阻塞磁盘 I/O

- **证据**：全仓 **零 `spawn_blocking`**。① 日志：`store.rs:295-335`，`LOG_LOCK`（`:323`）在 open+write 全程持有，`:302` 每条 `create_dir_all`；调用链 `proxy.rs:513/581/641/829/426`，任何成功转发至少 1 条。② 熔断落盘：`record_live_*` → `update_health`（`store.rs:829`）→ `persist()` → 序列化整份 AppConfig（实测 19692 字节）→ `atomic_write`（`secret.rs:552`）持 `WRITE_LOCK` 且含两轮各 6 次 `thread::sleep`（`:601`/`:621`），最坏累计约 **1.2 秒**。
- **影响**：阻塞的是 worker **线程**而非当前任务。一次 rename 撞上杀软扫描或企业管控机回退路径，该线程被占住 ~1.2s，期间**同线程上所有并发转发（含正在输出的 SSE）一并停顿**。表现为偶发无规律卡顿与 SSE 断流，不报错、日志只见延迟数字变大，极难归因。多 Key 故障转移时放大倍数 = 候选数。
- **方案**：① 日志改单写者异步——`SyncSender`（有界 4096，**满则丢弃并计数**）+ 写线程持长驻 `BufWriter` 与当前日期，跨天才重开文件，每 200ms flush；`write_log_to_file` 改 `try_send`。可退役 `LOG_LOCK`（单写者模型下 `store.rs:315-319` 担心的粘行天然消失）。② `record_live_*` 改内存标脏 + 后台合并落盘（熔断态可重建，丢最后几秒可接受）。
- **必做收尾**：`RunEvent::Exit` 里发 flush 并 join 写线程；**队列满丢弃必须计数并暴露**，否则是「静默丢日志」——本项目最忌讳的形态；加 `#[cfg(test)] fn flush_log_for_test()` 给现有日志断言插同步点。
- **M / 中风险**

#### P1-4 `AppError::Upstream(String)` 丢状态码，重试判定靠中文子串匹配

- **证据**：`error.rs:20`；`upstream.rs:617` 把**上游响应体前 400 字符拼进同一字符串**；`upstream.rs:370-382`：
  ```rust
  msg.contains("HTTP 502") || ... || msg.contains("连接")  // ← 会匹配到上游响应体里的文案
  ```
  调用点 `upstream.rs:420`（`text_completion` 重试循环）、`:1190`（`ToolSession`）。proxy 侧因拿不到结构化状态码，被迫另建 `StreamAttempt::HttpError`（`:1037`）与 `ForwardOutcome`（`:1259`）——同一件事两套表示。
- **影响**：上游返 **401/403** 且响应体含「请检查网络连接后重试」（中转商常见文案）或含 `HTTP 429` 字样（网关回显原始报文）→ 判为可重试，白跑 3 次并线性退避。聚合场景下每个成员各白等一轮，直接吃掉整轮 `total_timeout_ms`，用户看到「聚合超时/部分成员无结果」，真因只是一次鉴权失败。反向漏判同理：英文 `connection reset` 不含「连接」，本该重试的抖动被判死。
- **方案**：`Upstream { status: Option<u16>, msg: String }`（`None` = 连接层失败），`Display` **逐字保持**现有格式；`is_retriable_upstream_error` 改 `matches!(s, 429|502|503|504|529)`，删掉全部 8 条 `contains`；**同批改 `aggregate.rs:1090` 的 `mentions_4xx`**。加故障注入测试：「401 + body 含『请检查网络连接』」与「401 + body 含 `HTTP 429`」断言不可重试——**当前实现下这两条必红**。
- **M / 中风险**（改枚举形状会引发一批编译错误，但全部由编译器精确定位）

### P2（结构性负债）

#### P2-1 `upstream.rs` 7224 行混装 5 个职责

- **证据**：生产 4251 + 测试 2974（130 个测试平铺单个 `mod tests`）。`src-tauri/src/` 下无任何子模块目录，19 个 `.rs` 全平铺，也不存在 `src-tauri/tests/`。可清晰划出：模型发现（≈320 行）、用量观测（≈130）、**聚合会话 `ToolSession`（≈660，与代理转发完全无关）**、协议转换（≈1590）、流式翻译（≈1090）、HTTP 客户端与鉴权（≈90）。`health_probe` 也混在其中而项目已有独立 `health.rs`。
- **影响**：改一行（含只改注释）重编整个 7224 行编译单元；`ToolSession`（聚合）与 `SseTranslator`（转发）相邻，新人无法从文件名判断该看哪段——docs/14:134 那张表就是为此而写；任何两项并行改动都撞同一文件。
- **方案**：改 `src-tauri/src/upstream/` 目录 + `mod.rs` 重导出，**保持 `crate::upstream::X` 路径不变**（现有 43 处外部引用零改动：proxy 19 / aggregate 17 / agent_tools 3 / health 2 / lib 2 / model 1 / store 1）。子模块：`models.rs`、`usage.rs`、`session.rs`、`convert.rs`、`sse.rs`、`auth.rs`；`health_probe*` 移入 `health.rs`。**每个子模块带走自己主题的测试**，这一步把 2974 行单模块自然打散成 6 份。
- **注意**：私有辅助（`sse`/`sse_data`/`uuid_like`/`truncate_body`）被多段共用，需提 `pub(super)`；大量私有函数被测试直接调用，须与测试同批移动。**一次一个子模块提交，每次全绿再继续。**
- **L / 中低风险**

#### P2-2 请求构造两条路径逐字重复 38 行，鉴权头三份且已分叉

- **证据**：`try_stream_to_key`（`:1066`）与 `forward_to_key`（`:1354`）前置段落去空行去注释后**逐行比对 38 行完全一致**。鉴权头：`proxy.rs:1104`/`:1396` 用 `matches!(key.protocol, Protocol::Anthropic)` 且带 `anthropic-version`；`upstream.rs:4204` `apply_auth` 用 `is_openai()` 且**不带**，该头由 `:608`/`:1248`/`:1419` 三处各自补。另有 **11 处非穷举**协议判断会静默按「非 Anthropic 即 OpenAI」处理。
- **影响**：任何转发前置语义变更须同时改 2~5 处，漏一处即「非流式生效、流式不生效」——`anthropic-version` 的现状就是该风险已发生过一次的证据。新增协议（Gemini）时鉴权头会被静默套上 `Bearer`、客户端身份头套 Codex UA，不编译失败、不 panic，直接发错误的头，表现为 401 或 `client_restricted` 403，排查方向极易被误导到「Key 配错了」。
- **方案**：① 抽 `build_upstream_request(...) -> UpstreamRequest{url, payload, real_model, same_protocol}`；② 抽 `apply_upstream_headers(...)`，让 `anthropic-version` **只在一处**添加；③ `impl Protocol` 补**穷举 match** 的 `auth_scheme()`/`version_header()`/`client_identity()`/`supports_1m_beta()`，11 处调用点改读；④ **超时语义必须保持差异**——抽取只搬那 38 行，超时设置留各自调用点。
- **注意**：`apply_client_identity` 的头值是实测判据（`upstream.rs:4224` 注释记录「缺失即被判 `detected:unknown` 而 403`」），搬迁时**逐字保持**，加断言锁住现有两套头的完整集合。
- **M / 中低风险**

#### P2-3 Replace 导入清空 keys 却不清理密钥库

- **证据**：`store.rs:566-573` Replace 分支只动配置，**全程未触碰 `self.secrets`**；对照 `delete_key`（`:682-697`）在 config 落盘成功后显式 `secrets.write().remove()`。`reconcile_has_secret_flags`（`:616-649`）只遍历 `cfg.keys`，孤儿既不在遍历范围也无其它剪枝路径。
- **影响**：① Replace 导入后被删 Key 的**可解密钥材料仍完整留在 `secrets.enc`**，UI 无入口可见更无法删除。② 更隐蔽：日后导入「含同 id 但不含密钥段」的文件时，reconcile 的反向修复分支（`:640-643`）会读到孤儿密文把 `has_secret` 刷成 true，得到「新配置 + 旧密钥」的嵌合体 → 莫名 401 或用错账号扣错额度，根因埋在几次导入之前。
- **方案**：① `apply_imported_config` 返回被移除的 id 列表，由 `portable.rs:341` 接住清理，**时序必须「配置先落盘、再删密钥」**；② 清理须在 `guard.set()` 循环**之前**完成或跳过 `file_ids`，别误删本次要写入的同 id；③ 加 `prune_orphan_secrets()` 兜历史遗留——**这是破坏性操作**，先备份、只在非锁定态执行、**首版只记日志 + UI 提示条数由用户确认再删**。
- **M / 中低风险**

#### P2-4 健康探测串行遍历「全分类 × 全 Key」

- **证据**：`lib.rs:1388-1394` 三分类串行 await；`health.rs:192-195` 分类内 Key 也串行；`fast_timeout`（`upstream.rs:4193`）封顶 30s，其注释 `:4188-4190` **自己承认**「一个挂掉的慢 Key 会把整个分类的探测阻塞几分钟」。间隔 `lib.rs:1396` `interval.max(10)`，默认 60s。
- **影响**：6 Key 不可达时单轮 180s > 间隔 60s → 探测轮次首尾相接、永不空闲，常驻线程持续打上游。更实际的是**健康状态严重滞后**：排最后的 Key 要等前面全超时才被探到，UI 徽标与真实状态差几分钟，而这正是用户判断「该换哪条 Key」的依据。另 `check_one` 两次 `get_key`（各克隆整 Key）+ 一次 `get_settings()`（克隆整份 AppSettings）。
- **方案**：① `for_each_concurrent(4)` 把三分类全部 Key 拉平（**并发度必须有界**，不能 `join_all`，否则「启动瞬间打爆上游」的风险从无变有）；② 整轮套 `timeout(interval)` 保证不重叠；③ 两次 `get_key` 合一、`get_settings()` 换窄读取器（照抄 `store.rs:924-953` 已有模式）；④ `fast_timeout` 从 30s 压到 docs/02 §6.3 原本写的 **3–5s**。预估 6 Key 全超时单轮 180s → 约 60s。
- **M / 中低风险**

#### P2-5 同协议直通做两次整树 JSON 深拷贝

- **证据**：`proxy.rs:1374` `req_json.clone()`（第一次，只为改 model）→ `:1381` `convert_request` 而 `upstream.rs:2311` 开头即 `if from == to { return body.clone() }`（**第二次**）。流式同构（`:1086`/`:1091`）。**同协议是最常见场景**（Claude Code→Anthropic、Codex→Responses）。
- **影响**：`serde_json::Value` 是指针密集树，200 KB JSON 展开后堆占用常达 1~2 MB、节点数以万计。白做两次全树深拷贝，实际改动只有 `model` 一个标量。故障转移时每候选重来一遍。这是热路径上最大的一块纯浪费，与首字节延迟直接相关。
- **方案**（分两步）：① 加 `convert_request_owned(body: Value, ...)`，`from == to` 时零拷贝移动——**几乎无风险，收益一半**；② 摘掉第一次克隆：`if next.is_some() { req_json.clone() } else { mem::take(&mut req_json) }`。**第二步必须有测试锁住「第 N 个候选拿到的仍是原始未污染 body」**（构造两候选、第一个失败、断言第二个收到的 payload 的 model 字段不是前一候选 resolve 后的值）。
- **M / 第一步低、第二步中风险**

> **实施状态（2026-08-03）：两步均已完成。**
>
> 第一步：`convert_request_owned` + 两处调用点改按值传入，有
> `convert_request_owned_passes_through_and_matches_borrowed` 锁住「同协议原样透传 +
> 跨协议与按引用版本结果一致」。
>
> 第二步（与 P2-2 同批做，因为那次本来就要重排这两个函数的前置段落）：
> 两个转发函数的 `req_json` 参数改 `Cow<'_, Value>`，调用方**只对没有后续候选的那次**
> `mem::take`（零拷贝），之前的候选传 `Borrowed` 由被调方自行克隆。
>
> 落地时发现的关键点，记下来避免重犯：
> - 响应侧翻译要用的工具集合（`collect_tool_namespaces` / `collect_custom_tools` /
>   `collect_search_tools`）原先在**构造 payload 之后**才收集，与消费 `req_json` 冲突。
>   已提前到消费之前，并**保持惰性**——只在跨协议时收集（同协议是最常见路径，
>   不能为这里的便利给它增加无谓工作）。
> - **`Cow` 的构造必须放在真正要用的那一刻**。初版把它提到 `if wants_stream` 之前，
>   于是非流式路径拿到已被 take 空的 body，发给上游只剩 `"messages": []`——

>   断言各自收到自己那个。已故障注入验证（让非最后候选也 take → 变红，报 `实际: null`）。

#### P2-6 每请求每候选一次 DPAPI 解密 syscall，且明文密钥全程未清零

- **证据**：`proxy.rs:1363-1367`/`:1075-1079` 每请求 `secrets.read().get(&key.id)?`；DPAPI 分支 `secret.rs:194-199` 调 `CryptUnprotectData`（`:479-494`）——**一次内核态系统调用，在 parking_lot 读锁持有期间同步执行**，且在 async fn 内未包 `spawn_blocking`。返回值落成堆上 `String`，`proxy.rs:1107` `format!("Bearer {secret}")` 再复制一份，**都是普通 String/Vec 无 zeroize**（全仓 zeroize 只在 `crypto.rs:41/231/232` 保护 `DerivedKey`）。
- **影响**：① 每请求一次 syscall（10~50µs，杀软钩子下更高）+ 至少 3 次堆分配，按候选数放大；② 明文 API Key 以未清零副本散落堆上，崩溃 dump / 页文件换出 / 休眠镜像都可能留存。**最值钱的东西（上游 Key 明文）反而没有任何缩短窗口的措施**，与项目已为 `VaultKey` 清零的意图不一致。
- **方案**（先 ② 后 ①）：① 明文类型换 `zeroize::Zeroizing<String>`（crate 已在依赖里）；② 加进程内解密缓存 `RwLock<HashMap<String, Zeroizing<String>>>`，在 `set`/`remove`/三个迁移/`lock`/`unlock` **共 7 处**失效（写入点已收敛可穷举），**建议只在 DPAPI 模式启用**；③ **锁定态必须清空缓存**，否则破坏「锁定态 `get` 返 Err」这条刻意行为。
- **必测**：`lock()` 后 `get` 仍返 Err 且缓存已清；`set` 后立即 `get` 拿到新值；三个迁移后缓存不残留旧模式明文。
- **M / 中风险**（触碰密钥模块，须严守第六节四条锁定态刻意行为）

#### P2-7 `lib.rs` 承担业务编排而非纯 IPC 边界

- **证据**：58 个 `#[tauri::command]` + 托盘 + 服务层 = 2055 行生产码。含明确的服务层逻辑：`apply_tool_config_for`（`:476-527`，含桌面端模型名合规校验与中文告警生成）、`mcp_client_timeout_ms`（`:714`，跨分类取最大值 +30s 的业务规则）、`register_and_record`（`:730`）、`rewrite_registered_clients`（`:752`）。对比 `aggregate_plan`（`:1263`）是理想的 3~5 行薄转发——**项目本身有正确范式，只是未贯彻**。
- **影响**：① 这些编排因身处 lib.rs 而难以单测（lib.rs 仅 12 个测试），而它承载的分支正是 docs/14 反复强调的高危区；② 托盘与 IPC 双入口必须共用同一编排，当前靠手工抽 `apply_tool_config_for` 解决（`:468` 注释已说明「若托盘只 start 不写 config，用户会看到托盘显示已启动但根本没走代理」），但「发现漂移后再抽一个」无结构保证，下一个双入口功能仍会重犯。
- **方案**：新建 `service.rs`，迁入全部非 command 编排 + `save_settings`/`set_mcp_enabled`/`restart_mcp`/`export_config` 的函数体；command 只留参数解构 + 一行调用。这些函数收 `&Arc<Store>` 而非 `tauri::State`（`apply_tool_config_for` 已是这个签名，照此推广）即可直接单测。
- **硬约束：命令名不能变**——前端 `bridge.ts` 与其严格对齐（`lib.rs:2` 已注明），改名即全线 invoke 失败。参数名也不能动（影响 camelCase 序列化）。
- **M / 低风险**（`generate_handler!` 支持路径引用）

#### P2-8 `CategoryType` 硬编码三值，且 settings 用字符串键并存两套真相

## 六、明确不建议改动

### 6.1 三条「故意不修」（沿自 docs/14，本次确认仍成立）

1. **SmartScreen 安装告警**——需代码签名证书（OV $200–400/年，EV $400–700/年），**无代码解法**
2. **`retrieval.rs` 的 `cwd` 无路径白名单**——加白名单会破坏「传任意项目目录做检索」的正常用法；浏览器攻击面已由 `mcp.rs origin_allowed()` 堵住，剩下的属 127.0.0.1 单机自管的既定信任模型
3. **请求日志存明文对话**——默认关，开启是用户显式选择。（唯一建议：按 5.3 #15 把代价说清楚，不改行为）

### 6.2 不建议做的重构

| 不做 | 理由 |
|---|---|
| **P3-1 流式中枢全量重构**（3 解析器 + 3 发射器） | 风险全清单最高：SSE 是转发热路径且是 Codex/Claude 工具调用能否跑通的命门（namespace 折叠、`custom_tool_call`、`tool_search` 都靠它）。而**用户可见收益极小**——两个 →Chat 方向缺 usage 只影响非三大客户端的第三方下游。**改为只做「补 usage + 补黄金样本测试」**，把重构留到真要加第 4 种协议时 |
| **`ClientIntegration` trait 全量化** | 只有 3 个客户端，为不确定的扩展提前抽象不划算；且 `with_rollback`（`tools.rs:1301`）的原子性横跨「双文件」与「多文件+_meta」两种复合操作，trait 化后极易让每个实现各自发明回滚——比现在的 7 处 match 危险得多。**只做消除 `unreachable!()` 的小改** |
| **测试外提到 `src-tauri/tests/` 独立 crate** | 随 P2-1 拆分带走已获大部分收益；且依赖 `#[cfg(test)]` 内部计数器的测试（`tools.rs:596`、`store.rs:1204`、`upstream.rs:996`）必须留内联，会造成测试位置二分 |
| **`update_health` 改走 `mutate_and_persist`** | 高频后台调用，整份 clone 快照代价不对称，且健康态是可重建的瞬态。**保留直写**（函数注释已写明刻意例外） |
| **开启 reqwest 的 `http2` feature** | 当前是 HTTP/1.1（`Cargo.toml` `default-features = false` 未开 http2）。开 h2 会改变与**所有**上游的 ALPN 协商，部分中转商网关对 h2 行为不同，**需真机验证**，不应与纯增益调参混做 |

### 6.3 架构层面的刻意判断

| 点 | 为什么不能改 |
|---|---|
| 流式不设总超时（`proxy.rs:1066/1112`） | 设了会掐断长回答。P1-1 加预算时**只掐 `send()` 探头，不掐已建立的 SSE 流** |
| 流式与非流式超时语义差异（`:1112` vs `:1403`） | P2-2 抽公共构造时，超时**必须留各自调用点** |
| `all_failed_gate_remaining` 里的 `.max()` | 与 P1-4「`Retry-After` 取最小值」不矛盾——它比较同一结论的两个下限，都是「不早于」 |
| `status_counts_against_breaker` 排除 400 | 空探测 + 自身转换 bug 会把整池好 Key 刷熔断（实测 68 条失败近半是这两类）。配套 `is_contentless_probe` 在代理侧直接挡回 |
| 探测与熔断彻底分离 | 探测只写 status/latency，`is_candidate` 只看熔断窗口——故探测端点 401 / 探测模型名不匹配都不会把真实流量本可成功的 Key 踢出路由 |
| `update_health` 只在三字段变化时落盘 | latency 每轮变但只更内存，**稳态转发零磁盘写**。这是热路径最值钱的优化，勿「顺手统一」掉 |
| `if from == to { return body.clone() }` | 规避 Responses→Chat→Responses 往返丢信息。P2-5 改零拷贝时保持该分支语义 |
| `Protocol::OpenaiChat` 的 `serde alias = "openai"` | 旧配置无损反序列化，删不得 |
| `ProviderKey.headers_json` 死字段 | 「自定义请求头」预留位，旧 config 反序列化需要 |
| `disableDeploymentModeChooser` | 刻意对齐 cc-switch，非疏漏 |

### 6.4 密钥与主口令的四处锁定态刻意行为

1. **锁定态 `get` 返 `Err` 而非 `Ok(None)`**——后者会让转发、`has_secret` 对账、导出都当成「这个 Key 没配密钥」去提示用户重录。**P2-6 加缓存时锁定必须清空缓存以维持这条**
2. **锁定态 `set` 拒绝写入，绝不回退 DPAPI**——否则库里两种密文并存而用户以为全由口令保护
3. **锁定态跳过 `has_secret` 对账**——否则会把全部标记刷成 false 写盘
4. **锁定态跳过健康探测**——否则 UI 一片红而真实原因只是没解锁

另：**`save_settings` 不让前端覆盖 `master_password_enabled` 镜像字段**（用户切个主题就带上旧快照，若能写成 true 则下次启动按「已启用」引导解锁而库里没有 `master` 头部，自造死局）；**降级态禁止切换模式**（那时 `entries` 是空的，迁移等于把密钥全丢掉还声称已加密）。

### 6.5 聚合（大脑）的刻意设计

`text_completion` 不动、另起 `ToolSession`（工具关闭时请求体与旧实现**逐字节一致**）；收尾轮仍须声明 tools（抽掉直接 400）；assistant 消息照抄上游返回不重建（重建会丢 thinking block 的 `signature`）；时间预算 70/30 切分；`codegraph_query` 不可用时不声明给模型；`maxToolRounds` 夹在 2~12（**夹下限是关键**，配 1 轮会让工具声明了却永远调不动）；图片在 `aggregate` 加载而非 `mcp.rs`；图片校验不过整次报错不静默丢；**敏感路径按「模型给的名字」与「解析链接后的真实落点」各判一次，两次都不能省**。

另：信号量排队时间刻意不计入成员超时；`pack_symbols` 预算装不下第一个符号时截断后装入而非 `break`。

### 6.6 其他

- **托盘「代理」子菜单语义必须与界面按钮一致**（起=顺带写工具配置、停=顺带还原），否则出现「托盘说已启动、客户端没走代理」。P2-7 重构 `lib.rs` 时这条编排不能被拆散
- **托盘图标像素数据长度非法时原样返回不做部分修改**——宁可两态同图标，也不要花屏，有测试锁住
- **`parse_and_apply` 的 canonicalize 防线是 fail-closed**——失败即判不安全，宁可拒写。测试用 junction（`mklink /J`）真实构造，而非因 symlink 需特权就跳过
- **docs/13「非 GPT 主 Key 支持 Codex 工具」刻意不动代码**——前提已被证伪（详见 docs/13 第十一节）

> **Tailwind 的透明度修饰符只认标度内的值，写错不报错、直接一条 CSS 都不生成。**
> Tailwind 3.4 的 `opacity` 标度是 5 的倍数，而本仓有 **20 处**写了 `bg-warning/8`、
> `bg-danger/12`——包括 `Badge` 组件**除 neutral 外的全部彩色变体**，以及各类警告横幅。
> 它们一直表现为「有边框、有字色，独独没有底色」，因为看着**仍像个提示框**而长期无人发现。
> 判据是可证伪的：`npm run build` 后去 `dist/assets/*.css` 里搜 `.bg-warning\/8`，
> 修之前搜不到、修之后搜得到。修法是把 8 / 12 补进 `tailwind.config.js` 的 `opacity` 标度，
> 而不是把 20 处类名改成 `/10`——保住设计稿原本的 8% / 12%。
