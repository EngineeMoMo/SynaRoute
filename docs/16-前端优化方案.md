# 前端优化方案（2026-08-11）

## 一、当前状态评估

**优点**：
- 细粒度状态订阅（避免无关重渲染）
- 实时推送 + 兜底轮询的双层刷新机制
- 代际号防止跨分类串台
- 完善的错误提示与回滚

**待优化点**（按用户反馈）：
1. **效率**：部分页面操作步骤多、信息密度低
2. **美观**：缺少现代感、视觉层次不够清晰
3. **易用性**：重要操作藏得深、缺少悬浮提示、没有快捷面板

**位置**：`src/components/QuickPanel.tsx`（新建）+ App.tsx 挂载  
**触发**：右下角悬浮按钮（Cmd/Ctrl+K 快捷键可选）

⚠️ **换 title 必须同时补 `aria-label`**：原生 `title` 兼作无障碍名称，

### 实施中发现并修掉的三处「静默失效」

这三条都属于**不报错、只是功能悄悄没有**的类型，与 CLAUDE.md 记录的
`bg-warning/8` 同一族，故单列出来：

1. **`window.location.hash` 导航是空操作**（QuickPanel 的「查看日志」按钮）。
   本应用导航是 App 里的 `useState<NavKey>`，全仓**没有** hash/history 路由，
   写 hash 不会有任何反应 —— 按钮点了什么也不发生、且不报错。
   改为 `onOpenLogs` 回调上抛（与 `UpdateBanner.onOpenSettings` 同一模式）。
   判据：实测点击后 `main h1` 变为「运行日志」且面板关闭。

2. **`animate-in` / `fade-in-0` / `zoom-in-95` / `slide-in-from-bottom-4` 零 CSS**。
   这套类名来自 `tailwindcss-animate` 插件，而本仓 `plugins: []` ——
   四个类**一条 CSS 都不生成**，元素照常渲染、只是没有动效。
   已在 `styles.css` 自建 keyframes。判据：产物 CSS 里四个类各 = 1（此前为 0）。

3. **Tooltip 首帧闪在屏幕左上角**。位置要先量尺寸才能算，`useEffect` 在浏览器
   **绘制之后**才跑，首帧会画在 `{0,0}`。改用 `useLayoutEffect` 在绘制前算完。
   判据：实测 hover 后 `style.left/top` 直接是最终值，从不为 `0px`。

### 关于新增测试的可信度

`tests/silentClassNoop.test.ts` 的每条断言都做过**故障注入验证**（去掉防线后测试必须变红）：

- 删掉 `tailwind.config.js` 的 `opacity: 8` → 3 条红（精确指出缺哪几个 `/8` 类）
- 把 `@keyframes synaroute-fade-slide-up` 改名制造 typo → 1 条红

注入过程中修掉了这个测试**自己**的两个假绿：
- 正则按未压缩 CSS 写（`.cls {`），而产物是压缩的（`.cls{`），导致零匹配被误读成全合规；
- 定义侧用 `toContain("@keyframes " + name)` 子串比对，`...-up-TYPO` 把正确名当前缀包含，
  缺失的定义被判成存在。现改为**精确整名**集合比对。

**教训**：判据必须取自**产物**而非源码，且断言要能区分「零匹配」与「全通过」——
否则测试本身就是下一个静默失效点。

## 八、第二阶段实施记录（性能，2026-08-11 已完成）

### 先量再改：方案原本的 PERF-2 写错了落点

方案第二阶段写的是「给 KeyCard 包 `React.memo` + 回调用 `useCallback`」。实测发现**这样做是白费的**：

用 React fiber 读 KeyCard 的 `memoizedProps`，在轮询前后各取一次：

| prop | 轮询后引用是否稳定 | 内容是否相同 |
|---|---|---|
| `onEdit` | ✅ 稳定 | — |
| `k` | ❌ **每次必变** | ✅ `JSON.stringify` 完全相同 |

原因：`listKeys` 走 IPC，每次返回的都是全新反序列化对象。`React.memo` 默认浅比较
判的是 `prevProps.k === nextProps.k`，引用变了就一律重渲染 —— **只在组件上包 memo，
命中率是 0**。

所以真正的落点在**数据层**：`src/lib/reuseUnchanged.ts` 在 store 收到轮询结果时逐条比对，
内容未变就复用旧对象、整列表未变连数组引用一起保住。这一步把「内容没变」翻译成
「引用不变」，组件侧的 memo 才开始有意义。

### 已交付

| 项 | 落点 | 判据 |
|---|---|---|
| 数据层引用复用 | `src/lib/reuseUnchanged.ts`，在 `loadCategory` / `refreshCategory` / `refreshEvents` 三处接入 | 轮询后 `k` 引用稳定（此前必变） |
| KeyCard memo | `src/components/KeyCard.tsx` | 5s 轮询窗口内卡片列表 DOM 变更 = 0 |
| LogRow memo | `src/pages/LogsPage.tsx` | 8s（≈4 次 2s 轮询）内日志行 DOM 变更 = 0 |

基线：`npm test` **35 passed / 0 failed**，`tsc` 零错误，`build` 通过，控制台零报错。

### PERF-1 虚拟滚动：**刻意不做**

方案原本要给日志页上虚拟滚动。压测后判断不划算：

- 后端事件环上限 `MAX_EVENTS = 500`，即最坏情况就 500 条；
- 实测 500 行真实 DOM：插入 + 强制同步布局 **27.4ms**，滚动重排 **1ms**，总高 21661px；
- 而 LogRow 支持展开，展开后高度从 ~40px 变到数百 px，且**高度取决于异步拉回的 trace 正文长度**
  —— 变高虚拟滚动要接测量回调，易出现跳动和滚动位置漂移。

为一次性的 27ms 引入这份复杂度 + 一个新依赖不值得。memo 消掉的是**每 2s 复发**的那份成本，
零依赖、收益更大。若日后放开 500 上限，再回来上虚拟滚动。

### 测试的双向故障注入

`reuseUnchanged` 同时压着性能与正确性两条线，错误复用会直接导致
「开关点了不动」「排序失灵」，比性能问题严重。所以两个方向都注入验证过：

| 注入 | 预期 | 实际 |
|---|---|---|
| 去掉 `JSON.stringify` 内容比较（无条件复用旧对象） | 正确性测试必须红 | ✅ 红 5 条，含「真实变更必须传出去」 |
| 去掉顺序变化检测（`prev[i] !== old` 那行） | 排序测试必须红 | ✅ 红 1 条「仅顺序变化时数组必须换新」 |

写测试时自己也踩了一个假设错误：首次加载（`prev` 空）时断言了数组同引用，
但 `.map()` 必然产出新数组 —— 该断言改为只校验**元素引用**直通。

### 与既有约定的耦合点（改一处要想到另一处）

`reuseUnchanged` 与两个 memo 组件是**成对**的：删掉前者，两个 memo 立刻恒失效且**不报错、
不影响功能**，只是性能悄悄退回原样 —— 又一个静默失效点。三个文件的注释里都写明了这层依赖。

### 方案第 2 条的写法会破坏无障碍，已改

方案原文是 `from-primary to-primary-light`（往**亮**处渐变）。实测算了对比度后否决：

| 色值 | 白字对比度 | WCAG AA（4.5:1） |
|---|---|---|
| `--primary` #6D5EF7（基色） | **4.57** | 勉强过，余量几乎为零 |
| #8B80FA（按方案取的浅端） | **3.20** | ❌ 不合格 |
| #5848E4（改用的深端） | **6.07** | ✅ |

基色本身只有 4.57，**任何提亮都会跌破 AA**。所以渐变改成往深处走——层次感一样在，
白字对比度反而比原来的纯色更好。色标名也从 `primary-light` 改为 `primary-deep`，
避免名字与实际方向相反。

**教训**：涉及文字底色的视觉改动，必须先算对比度再落地，不能照抄方案里的色值方向。

### 三个刻意的实现选择

1. **脉冲用 `box-shadow` 而非 Tailwind 自带的 `animate-pulse`**：后者是整体 opacity
   呼吸（0.5↔1），文字会跟着变灰、可读性下降。这里只让光晕呼吸，文字始终满对比度。
   用 `currentColor` 画光晕，自动跟随徽标语义色，不必为每种色写一遍。

2. **抖动只在「刚进入熔断」时播一次**，靠 `useRef` 记住上一次状态。HealthBadge 跟着
   5s 轮询重渲染，若常挂 `status-shake`，节点因切分类/列表重排而重建时会再抖一次，
   表现为「隔一会儿自己抖一下」。熔断是持续状态（最长 60s），持续抖动只会变噪音。

3. **`prefers-reduced-motion` 兜底是必需项不是装饰**：无限循环脉冲对前庭敏感用户是
   实际障碍。媒体查询刻意放在 `@layer utilities` **之外**——层内的媒体查询在某些
   Tailwind 版本下会受 layer 顺序影响优先级。验证方式是用 CSSOM 把条件强制改成 `all`，
   确认动画真的变 `none`（只测「另插一条同选择器规则能否覆盖」是不够的，那绕过了层级顺序）。

### 顺带修掉两个实测发现的问题

这两个都不在 UI-1 范围内，是验证过程中撞见的：

1. **快捷面板悬浮按钮遮住最后一张卡片的「启用」开关**（本轮新引入的回归）。
   截图才看出来：FAB 是 48px + 24px 边距，而列表 `pb-6`（24px）不够，滚到底时
   FAB 矩形与最后一个 Switch 重叠、点不到。已把分类页列表改成 `pb-24`。
   逐页验过其余 6 个滚动页，滚到底都没有可交互元素落在 FAB 区域，故只改这一处。

2. **KeyCard 三个图标按钮缺 `aria-label`**（既有缺口）。它们只有 Tooltip 的视觉提示，
   而 Tooltip 是 hover/focus 才出现的视觉层、不构成无障碍名称——屏幕阅读器只会读到
   一个空按钮。已补 `aria-label`，文案与 Tooltip 同源。

### 验证过程中的一次自我纠错

故障注入 `prefers-reduced-motion` 那条测试时，头两次显示「测试仍通过」，我差点据此
认定测试没有捕获力。实际原因是 Bash 工具里 `python3 - <<'PY'` 的 stdin 没接上、
脚本压根没执行，**源码从未被改动**。改用编辑工具注入后测试立刻变红。

教训：故障注入必须先确认「注入本身生效了」（这里是 `grep -c` 应从 1 变 0），
否则「测试没红」既可能是测试无效，也可能是注入无效，两者结论完全相反。

### 补哪些、不补哪些

原则是**只补「界面文字本身答不了的问题」**。本页说明文字本来就密，按数量凑提示只会
制造噪音。故：

| 位置 | 补的是什么问题 |
|---|---|
| 路由模式徽标 | 整条状态条最晦涩的元素——一个图标 + 一个光秃秃的数字，此前全靠原生 title |
| 「N 个 Key 不可用」 | 「不可用」是**健康探测**的结论，而裁判可用性的是真实流量；不说清用户以为代理废了 |
| Key 计数行 | 停用的 Key 不会在别的 Key 失败时被自动启用（很容易被反向理解） |
| 熔断横幅 | 「我要做什么吗」——不用，倒计时结束自动恢复，别去停用或删那条 Key |
| cc-switch 导入 | 「会覆盖我的 Key 吗、会切接入吗」——都不会，但这话原先只写在点开后的弹窗里 |
| 成员健康徽标 | 探测不可用**不会**让整轮聚合失败，只是该成员可能无结果 |
| 并发上限 | 成员数超过上限会排队分批，不是被丢掉（此前该字段零说明） |
| 成员模型下拉 | 改完要点「保存配置」才生效 |

**刻意不加**：决策者 / 汇总模型两处 —— `KeyModelSelect` 的 `hint` 已是常驻可见文字。

### 两个实施要点

1. **换掉原生 `title` 必须补 `aria-label`**。原生 title 兼作无障碍名称，直接删会让
   图标按钮在屏幕阅读器里变成空按钮（与第七节 KeyCard 那条同一个坑，这是第二次）。
2. **Tooltip 用 `cloneElement` 附事件，包不同子元素要各自实测**：包 `<select>` 后
   下拉仍能正常改值（已验：`opus-4-6` → `opus-4-7` 成功）；包 `HealthBadge` 这类
   自定义组件要外套一层 `<span>` 承接 ref，否则 ref 落不到 DOM 节点上。
   `StatusBarPicker` 的提示在菜单展开时要 `disabled`，否则提示框浮在自己刚打开的
   选项列表上挡住第一项。

### ⚠️ 同一个坑第二次：故障注入前必须确认注入生效了

上一轮是 `python3 - <<'PY'` 的 stdin 没接上；**本轮是本机 `python` 根本不可用**——
它是 Windows 应用商店的**占位存根**：存在、`--version` 无输出、退出码 49，
用它改文件**静默不生效**。我据此一度认定「并发去重那条测试没测到东西」，
实为编辑从未落盘（`grep` 一查，目标行原样未动）。

**结论**：改文件不要走 `python` 一行流，用编辑工具。故障注入后先 `grep` 确认目标行
真的变了，再看测试红绿——否则「测试没红」既可能是测试无效、也可能是注入无效，
两者结论完全相反。
