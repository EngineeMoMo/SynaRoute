# 用量查询 + 桌面悬浮窗方案（2026-08-11）

## 零、需求与取证

用户诉求两条：

1. **参考 cc-switch 做用量/余额查询** —— 「不然用户不知道剩余多少金额」
2. **悬浮窗改造** —— 默认关闭；用户开启后，**最小化到托盘才出现**；图标用软件自己的图标

用户明确指定「参考 cc-switch」，故先取证它的真实实现，而不是凭想象设计。

### cc-switch 的真实机制（取证自本机 `~/.cc-switch/cc-switch.db` + 用户提供的界面截图）

⚠️ **取证过程中的一次自我纠正**：`/tmp/cc-switch` 看似是源码目录，实为**空骨架**
（`find -name "*.rs"` = 0 个文件）。我曾据此得出「cc-switch 没有余额功能」的结论，
**该结论错误**。真实证据来自数据库文件里持久化的配置 JSON。

**它有两套并存的机制**，不是一套：

#### A. 余额查询（用户可编辑的 JS 脚本）

存在供应商配置的 `usage_script` 字段里：

```json
{
  "enabled": true,
  "language": "javascript",
  "code": "({ request: {...}, extractor: function(response) {...} })",
  "timeout": 10,
  "templateType": "balance",
  "autoQueryInterval": 30,
  "apiKey": "...",
  "baseUrl": "..."
}
```

脚本内容（内置「通用模板」原文）：

```javascript
({
  request: {
    url: "{{baseUrl}}/v1/usage",
    method: "GET",
    headers: { "Authorization": "Bearer {{apiKey}}" }
  },
  extractor: function(response) {
    const remaining = response?.remaining ?? response?.quota?.remaining ?? response?.balance;
    const unit = response?.unit ?? response?.quota?.unit ?? "USD";
    return {
      isValid: response?.is_active ?? response?.isValid ?? true,
      remaining,
      unit
    };
  }
})
```

界面（用户截图）要素：**启用开关**、**预设模板切换**（自定义 / 通用模板 / NewAPI /
Token Plan / 官方）、**凭证覆盖**（API Key、请求地址，留空则用供应商自身配置）、
**超时（秒）**、**自动查询间隔（分钟，0 = 不自动）**、**提取器代码编辑器**。

关键设计点，值得照抄的是这几条：
- `{{baseUrl}}` / `{{apiKey}}` **占位符**——脚本可复用，不必为每个 Key 重写
- **多重 `??` 回退**取值——兜住各家字段名差异（`remaining` / `quota.remaining` / `balance`）
- 统一返回契约 **`{isValid, remaining, unit}`**
- **凭证可覆盖**：余额接口的域名/密钥有时与转发端点不同（独立计费面板）
- **预设模板**：绝大多数用户点一下即可，不必理解字段

#### B. 本地成本核算（数据库表）

| 表 | 作用 |
|---|---|
| `model_pricing` | 每模型单价：`input/output/cache_read/cache_creation_cost_per_million`，**全为 TEXT** |
| `proxy_request_logs` | 单请求级：4 类 token + 4 类成本 + `cost_multiplier` + `data_source` |
| `usage_daily_rollups` | 按 `日期 × app_type × provider × model` 汇总，含 `total_cost_usd` |
| `session_log_sync` | 增量读 CLI 会话日志（补齐非代理路径的用量） |

同样值得照抄的：
- **成本一律存字符串**，不用 f64 —— 避免浮点累加误差（金额场景不可接受）
- **`cost_multiplier`** —— 中转站普遍按官方价打折（0.3 之类），一个数就能表达
- **`data_source`** —— 区分数据来自代理实测还是日志导入，口径不混

## 一、与 SynaRoute 现状的差距

| 现状 | 差距 |
|---|---|
| `TokenUsage { input, output, cache_read }` | **缺 `cache_creation`**。缓存写入单价通常是输入价 1.25 倍，漏了成本会偏低 |
| 用量只有「分类 × Key」累计，无日期维度 | 要按日趋势必须加日期维度 |
| `UsagePage` 注释明写「只统计 token、不换算钱：各中转商单价差异巨大，SynaRoute 无从得知」 | 这是**当初的刻意决定**，本轮推翻它。推翻的正当性：不由 SynaRoute 猜价，而是让用户填倍率/单价 |
| 悬浮窗 `QuickPanel` 是**主窗口内的组件** | 需求要「最小化到托盘后出现」，页面内组件做不到 —— 必须改成独立 Tauri 窗口 |
| 无 `show_tray` / 悬浮窗开关字段 | 需新增设置项，且默认关闭 |

**关键约束**：`lib.rs:1232` 的 `CloseRequested` → `window.hide()` 就是「最小化到托盘」
那一刻，悬浮窗的显示/隐藏必须挂在这里，才符合「最小化后才出现」。

## 二、设计

### 2.1 余额查询（对齐 cc-switch，但不执行用户代码）

**照抄**：占位符、多重回退取值、`{isValid, remaining, unit}` 契约、预设模板、
凭证覆盖、超时、自动间隔。

**唯一偏离**：cc-switch 让用户写 JavaScript 并执行；SynaRoute 改为**声明式配置**，
由 Rust 发请求 + 按候选字段名递归提取。

> 偏离理由（安全）：内置 JS 引擎等于在应用里开一个任意代码执行入口，而脚本里还嵌着
> 明文 apiKey。SynaRoute 是本地密钥托管应用，这个代价换来的灵活性用不上——实测
> cc-switch 自己的「通用模板」提取逻辑就是几个 `??` 回退，声明式完全覆盖。
> 用户对此无偏好（问过），故按更安全的一侧实现。

数据结构（新增，挂在 `ProviderKey` 上）：

```rust
pub struct BalanceQuery {
    pub enabled: bool,
    /// 预设模板 id：generic / newapi / tokenplan / official / custom
    pub template: String,
    /// 请求路径，支持 {{baseUrl}} / {{apiKey}} 占位符
    pub url: String,
    pub method: String,                    // 默认 GET
    /// 认证头形态：bearer / x-api-key / none（对齐三种常见上游）
    pub auth: String,
    /// 凭证覆盖：留空则用本 Key 自身的 baseUrl / 密钥
    pub base_url_override: Option<String>,
    pub api_key_override: Option<String>,  // 存密钥库，不进 config.json
    pub timeout_secs: u32,                 // 默认 10
    pub auto_interval_min: u32,            // 默认 0 = 不自动查
    /// 自定义取值路径（留空 = 走内置候选链自动探测）
    pub remaining_path: Option<String>,
}
```

取值优先级：`remaining_path` 显式指定 → 内置候选链自动探测：

```
remaining, balance, credit, quota.remaining, data.balance,
data.remaining, data.quota.remaining, ...
```

单位与有效性同样走候选链（`unit` / `quota.unit`，默认 USD；`is_active` / `isValid`）。

返回：`BalanceResult { ok, remaining, unit, is_valid, queried_at, error }`。

**失败必须可见**：查不到就在卡片上如实标「查询失败 + 原因」，绝不显示 0 或空白 ——
显示 0 会让用户以为余额真的用光了，这类误导比不显示更糟。

### 2.2 本地成本核算（对齐 cc-switch）

- `ProviderKey` 增 `cost_multiplier: Option<String>`（默认 "1.0"，官方价的几折）
- 内置常见模型官方价表（Rust 静态表，覆盖 claude / gpt / glm / deepseek 系）
- 可选逐模型单价覆盖（`model_pricing`，用户填了就优先）
- 成本一律 **字符串存储 + 定点数运算**，不用 f64
- 用量累加器加**日期维度**：`date × category × key × model`
- `TokenUsage` **补 `cache_creation` 字段**（现在缺，会让成本偏低）

保留期：按日汇总只留最近 90 天，滚动清理（避免 `usage.json` 无限增长）。

### 2.3 悬浮窗改造

| 项 | 现状 | 改为 |
|---|---|---|
| 形态 | 主窗口内组件 | **独立 Tauri 窗口**（`always_on_top` + `skip_taskbar` + 无边框） |
| 默认 | 常驻显示 | **默认关闭**（`floating_widget_enabled = false`） |
| 显示时机 | 一直在 | **仅「开关开启」且「主窗口已隐藏到托盘」时显示** |
| 图标 | `Zap` 通用图标 | **软件自己的图标**（`icons/32x32.png`） |

显示条件是**两个条件的与**，在 `CloseRequested`（→ 托盘）与主窗口 `show()`
（← 从托盘唤起）两处各切换一次，保证「主窗口在前台时悬浮窗不碍事」。

内容沿用现有 QuickPanel 那套（三端代理状态 / 主 Key 健康 / token），
**加上本轮新增的余额与今日消耗** —— 这正是用户「不知道剩余多少金额」的落点。

## 三、实施顺序与验收判据

| 批次 | 内容 | 判据 |
|---|---|---|
| ①✅ | `TokenUsage` 补 `cache_creation`；成本定点数运算 + 单价表 | 单测：定点乘加无浮点误差；缓存写入计入成本 |
| ②✅ | 按日汇总 + 90 天滚动 | 单测：跨天分桶正确；超期清理不误删当期 |
| ③✅ | 余额查询后端（占位符 / 候选链 / 超时 / 失败可见） | 单测：各家返回结构都能取到值；超时如实报错不显示 0 |
| ④ | Key 编辑器 UI（开关 / 模板 / 凭证覆盖 / 测试查询） | 浏览器实测：点「测试查询」能出结果或明确错误 |

| ⑥ | 悬浮窗独立窗口化 + 默认关 + 托盘联动 + 换图标 | 真机实测：默认不出现；开启后仅最小化到托盘才出现 |

## 三点五、实施中实测抓到的两个坑

这两个都不是编译期能拦住的，靠断言才暴露，故记录在此。

### 坑 1：单价用微美元 → 缓存 token 静默免费（第①批）

`ModelPricing` 起初按微美元（1e-6）存单价，`$3/MTok` → `3`。
缓存命中价 = 输入价 ÷ 10 → **整数除法 `3/10 = 0`**，于是缓存 token 完全不计费。
连 Haiku（$0.25/MTok）的输入价本身都会退化。

改为**纳美元**（1e-9）：`$3/MTok` → `3000`，缓存价 `300`。
已立回归测试：全表自检「任何模型的四项单价都 > 0」。

### 坑 2：把「历史总量」当成「当天消耗」（第②批）

`usage_totals` 是**跨全部历史**的累加器（热路径只往里加）。
flush 时若直接把它整份写进当天的桶，会有两个后果：

- 每次 flush 都把同一批历史重复计入当天（实测：v1 的 500 + 当天 200 → 桶里 700）
- 跑一周后「今日花费」= 「累计花费」，趋势图完全失真

正确做法是引入**基线**：

```
今日增量 = usage_totals − usage_baseline     （逐字段 saturating_sub）
flush 后 usage_baseline ← usage_totals        （抬基线）
跨 UTC 零点 → 换桶 + 抬基线
```

由此 v1 老文件的历史（无日期维度，无从得知属于哪天）成为启动基线、
**不计入任何日桶**，如实丢弃日维度而不是编造一个日期把整段历史堆到某天。
已立两条回归测试：日桶只含本次增量、无新消耗时重复 flush 不翻倍。

### 附带修正：版本门测试原本是失效的

`newer_usage_file_is_never_overwritten_by_older_program` 里 `dailyBuckets`
被写成对象，而 v2 类型是数组 → serde 在**版本门之前**就解析失败，
走「损坏文件」分支，于是这条测试测的根本不是版本门。
把已知字段改回合法形状、未来字段另用 `futureOnlyField` 表达后才真正生效。

## 四、风险与刻意取舍

1. **不猜单价**：内置表只作默认值，用户可改倍率或逐模型覆盖。面板必须标明
   「按你配置的单价估算，非账单」——否则用户会拿它跟中转站账单对数字。
2. **余额接口无标准**：候选链兜不住的站点，留 `remaining_path` 手填出口。
3. **不执行用户 JS**（见 2.1 偏离理由）。
4. **`cache_creation` 采集依赖上游返回**：部分中转商不下发该字段，此时该项为 0，
   成本会略偏低。面板需注明，不能假装精确。
5. **悬浮窗不做「显示余额明细」**：悬浮窗定位是瞥一眼，明细去用量页。
