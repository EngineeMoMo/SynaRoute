## 一、这是什么

Tauri 2 桌面应用（Rust 后端 `src-tauri/` + React/TS 前端），在本机跑一个 HTTP 代理，
把 Claude CLI / Claude 桌面端 / Codex 桌面端的 API 请求路由到用户配置的多条上游 Key，
含故障转移、模型映射、协议转换、加密密钥存储、健康检查、用量统计、多模型聚合决策。

**三个客户端分类各自独立**（`CategoryType`）：独立端口、独立 Key 池、独立启停。
启动代理时**顺带写客户端配置**指向本机代理，停止时**顺带还原** ——
这个语义在界面按钮与托盘菜单上必须一致，否则会出现「托盘说已启动、客户端没走代理」。

### 运行数据落在哪

| 内容 | 位置 | 备注 |
|---|---|---|
| 配置（不含密钥） | `%APPDATA%\SynaRoute\config.json` | Key 的地址/映射/倍率都在这里 |
| 密钥库 | `%APPDATA%\SynaRoute\secrets.enc` | DPAPI 绑账户，**不可跨机器搬运** |
| 日志 | **exe 同级** `logs\*.jsonl` | 刻意不走 `%APPDATA%` —— 躲 MSIX 虚拟化 |
| 更新签名私钥 | `~/.tauri/synaroute.key` | 明文、无口令；CI 用 GitHub Secrets |

前两项可用 `SYNAROUTE_DATA_DIR` 覆盖（2026-08-27 加，见 `data_dir.rs`）；
它**不解决** MSIX 虚拟化，那层重定向发生在文件系统调用上。

### 前后端边界的三条硬约束

1. **所有调用走 `bridge.ts` 的 `call<T>("cmd", args, mock)`**（74 处）。第三参是浏览器
   预览用的 mock。有策略门 `invoke-command-must-exist` 核对命令名 ——
   拼错**没有编译错误**，只在用户点到那个按钮时炸。
2. **`UserPrefs` 的字段集必须与 `src/lib/prefs.ts` 的 `pickPrefs` 逐字段对齐。**
   漏一个键 → `saveSettings` 提交的 JSON 缺键 → `#[serde(default)]` 补成 false →
   **静默关掉用户的开关**。这类缺陷已吃过两次（含一个 P0：切主题把刚关掉的自启动装回系统）。
3. **带系统副作用的开关不进 `UserPrefs`**（`auto_start` 写注册表、`lan_exposure` 重建
   监听 socket），改走专用命令。判据写在 `model.rs` 那段注释里。

演示数据在 `mockData.ts`，生产构建由 vite alias 换成空桩。有跨语言判据
`tests/vendorSeedParity.test.ts` 防它与 Rust 厂商清单分叉 ——
官网截图就是从演示模式截的，分叉会对外少报厂商数。

### 🔴 这张表的局限（必读）

### 🔴 两条不存在的 NFR（本文档伪造过它们）

「单文件 ≤900 行」与「单日日志 ≤100MB」**在 docs/01 和 docs/02 里都搜不到**。

两条的真实性质：

  它只管**新文件**，且**已经在执行**（本轮 `updater_msg` 208 / `data_dir` 115 /

  **规则本身是自洽的，不存在「文档写 900、代码 3137」那种不一致** —— 那句话是我编出来的。
- **100MB 没有任何出处**，但**它指向的风险是真的**（全仓当时无任何按体积限日志的代码）。

  ✅ **2026-08-27 已实现**：`log_rotate.rs` 两级上限（单文件 16 MB 滚动切分 +
  单日 16 个文件 = 256 MB，越界删当天最旧的）。定的值是 256 MB/天而不是那个凭空的 100MB。

## 六、四条曾被记成「界面承诺 ≠ 实际行为」的项（**逐条 grep 复核后只剩一条成立**）

> 🔴 **旧版标题是「四条界面承诺 ≠ 实际行为」，那个归类错了三条。**

> 教训与 CLAUDE.md 里那条一致 —— 判据必须落到代码，转述不算取证。

真·界面撒谎的形态是：界面让用户配，后端不读或只在别处读，用户照界面做得到静默的无效。
**这类比「功能缺失」更糟** —— 缺失是看得见的，撒谎是看不见的。
而「有字段无 UI」是另一类问题（用户无法控制，但也不会被误导），严重程度低一档。

### 6.3 大脑聚合开关的文案与实现不符（**已修**，2026-08-27）

`proxy.rs` 对 `aggregate` / `brain` **零引用** —— 普通转发**永远不聚合**。

实测该开关的真实作用域是 `aggregate.rs:134` 与 `:460` 两处门禁：
关着时 `synaroute_ai` 与手动执行**直接报错**，与普通转发无关。
文案已改为「控制本分类的 synaroute_ai 工具能否调用…普通转发不受影响，始终走多 Key 故障转移」。

**建议：改文案。** 不是实现不了，是**产品上不该那样**：聚合要 fan-out 到 N 条 Key、
等全部返回、再综合一轮，延迟至少是单次的 N 倍 +1 轮，且**综合完成前无法流式输出** ——

聚合的正确入口是 MCP 工具 `synaroute_ai`（FR-014 已实现）。

### 棘轮为什么只数生产段

Rust 测试**同文件内联**。按整文件冻结的话，「补一条回归测试」会被门挡住 ——
那会让质量门变成**质量的敌人**，而本仓核心纪律恰恰是每个缺陷都留一条回归测试。
故 `.rs` 只数尾部 `#[cfg(test)] mod tests` 之前的行。

判据的**单一事实来源**在 `scripts/lib/rust-source.mjs`，别在别处抄第二份 ——
曾经抄过，两份立刻漂移（一份认 `pub(crate) mod tests` 一份不认），
而在 `check-forbidden` 那侧失效方向是**隐蔽的**（测试段被当成生产段扫）。

### 想抬高上限的规矩

在 `ratchet.json` 里加 `raises`（`from`/`to`/`why` ≥20 字/`when`），否则 `ratchet:verify` 拦。
这条不是洁癖，是 OmniRoute 用一整节文档记下的实测代价：**抬高**是十秒的 JSON 编辑、
是解红最快的路；**降低**要有人主动跑 `--update`。他们「下个周期收紧」写了 31 次兑现 1 次。
结论原样抄下来：**能抬高上限的机器人比没有机器人更糟。**

## 九、测试纪律

**当前基线（2026-08-27）**：`cargo test --lib` **831 passed / 0 failed / 3 ignored**；
`cargo clippy --lib --all-targets -- -D warnings` 零警告；`npm test` **119 passed / 15 文件**；
`tsc --noEmit` 干净；`npm run gates` 全绿。

核心纪律两条：

1. **每个缺陷留一条回归测试。**
2. **每条修复做故障注入** —— 去掉修复后对应测试**必须变红**。没红就当场重做注入手法。

### 🔴 注入手法上踩过的八个坑

| # | 坑 | 教训 |
|---|---|---|
| 1 | `sed` 多行模式**根本没改到代码**，注入后恒绿 | 注入不变红时**先怀疑注入本身** |
| 2 | `String.replace` 用 LF 搜索串改 **CRLF** 文件，静默不匹配 | 先确认文件行尾 |
| 3 | 用 `cp -p` 恢复 `.rs`，**cargo 沿用注入版产物** → 假红 | 恢复 `.rs` 后要 `touch` |
| 4 | 用例只把计数推到 33，没压到 `1i64 << 64` 的边界 | 注入不变红也可能是**用例没压到边界** |
| 5 | 判据有两个下限常量，改一个被另一个挡住 | 别留重复的门限 |
| 6 | 想用「文件换成目录」让 `remove_file` 失败，但 `with_rollback` 先拍快照就返回了 | 那个窗口压根没打开 |
| 7 | 想用打 500 把 Key 打到熔断，但 **5xx/429 刻意不计熔断** | 永远打不出来 |
| 8 | 「连续调 1000 次断言互不相同」去掉修复照样绿 | **测并发缺陷的用例必须并发地写** |

第 8 条的实测：`db_copy_path` 自身开销就够拉开 100ns，单线程压根撞不上；
改成并发 8×2000 后注入即红（16000 次只得 15179 个不同名）。

**第 1、2 条的通用防身手法**（`log_rotate` 那轮起用，8 条注入一次全红）：
注入脚本里**断言文件真的变了**，改不到就直接判这次验证无效 ——

```js
const injected = apply(ORIG);
if (injected === ORIG) { console.log("注入没改到文件 —— 这次验证无效"); allGood = false; continue; }
```

没有这一行，「搜索串对不上」的表现就是**全部注入都显示变红失败（即仍绿）**，
而人的第一反应会是「代码没问题」而不是「脚本没生效」。
另外恢复时也要断言注入串还在，否则会静默留下一个改坏的文件（这轮真撞上了一次：
shell 转义让恢复脚本找不到注入串，因为有断言才当场发现）。

### 🔴 单元覆盖 ≠ 覆盖接线（反复出现的一类盲区）

「定义函数有测试、分发函数有测试」不等于「两者之间的接线有测试」，
而**接线漏了的表现恰恰是静默的**。**五个**实例（已经不是个例，是本仓的固定盲区）：

| 实例 | 把接线打断后 | 补的判据 |
|---|---|---|
| `mcp.rs` 的 `handle_http` 取 path 传给 dispatch | 硬编码成 `Unbound`，**776 条全绿** | `handle_http_derives_the_caller_from_the_request_path` |
| `route_meta` 「每个出口都调一次」 | 必然会漏，且漏掉是静默的 | 改成 wrapper + inner，头在**唯一出口**挂 |
| `lan_guard` 的 `accept` 传 peer | 丢回 `_` + 硬编码 loopback = **缺陷本体**，11 条里 10 条全绿 | **源码级判据** `accept_must_pass_the_real_peer_into_the_guard` |
| `log_rotate` 的写线程走 `OpenLog` | 改回裸 `write_all` = 体积上限完全不生效，11 条里 **10 条全绿** | **源码级判据** `the_log_writer_thread_must_go_through_openlog` |
| `custom_headers` 的三处接线（保存校验 / 转发合并 / KeyEditor payload） | 摘掉任一处都是「配了但无效」，而全部校验用例都直接调函数、照样全绿 | 后端 2 条 + 前端 3 条源码级判据 |

**共同形态**：单元测试直接构造/调用那个组件，于是组件本身怎么测都绿 ——
而**谁在调用它、传的是不是真东西**没有任何东西管。五次里有三次
「注入后仍绿」是在写完测试之后才发现的。

对策两条：
1. **为接线单独写判据**，必要时用源码级断言（`include_str!` 读自己的源码，剥掉测试段）。
2. **收成唯一出口/唯一判据点**，让「记得在每处都调一次」这种纪律根本不存在
   （`route_meta` 的 wrapper+inner、`log_rotate::parse_name` 的单一事实来源都是这么做的）。

## 十一、发版流程

版本号要同步 **五处**（四文件）：

```
package.json  ·  package-lock.json ×2（.version 与 .packages[""].version）
src-tauri/tauri.conf.json  ·  src-tauri/Cargo.toml
```

`package-lock` 用 `npm install --package-lock-only`，别手改。`Cargo.lock` 由 `cargo check` 自动对齐。

cargo 每次构建自己会对齐，收进来只会让「刚 bump 完还没构建」这个正常中间态变红）。

```bash
# 1. bump 五处 → 2. 全量回归 → 3. 提交 → 4. 打 tag 推送
git tag -a v0.1.4X -m "SynaRoute v0.1.4X" && git push origin v0.1.4X
```

CI（`release.yml`）四平台矩阵构建 + 签名 + 上传，然后 `publish-release` 自动转正式。

### 发版验收判据（一次列全）

1. `/releases/latest` 解析到期望的 tag
2. **17 个资产**全部 `state: uploaded`
3. `latest.json` **11 个平台条目**，每条都有 signature
4. 每个 signature 的 keyid == `tauri.conf.json` 里 pubkey 的 keyid（`7A46ECB8087DE26F`）
5. **匿名**取 `releases/latest/download/latest.json` 与 API 取到的**字节一致**（`cmp`）
6. Windows job 的三道产物门 success

### 🔴 上传阶段的瞬时故障（已发生两次）

GitHub 会在**资产上传步骤**吐 HTML 500 页（`##[error]<!DOCTYPE html>` … `Unicorn!`），
而**构建本身已经成功**。后果：草稿 + 资产缺失 + `latest.json` 缺平台条目 +
`publish-release` 被 skip。v0.1.27 缺 5 个条目、v0.1.40 缺 `darwin-aarch64` 两个。

**修法：`POST /actions/runs/{run_id}/rerun-failed-jobs`。** 只重跑失败的 job，
`create-release` 保持 success 故 `release_id` 保留，重建的资产落进**同一个草稿**，
随后 `publish-release` 自动转正式（约 7 分钟）。

**不要手工补 `latest.json` 的缺失平台条目** —— 那需要该平台的二进制，
Windows 机器上造不出 macOS aarch64 的。手工修复只适用于「资产在、JSON 丢了条目」。

⏱ **不要用一条长 Bash 轮询 CI。** 一次 ~22 分钟的轮询把 shell 弄成无响应 >10 分钟，
恰好在发版最需要观测的时刻。每次调用只轮 3~5 轮（≤5 分钟）。

### 🔴 发布物绝不能含本地数据与密钥

`npm run audit:release` 查五项。两个已踩过的判据坑：
**别用 i18n 占位文案当演示数据的判据**（`厂商1（官方直连）` 是输入框灰字，每个包都有）；
**别查开发机用户名**（Rust 把 `.cargo/registry` 源码路径嵌进二进制供 panic 用，每个 Rust 程序都有）。

## 十二、版本号有两个独立来源（漂移是静默的）

| 来源 | 消费者 |
|---|---|
| `tauri.conf.json` 的 `version` | `package_info().version`（`get_app_version` / `check_for_updates` / 诊断导出）**与** Windows VERSIONINFO 的 FileVersion（tauri-build `lib.rs:632`） |
| `Cargo.toml` 的 `[package] version` | `CARGO_PKG_VERSION` → `x-synaroute-version` 响应头 |
| `package.json` / `package-lock.json` | 运行时**无人消费** |

两条链路一旦漂移，**exe 属性页与响应头会给出两个不同的版本，且不报错**。

**「产物过期导致版本号卡住」这个假设已排除**：tauri-build `lib.rs:485` 对每个配置路径都
emit `cargo:rerun-if-changed`，改版本必然触发重编。别为此烧一次 `cargo clean`（53 GB target）。

**取运行实例真实版本的最快办法**（无需 IPC）：

```bash
curl -i http://127.0.0.1:<代理端口>/v1/models
```

读 `x-synaroute-version`。`/v1/models` 在转发前就返回，**不耗配额**。
端口在 `config.json` 的 `settings.proxyPorts`。

⚠️ 扫二进制找版本号时小心：crate 依赖路径（`tracing-core-0.1.36`、`rustc-demangle-0.1.27`）
长得和应用版本一模一样。必须看上下文 —— 本仓在这上面误判过一次。

## 十三、🔴 MSIX AppData 虚拟化（本项目最大惨案）

Claude 桌面应用是 MSIX 打包（包家族 `Claude_pzs8sxrjxfjjc`）。
Windows 对包内进程做 AppData 虚拟化：**Claude Code 及其派生的一切子进程**
（Bash / powershell / node / 它启动的 SynaRoute）读写 `%APPDATA%\SynaRoute\*` 时，
被透明重定向到
`%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\SynaRoute\*`
的**包内私有副本**。用户双击 exe 无包身份，读写**真实文件**。

→ **两个平行宇宙。** 曾致「用户 UI 4 条 Key vs Claude 处处验证 6 条」多日排查惨案。

铁律四条：

1. **诊断/修改用户真实 `%APPDATA%` 数据必须逃逸包身份**：
   `schtasks /Create ... /TR "F:\...\x.bat"` + `/Run`（计划任务服务启动无包身份）；
   bat 与产物放非 AppData 盘（`F:\`、`E:\` 不被虚拟化）。
   Git Bash 下 schtasks 需 `MSYS_NO_PATHCONV=1`（用完 unset，否则破坏 `taskkill //F`）。
2. **交付验证必须让用户亲自双击启动**，用共享的 exe 同级 `logs\`（非虚拟化）里的
   「启动自检」行核对。**Claude 自己启动的实例活在虚拟宇宙，其表现不代表用户。**
3. 症状特征（复发速查）：同一 exe 用户开与 Claude 开数据不同；
   Claude 探针全对但用户仍旧；`%APPDATA%` 目录清单在两个视角下不同。
4. **不要删包容器里的虚拟副本**（可能留 tombstone 遮蔽真实文件）。

完整复盘见 [docs/11](11-MSIX虚拟化踩坑复盘.md)。

## 十四、安全

### 14.1 密钥存储两种模式

| 模式 | 机制 | 关键点 |
|---|---|---|
| 默认 | Windows DPAPI 绑当前账户 | `secrets.enc` **不可跨机器搬运** |
| 主口令增强（FR-018 可选） | Argon2id 派生 KEK + AES-GCM | 长驻密钥（解锁派生一次，各条只做 AES-GCM） |

🔴 **模式的事实来源是 `secrets.enc` 里有无 `master` 头部**，
`settings.master_password_enabled` 只是 UI 镜像。启动时以库为准对账，
且 `save_settings` **不许前端覆盖它** —— 否则自造「配置说开着、库里没头部」的死局。

**锁定态四处刻意行为**：`get` 返 `Err` 不返 `Ok(None)`、`set` 拒写且不回退 DPAPI、
跳过 `has_secret` 对账、跳过健康探测。

三个迁移操作都是「先整库解密成功 → 备份 → 写盘 → 失败回滚内存」。

### 14.2 局域网访问（2026-08-27 加固）

`lan_exposure` 开 → 绑 `0.0.0.0`。**非 loopback 入站必须带接入令牌，否则 401**；
本机（`127.0.0.1`/`::1`）**无条件放行**。

- 本机放行不是省事：要求本机也带令牌就得同步改**三份**客户端配置，
  漏一份的表现是「接入完成但一直 401」，用户无从判断是配置还是代理坏了。
- 令牌存 `secrets.enc` 不存 `config.json`：① `AppSettings` 的字段会被前端批量
  `saveSettings` 覆盖，在这里失效方向是「鉴权静默失效」；
  ② 锁定态 `get` 返 `Err` → 本模块把 Err 当拒绝 → **自动 fail closed**。
- 令牌在 `ProxyManager::start` 开局域网时生成，并落一条**带明文令牌的事件** ——
  那是目前用户唯一的获取通道（设置页 UI 未做，见 §7 B5）。

实现在 `lan_guard.rs`。

### 14.3 MCP 的 Origin 校验

MCP **恒定绑 `127.0.0.1`**，不跟随 `lan_exposure`。
`origin_allowed` 做 DNS rebinding 防护：只放行 loopback 源与 `null`，
无 Origin 头放行（非浏览器客户端不发 Origin），
且**校验在 OPTIONS 预检之前** —— 非法源连 CORS 许可都拿不到。

⚠️ 所以响应头里那个 `access-control-allow-origin: *` **不构成漏洞**。
本仓曾只看到那个头就推断「任何网站可通过浏览器调本机 MCP」，
核实后不成立 —— **那是不完整的取证**。有 `origin_gate_blocks_web_pages_but_not_native_clients` 钉着。

### 14.4 签名密钥台账（**每次换钥必须更新**）

| KeyID | 生效区间 | 覆盖版本 | 状态 |
|---|---|---|---|
| `1F6689C022960775` | 初始 ~ 2026-08-14 | ≤ v0.1.19 | 退役，无留存副本 |
| `DE14C6EC68286277` | 08-14 ~ 08-16 | **仅 v0.1.23** | 🔴 连口令一起公开，**永久失效** |
| `7A46ECB8087DE26F` | 08-16 起 | v0.1.26 ~ 现在 | 现役，**未泄露 → 不要换** |

**换钥的代价**：已发布客户端嵌着当时的公钥，换私钥 = 所有老用户应用内更新失效、
只能手动重装。这个代价已付过两次。停在 v0.1.23 的用户处境最坏
（正版更新收不到，用泄露钥签的伪造更新收得到）——
已在官网下载页与 Release 说明做了带外通知。

**也没法用一次「桥接发布」捞回来**：`latest.json` 一个平台只能带一个签名，
而老客户端问的是同一个 URL。给它签旧钥会让新版客户端全部拒收，净效果更差。

## 十五、本仓缺陷分类法（写新代码前的自查表）

这七类是从实际修过的缺陷里归纳的。**动手前对着过一遍**比事后审查便宜得多。

### 1. 静默失效 —— 代码在、就是不生效

- 开机自启动：字段在、UI 能点、值落盘，后端**从无代码**注册自启动项
- Tailwind 透明度修饰符只认标度内的值：写 `bg-warning/8` **不报错、一条 CSS 都不生成**
  （全仓 20 处这么写，一直「有边框有字色、独独没底色」而无人发现）
- `builtin_seed()` 只在 `vendors.is_empty()` 时注入 → 加了厂商但老用户看不到

**自查**：加任何用户可见的开关/输入前，先 grep 后端是否真的**读**它。

### 2. 界面说 A、实际 B

- 「切回官方」复位 deploymentMode 却保留 MCP 注册 → 那句「大脑聚合继续可用」是假的
- 托盘启停语义与界面按钮不一致 → 「托盘说已启动、客户端没走代理」
- §6 那四条

### 3. 数字当着用户的面变错

- 90 天滚动删桶让「累计用量」每 90 天掉一截
- v1 用量文件的 `entries` 重启一次就永久消失
- 「今日用量」比「累计」慢一分钟（未落盘增量没并进当天桶）
- 计费倍率填 `"inf"` 能把金额撑成 $18446744073（`f64::INFINITY` 能过 `> 0.0`）
- 单价表停在**退役价** → 全仓金额恒为真值 3 倍

### 4. 代理自己造成的失败算在上游头上

- 被故障转移预算掐短的尝试计入熔断 → 排在预算末尾的候选每轮被削短，**系统性偏置**
- `Retry-After` 取**最大**值 → 一个撞配额的 Key 拖垮整池
- 补全端点 404 三次打停整条 Key → 已加**模型级锁定**作为第二层

### 5. 排障时看到的是假现场

- 流式失败的链路快照把**下游原始请求体**当成「上游请求」（跨协议时根本不是一回事，
  而 400 的成因几乎全在转换里）
- 折叠日志展开后看的是第 1 次的正文，而表头是最近一次

### 6. 指错方向的告警比没有告警更糟

- 更新失败：网络不通 / 清单缺平台条目 / 验签失败 三类挤成一句归因
- Codex 漂移告警不分形态 → 每支说的必须是那个形态下 Codex **实际的**行为
- 用量「—」的四种成因分开报，只有一种该给「去设默认兜底模型」那句

### 7. 事件环被噪音挤满

`MAX_EVENTS` 是个**环**。任何「每次都记一条」的事件都会把有用的挤出去。已修过三处：
短路窗口每次重发记一条、MCP 分类回落每次记一条、局域网被拒每个 IP 只记一条（本轮）。

**自查**：新增事件前问「它会不会高频？」高频就必须节流。

## 十六、环境与协作约定

### 硬规则

- 改配置/二进制前**必先备份**（带日期后缀，可回滚）
- **禁止把本机路径硬编码进代码**，路径一律动态解析（有机械判据）
- 提交信息与代码注释用**中文**；注释写**为什么**，不只写做了什么
- 只在用户明确要求时提交；`git add` 指定文件，不用 `git add .`

### 本机环境的三个已知坑

1. **终端中文输出会间歇性乱码。** 不能把损坏的输出当源码读 ——
   本仓因此误报过三条不存在的官网缺陷。拿不准就用 Read/Grep 工具重取，
   或改用只输出 ASCII 的判据。
2. **`gh` CLI 没装。** 查 CI 用 REST API，token 从 git 凭据存储取：
   `printf "protocol=https\nhost=github.com\n\n" | git credential fill`。
   仓库是公开的 `EngineeMoMo/SynaRoute`。
   本机 `git clone` / `raw.githubusercontent.com` 被墙，**`api.github.com` 正常**。
3. **Node 在 Git Bash 下不认 `/tmp`。** 它是 Windows 二进制，
   `fs.readFileSync('/tmp/x.json')` 会去找 `C:\tmp\x.json`。
   改用 stdin 管道或 `process.env.TEMP`。
