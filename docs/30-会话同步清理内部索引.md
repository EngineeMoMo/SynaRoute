# 30 · 会话同步清理内部索引（2026-09-13，v0.1.63）

## 30.1 问题定性：Desktop 侧栏被内部线程刷满

**症状**：用户报告 Desktop 侧栏出现大量 "The following is the Codex agent history..." 标题的会话记录，这些是 Codex 内部的 `guardian_review` 子代理线程。

**根因分析**：
1. **Codex 自己刻意不收它们**：本机取证 `threads` 3 行（含 1 条 guardian）但 `local_thread_catalog` 只有 **2 行**，且 `initial_build_complete = 1`、`observation_sequence` 已到 37 —— Codex 扫过了但决定不收。
2. **我们的补录逻辑把它们插了进去**：`plan_from` 的标题表达式用 `COALESCE(name, title, ...)`，而 guardian 的 `name` 是 NULL、`title` 存的是 Codex 注入的那段英文 → 被写进 `local_thread_catalog.display_title`。
3. **`worth_listing` 原先没有拦截内部线程**：只要有 rollout 就补，不看 `thread_source`。

**用户机器 vs 本机的差异**：
- **用户那台**：从官方登录切过来 → provider 从 `openai` 改成 `synaroute` → 进 `done_ids` → guardian 被插入
- **本机**：那条 guardian 早就是 `synaroute`、压根没进 `todo` → 本机取证「catalog 干净」什么都不证明

## 30.2 解决方案：三道防线 + 精确清理

### 插入防线：`worth_listing` 判据
```rust
fn worth_listing(row: &CatalogRow) -> bool {
    !row_is_confirmed_child(row) && !row.forked
}
```

`row_is_confirmed_child` 当前同时检查 `forked`、`thread_source == "user"`、
以及 `thread_source` / `source_kind` 中的已知内部线程标记。标题前缀只用于
`view::is_injected_prompt` 等展示/导出过滤，**不是** catalog 插入或删除证据。
因此 fork 在插入门上会被排除，不是「必须收录」；它的 `payload.id` 还可能是父会话 id，
误插入会把父行当成子行处理。

### 清理机制：精确删除已确认的内部索引行

**证据收集**（`codex_session_sqlite.rs::collect_child_thread_ids`）：
- 查 `thread_spawn_edges.child_thread_id`（父子边）
- 查 `agent_job_items.assigned_thread_id`（如果该列存在）
- 查 structured/text `source` 里的 `subagent` / `sub_agent` / `internal` 标记
- **跨所有 session DB 收集**（catalog 与 threads 可能在不同文件）

**当前删除判据**（`codex_session_catalog.rs::row_is_confirmed_child`）：
```rust
fn row_is_confirmed_child(row: &CatalogRow) -> bool {
    !row.forked
        && !row.thread_source.trim().eq_ignore_ascii_case("user")
        && (thread_source_marks_child(&row.thread_source)
            || source_kind_marks_child(&row.source_kind))
}
```

**catalog 行级 user 否决已实现（2026-09-15，原 `docs/08 A8-6`）**：`catalog_user_ids` 从库里
读出该 host 下 `thread_source='user'` 的 id 集合，删除侧与 `would_mutate` 都据它否决。于是
「rollout 已不存在、catalog 自己仍标 `user`、而 edge/job 证据把同一 id 带回成 stub」这个
冲突形态不再会被删。

🔴 **否决只作用于删除，不作用于更新**：provider 同步与清 `missing_candidate` 都是无损的，
被 user 标记救下来的冲突行**必须照常同步** —— 否则第三份 provider 副本在那些行上永远是
旧值。（第一版把更新也一起掐掉了，是写判据的用例当场抓出来的。）

**删除流程**：
1. 每个库先 `backup_db`（含 WAL），失败则跳过该库
2. 按 `(local host_id, thread_id)` 精确删除 catalog 行
3. 增加 `catalog_revision` 计数
4. **不删** rollout、`threads`、`thread_spawn_edges`、session 正文
5. **不改** `local_thread_catalog_sync_state` 水位线

### 为什么删除必须这么保守

**三条铁律**（详见 `codex_session_catalog.rs` 模块头）：
1. **catalog 带着 Codex 自己的账**：`observation_sequence` 递增序号、`catalog_revision`、sync_state 水位线 —— 写错这些不是「少一行」，而可能让 Codex 自己的扫描器判断错
2. **删除必须有正向证据且无冲突**：正向证据来自 `thread_spawn_edges` / `agent_job_items` / structured source 标记；当前实现对 rollout 证据检查 fork 与 user，但对「仅存在于 catalog 的 user 标记」仍有 A8-6 边界
3. **catalog 自身的证据只作用于同一个 DB 路径** —— 防止一个库的过时记录删掉另一个库的真实行

## 30.3 顺带修复：标题表达式缺 `NULLIF`

**症状**：可能补出**没有标题的空行**（侧栏显示一条点不出名字的记录）。

**根因**：`COALESCE` 只跳过 NULL，而 `name` 完全可能是**空串**（Codex 异步生成标题，没生成时就是 `''`）。

**修复**：
```rust
fn title_expr_for(cols: &HashSet<String>) -> String {
    let inner = ["name", "title", "preview", "first_user_message"]
        .iter()
        .filter(|c| cols.contains(**c))
        .map(|c| format!("NULLIF({c}, '')"))  // 每列都套 NULLIF
        .collect::<Vec<_>>()
        .join(", ");
    if inner.is_empty() { "id".into() } 
    else { format!("COALESCE({inner}, id)") }
}
```

**为什么这个坑之前没暴露**：`view::thread_info` 一直带 NULLIF，`plan_from` 这一处漏了 —— 同一件事两份实现漂移。

## 30.4 代码审查修出的第二条

**症状**：导出一条 guardian 会话时，Codex 注入的那段 `<environment_context>` 被当成用户真话写进 Markdown。

**根因**：导出侧 `classify_user_text` 自己写了一份注入判据、只认 `<environment_context>`，不认 guardian 那个前缀 —— 而模块头明写「绝不导出」那一类。

**修复**：改为委托 `view::is_injected_prompt`，现在只有**一份实现**、4 个生产调用点。

**判据是前缀不是 `contains`**：后者会把「用户自己贴那段来提问」也吞掉 —— 真话被当噪音丢掉比多留一段噪音糟。有反向用例钉着。
