## 优先补齐的事项

### P1：上游没有完成事件，转换器仍补发成功

**已复现。** 给 Chat→Responses 翻译器一条带文本、`finish_reason: null` 的增量，随后让流正常 EOF；既没有结束原因，也没有 `[DONE]`。当前输出仍包含 `response.completed`，并把半截文本标为 completed。

生产路径：

- `src-tauri/src/proxy/streaming.rs:89` 在 EOF 时仅用 `saw_error()` 判断是否失败；没有显式错误就记录 `End::Complete` 并调用翻译器 `finish()`。
- `src-tauri/src/upstream/mod.rs:183` 的 `sse_stream_errored()` 只识别可解析的错误事件，源码明确写出截断不在覆盖范围。
- `src-tauri/src/upstream/sse.rs:265` 的 `finish()` 可以直接补发成功终态，没有确认上游是否真正完成。

影响：客户端会把不完整答案当作正常结束；生产流末处理还会按成功结算健康/会话保持状态。后一个影响来自调用链静态分析，尚未通过真实 ProxyManager HTTP 用例单独测量。

建议按上游协议记录明确终态、失败及截断状态；EOF 缺少必要终态时输出下游错误并按失败结算。已经向客户端输出内容后，不应通过自动重放整个请求来掩盖问题。覆盖正常完成、干净 EOF 截断、传输错误、用户取消、工具参数只收到一半以及 usage 尾帧等情况。

参考：`D:\ReferenceProject\ccLoad\internal\app\proxy_forward.go:1093` 的转换流截断判定，及其相邻协议测试。ccLoad v4.13.1 的发布说明已列出这一类修复。

### P1：SSE 的 event 字段未参与错误识别

**已复现。** Responses→Anthropic 收到正常文本增量后，再收到 `event: error`、但 JSON 只带 `message` 的事件，当前没有输出错误，结束时反而输出正常 `message_stop`。

原因：`src-tauri/src/upstream/sse.rs:280` 逐行只取 `data:`；`event:` 被忽略。健康错误检测也只看 JSON 内的 `type/error`。不是所有命名事件都会在 JSON 中重复事件类型。

建议以 SSE 帧为单位解析并保留 event 名、多行 data、分块状态；明确事件名应参与错误判定。CLIProxyAPI v8.0.76 的发布说明包含“尊重显式 SSE 事件类型”、字符串/无类型错误与嵌套 Retry-After 保留，适合一起对照，但其中其他项目尚未在 SynaRoute 逐项证明为缺陷。

复现结果：

| 场景 | 当前识别错误 | 输出成功终态 | 输出失败事件 |
|---|---|---|---|
| Chat→Responses：无终态直接 EOF | 否 | 是 | 否 |
| Responses→Anthropic：命名 error、JSON 无 type/error | 否 | 是 | 否 |
| 对照：JSON 有 error 对象 | 是 | 否 | 是 |

本轮复现直接编译当前 `sse.rs`、`sse_error.rs`、`sse_bounds.rs`、`tools_meta.rs`，其辅助函数从当前源码提取；Protocol/TokenUsage 用最小类型定义。它验证生产翻译器与错误检测函数，并非完整 HTTP、原生客户端或安装包测试。

### P2：动态思考判断请求未纳入用量账本

`src-tauri/src/decision.rs:301` 的 `query()` 取得响应后只解析并返回 JSON，没有把判断服务的 token/费用记入账本。它同时服务会诊和原生档位选择；`docs/19-开发文档.md:71` 也明确记录这一限制。

路由意图判断走另一个 `upstream/routing_judge.rs`，已有用量接线，不能把两条路径混为一谈。

建议分别显示判断调用与业务模型调用；服务不返回 usage 时标为未知，不把它计作零成本。接收费判断服务时，这比直接宣传“自动思考省钱”更有价值。

### P2：会话列表只有前端分页，首次仍扫描完整快照

`src-tauri/src/tools/codex_session_ops.rs:495` 调用 `list_at()` 返回完整列表；`src/components/SessionBrowser.tsx:34` 才执行 slice。已有分页减少渲染，不减少初次文件/数据库读取。

建议增加后台增量索引和分页详情读取，缓存失效包含数据库、WAL/SHM、文件替换及 CODEX_HOME；仍须保留仅存在 rollout 文件、没有数据库行的会话。

参考 CodexPlusPlus `docs/session-paging.md` 及 `crates/codex-plus-data/src/storage/session_paging.rs` 的 ID/更新时间缓存、本页详情读取、短事务和部分失败处理。其源码许可为 AGPL-3.0，不能按 MIT 项目处理；优先按需求独立实现并编写适合本项目的测试。

### P2：Laya 版本及判断能力需要重新评估

本项目 `scripts/laya/requirements.lock.txt:37` 锁定 **0.3.29**，上游正式版为 **0.4.35**。当前 Laya 仅做高置信度的“是否需要深入推理”判断；命中时提升到模型目录中的 high，不降低用户手动档位。`decision/laya_judge.rs` 保存了旧版对中文/英文任务的测量依据，这个保守行为有明确原因。

建议分两步：

1. 用固定中文任务集与独立保留集对比旧版和 0.4.35，测误降档/误升档、截断、长任务、跟进问题及冷/热延迟，再决定是否改变当前规则；同时更新依赖哈希、模型固定版本和真实安装/离线复用验证。
2. 单独试验上游 `laya-rust`，crate 名为 `laya-onnx`，源码版本 0.1.0，使用 ONNX Runtime。它有机会替代本项目目前的 Python/venv/本地 HTTP 服务链，但仍需要模型文件、运行时、内存管理和安装验证。

不能将 Rust 版视作完整等价替换：其 README 明确注明路由/语言检测对齐 Python 0.4.14，histogram-binning 校准和 per-call hooks 尚未移植。本轮没有下载模型或运行新版本推理，没有验证性能提升。

### 最有价值的具体方向

**先补协议可靠性。** ccLoad 和 CLIProxyAPI 的更新能直接对应本轮已复现缺口。先补明确终态、命名错误事件及其回归，再逐项检查错误状态/Retry-After 等新修复是否也适用。

**再评估 Laya 的 Rust/ONNX。** 这是与本项目 Rust 后端相契合、可能显著减少环境安装环节的方向。收益必须用打包体积、首次启动、常驻内存、冷/热判断延迟和独立任务集质量来验证。

**谨慎借鉴 opencodex 的逐消息 effort。** v2.100.4 发布说明标为 experimental；源码仅在特定官方 Anthropic API、认证方式、模型和流式 Codex 入口生效，其他形态关闭。它维护历史身份、HMAC 摘要、容量和过期，不是简单插入一条 system message。本项目多数中转未必支持，不能直接宣布所有上游都能保缓存调档，更不能把代理请求改写说成官方客户端内部档位已经改变。

**cc-switch 的已有会话切回官方值得专项验。** 它先将待删除的环境值写为空，让运行中的 Claude Code 感知变化，再延迟删除。本项目当前主要恢复备份文件，尚未发现同类两阶段流程；但本轮没有在真实 Claude 会话复现，所以记录为待验证兼容项，不直接认定为已确认 bug。模型目录请求的默认 User-Agent 本项目已经有，不重复列为缺失。

WebSocket Responses、远程控制、更多原生协议、生成过程检查点调档属于可选扩展。应先根据实际客户端使用情况决定立项，当前证据不足以把它们全部定为必做需求。
