# secrets/ —— 加密后可入库的凭据

> [!CAUTION]
> **本目录里的 `synaroute.key.gpg` 目前不可信、也不可用，见下面「当前状态」。**
> 换机恢复**不要**照它走 —— 那会让你签出一个所有客户端都验不过的更新，而且构建不报错。

## 里面是什么

| 文件 | 内容 | 加密方式 |
|---|---|---|
| `synaroute.key.gpg` | Tauri 在线更新签名私钥的一份**旧副本**（2026-08-13 入库） | GnuPG 对称加密，AES-256，口令保护 |

## 当前状态（2026-08-23 实测）

这份密文有两个独立问题，任一都足以让它不能用于恢复：

1. **它保护的钥已经退役两轮。** 它入库于 `d2aa615`（08-13），而此后换过两次钥
   （见下面的钥匙台账）。按提交时间推断里面是 `1F6689C022960775`，
   **无法直接确证** —— 里层 rsign 口令未知，解不出来。
2. **它的 GPG 口令已经公开。** 那句口令曾被写进 `GITHUB_SECRETS_SETUP.md` 正文、
   随 `29b9257` 推上公开仓库（实测：用那句口令能解开本文件）。也就是说
   「密文可以公开，因为口令只有我知道」这个前提**已经不成立**。

不幸中的一点运气：外层 GPG 解开之后，里面那把 rsign 私钥**自己还带口令**，
而那个口令与已泄露的那句**不同**（实测用它签名报 `Wrong password for that key`）。
所以拿到这份密文的人还差一步，但别把这当成防线 —— 当作已泄露处置。

**建议：把这份 `.gpg` 从仓库里删掉，不要重新生成一份。**

```bash
git rm secrets/synaroute.key.gpg
```

它换来的好处是「换机自助恢复」，而这个好处「口令进密码管理器 + 明文私钥离线备份（U 盘）」
已经覆盖（本文件下面也一直这么要求）；它的代价是在公开仓库里多一个攻击面 ——
而这次泄露正是这个模式的产物。删除是一条命令，重新造一份的收益却是负的。

## 🔑 钥匙台账（**每次换钥必须更新这张表**）

原来这里只记了一次换钥，实际发生过两次。漏记的那把恰好就是泄露的那把，
于是排查时第一反应是「泄露的是现役钥」—— 一次因为台账不准而导致的误判。

| KeyID | 生效区间 | 覆盖的发布版本 | 私钥现在在哪 |
|---|---|---|---|
| `1F6689C022960775` | 初始提交 ~ 2026-08-14 | ≤ v0.1.19 | 本目录的 `.gpg`（推断）；口令未知 |
| `DE14C6EC68286277` | `29b9257`（08-14） ~ 08-16 | **仅 v0.1.23** | 🔴 **已连口令一起公开**，永久失效 |
| `7A46ECB8087DE26F` | `983c333`（08-16） 起 | v0.1.26 ~ 现在 | 只在 `~/.tauri/synaroute.key` 与 GitHub Secrets |

判据取法（换钥后自己复核用）：

```bash
# 某个版本的客户端认哪把公钥
git show v0.1.23:src-tauri/tauri.conf.json | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>console.log(Buffer.from(JSON.parse(s).plugins.updater.pubkey,'base64').toString().split('\n')[0]))"
```

### 现役钥没有口令

`~/.tauri/synaroute.key` 是**明文**（`docs/18 §3.4` 的 `签名口令为空` 说的就是它），
拿到文件即可签名。所以它的安全性完全取决于「那台机器的 home 目录有没有被同步/备份出去」：

- GitHub Secrets 是**运行副本**，发版只用它；
- 本地那份只当**离线备份**：用新的、强的、只存在密码管理器里的口令 GPG 加密，
  放 U 盘或外部盘，**不要**放进任何会同步的目录，更不要放进仓库。

## ⚠️ 换钥的代价（想换之前先读）

已发布客户端的二进制里嵌着当时的公钥，**换私钥 = 所有老用户的应用内更新失效**，
只能手动重装。这个代价已经付过两次：

- 停在 **≤ v0.1.19** 的用户，收不到 v0.1.23 之后的更新；
- 停在 **v0.1.23** 的用户，收不到 v0.1.26 之后的更新 —— 而这批人最糟：
  正版更新收不到，用泄露钥签的伪造更新却收得到。

也没有办法用一次「桥接发布」把他们捞回来：`latest.json` 一个平台只能带一个签名，
而老客户端问的是同一个 `releases/latest/download/latest.json`。给它签旧钥会让新版客户端
全部拒收，净效果更差。**结论：老版本用户只能带外通知（README / 官网 / Release 说明）手动重装。**

推论：**现役钥没泄露的情况下不要换它。** 换它只会再制造一批被甩掉的用户。

## ⚠️ 口令丢了 = 钥匙丢了

密文谁都解不开，包括你自己。口令必须另存（密码管理器），且仍要留一份明文私钥的
离线备份。仓库里那份从来不该是唯一副本。

## 机械判据

「密钥与口令不得进仓库」现在有脚本盯着，不再只是一条文字规矩：

```bash
npm run check:secrets      # 单独跑
npm run check:forbidden    # 策略门，gates 与 CI 都跑
```

实现在 [`scripts/lib/secret-scan.mjs`](../scripts/lib/secret-scan.mjs)，判据是
**解码后的内容特征**（这次的密钥包了一层 base64，按文件名判和按明文 grep 判都抓不到），
并且会拿仓库里出现过的口令去试解仓库里的密文 —— 就是上面第 2 条那个坑。

它只扫工作区，**不扫 git 历史、不扫 fork**。门变绿只代表「没有新增」。
